## 문제와 해결

### 1. 환불이 토스 결제를 취소하지 않았다

- **증상(코드 확인)**: `POST /api/credits/purchases/{orderId}/refund` 는 크레딧만 빼고 `REFUNDED` 로 바꾸는 "모의 환불"이었다. 토스 테스트 결제 내역은 승인 완료로 남았다.
- **정책(11-26 결정)**: 전액만(부분 취소 없음), 결제 승인 시각(`paidAt`) + 168시간 전까지, 잔액이 구매한 크레딧 이상이면 환불. 크레딧은 잔액 하나로 합쳐져 있어 결제 건별로 "그 결제분을 썼는지"는 따지지 않는다.
- **해결**: 결제 승인(`confirm`)처럼 외부 호출을 트랜잭션 밖에 두고 세 단계로 나눴다.
  1. 구매 행을 잠그고 조건 확인 → 크레딧 회수(`PURCHASE_REFUND`) → `REFUNDING`. 한 트랜잭션.
  2. 토스 `POST /v1/payments/{paymentKey}/cancel`(사유만 보내 전액 취소, `Idempotency-Key`).
  3. 취소 확인(`CANCELED`, 주문·결제 키 일치)이면 `REFUNDED`. 토스가 취소하지 않은 것이 확실한 오류(`NOT_CANCELABLE_PAYMENT`, `EXCEED_MAX_REFUND_DUE`, `REFUND_REJECTED` 등)면 크레딧을 되돌리고(`PURCHASE_REFUND_UNDO`) `PAID`. 그 밖(이미 취소됨·처리 중·일시 장애·응답 없음)은 토스 조회로 확인하고, 그래도 모르면 `REFUNDING` 으로 남겨 다시 누르면 이어서 처리한다.
- **크레딧을 토스 호출 전에 빼는 이유(논리)**: 뒤에 빼면 토스를 기다리는 사이 사용자가 크레딧을 다 써 버려 돈과 크레딧을 둘 다 돌려주게 될 수 있다. 결과를 모를 때 "크레딧은 빠졌는데 결과 모름"이 "돈은 나갔는데 크레딧이 남음"보다 안전하다.
- **마이그레이션 없는 방법도 검토(결정)**: 토스 호출 동안 잠금을 잡은 트랜잭션 하나로 묶으면 V32 가 필요 없지만, DB 연결·회원 잠금을 최대 약 20초 잡고, 취소 요청과 조회가 모두 응답 없을 때 롤백되어 위의 덜 안전한 쪽이 된다. 마이그레이션 쪽을 택했다.

### 2. 거절 뒤 다시 환불하면 원장 고유 인덱스에 막힌다

- **원인(코드 확인)**: `credit_ledger_purchase_reason_once` 가 구매 1건에 같은 사유의 원장 행을 하나만 허용한다. "거절 → 되돌림 → 다시 환불"을 허용하면 두 번째 `PURCHASE_REFUND` 가 막힌다.
- **해결**: 토스가 확실히 거절한 결제는 다시 시도해도 대부분 또 거절되므로 그 구매는 재환불을 막는다(409 "토스에서 환불을 거절한 결제입니다. 문의해 주세요."). 되돌림 기록 유무로 판단한다.

### 3. 같은 멱등 키로 다시 요청하면 첫 오류가 그대로 돌아올 수 있다

- **원인(토스 문서)**: 같은 키의 같은 요청은 다시 처리하지 않고 첫 응답을 돌려준다(15일). 첫 응답이 일시 오류였다면 같은 키로는 계속 그 오류만 받는다.
- **해결**: 이어서 처리할 때마다 새 키를 쓴다. 전액 취소는 한 번만 성공하고 두 번째는 `ALREADY_CANCELED_PAYMENT` → 조회로 `CANCELED` 확인 → `REFUNDED` 가 되므로 키를 바꿔도 두 번 환불되지 않는다. 마무리 단계는 키 일치를 요구하지 않는다(토스가 이 결제의 취소를 확인했으므로).

### 4. V32 를 운영 전에 Postgres 에서 돌려 볼 곳이 없었다

- **원인**: 테스트는 H2 에서 엔티티로 스키마를 만들어(`ddl-auto: create-drop`, Flyway 꺼짐) 마이그레이션 SQL 을 실행하지 않는다. 앱 기본 DB 주소는 운영 RDS 다.
- **해결(측정)**: PC 에 있던 `pgvector/pgvector:pg16` 이미지로 임시 컨테이너(`127.0.0.1:55432`)를 띄우고, DB 주소를 명령줄 인자로 넘겨(설정 파일보다 우선) 앱을 한 번 기동했다. 셸에 RDS 비밀번호 환경 변수도 없어 RDS 에는 붙을 수 없었다. `postgres:16-alpine` 은 V1 이 쓰는 `vector` 확장이 없어 실패해서 pgvector 이미지로 바꿨다.
- **확인**: 빈 DB 에 29개 마이그레이션(V1~V32) 적용, Hibernate 스키마 검증 통과, 앱 기동(`Started PairApplication`). 롤백하는 트랜잭션 안에서 환불 흐름 SQL 6건(REFUNDING·멱등 키 저장, 되돌림 저장과 PAID 복귀, 같은 구매 되돌림 두 번 차단, 음수·구매 번호 없는 되돌림 차단, 없는 상태 값 차단, REFUNDED 완료) 모두 통과. 컨테이너는 지웠다. 운영 `main` 배포(10:00) Release 도 성공했다.

### 5. AI 채팅 분당 제한을 스트림 안에서 걸면 429 를 줄 수 없다

- **원인(코드 확인)**: `/chat/stream` 은 `SseEmitter` 를 먼저 돌려주고 답은 다른 스레드에서 받는다. 그 안에서 예외가 나면 HTTP 상태는 이미 200 이고 SSE `error` 이벤트로만 알릴 수 있다.
- **해결**: 컨트롤러가 응답을 만들기 전에 `attempts.checkChatRate(id)` 를 먼저 부른다(`/chat` 도 같게). 넘으면 `TooManyChatsException` → 429 + `Retry-After` + 안내 문장. 1인 한도와 전체 한도를 함께 보고 둘 다 통과한 요청만 센다(막힌 요청은 세지 않고 AI·크레딧도 건드리지 않는다). 사람은 빌드·실행 제한과 같게 자가진단은 회원, 실전은 응시 1건으로 센다.
- **프런트**: 바꾸지 않았다. 스트림 요청이 실패하면 응답의 `message` 를 보여 주는 코드(`src/api.ts`, 크레딧 부족 402 와 같은 경로)가 이미 있다.
- **확인(테스트)**: 10번까지 통과, 11번째 스트림 요청은 스트림이 열리지 않은 채 429 와 `Retry-After`, AI 미호출, 다른 회원은 따로 셈(`ChatRateLimitIntegrationTest`). 단위 테스트 5개(1인·전체 한도, 막힌 요청 미집계, 1분 뒤 재허용, 설정값 검사).

## 결정

- **환불 정책**: 전액만, `paidAt` + 168시간(한국 날짜 기준보다 단순하고 시간대 문제가 없다), 잔액이 구매분 이상. "결제 뒤 한 번이라도 쓰면 불가"(원장 순서로 판단 가능)도 검토했지만 쓰지 않는다. 금액 계산은 어느 쪽이든 맞는다.
- **AI 채팅 분당 제한**: 팀 합의안 그대로(1인 10, 전체 300, 스트림 열기 전 429). 한도는 설정(`pair.assistant.rate-limit-per-minute`, `total-rate-limit-per-minute`)으로 바꾼다.
- **채팅 제한은 Redis 대신 서버 메모리**: 명세는 Redis 였지만 앱 서버가 1대이고 빌드·실행 제한과 같은 방식이다. Redis 로 세면 Redis 가 잠깐 멈출 때 채팅까지 막힌다. 서버 2대 이상을 겹쳐 돌리는 배포(블루그린)를 하면 Redis 로 옮긴다.
