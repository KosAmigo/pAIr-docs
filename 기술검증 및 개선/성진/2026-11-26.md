## 문제와 해결

### 1. 서버를 재시작하면 채점 중이던 응시가 `SCORING` 에 영원히 남았다 (52번 응시)

- **증상**: 52번 응시가 `SCORING` 에 멈춰 있었다.
- **원인**: 채점 큐가 꺼진 운영에서는 채점이 서버 안 스레드 풀(메모리)에서 돈다. 재시작하면 하던 작업과 기다리던 작업이 모두 사라지는데, 다시 맡기는 곳이 없었다. 큐를 켜기 전에 `SCORING` 이던 응시는 Redis 에도 없어서 큐의 복구(`recoverStale`)로도 살아나지 않는다.
- **해결**: 서버가 뜰 때(`ApplicationReadyEvent`) `SCORING` 응시를 찾아 다시 채점에 맡긴다. 끊긴 채점 기록(`RUNNING`)은 ERROR 로 닫는다. 24시간 채점 한도(10번)를 넘은 응시는 다시 맡기지 않고 ERROR 로 둔다(재시작이 반복돼도 비용이 늘지 않게). 큐 모드에서는 `enqueue` 의 중복 방지 표시가 두 번 넣는 것을 막는다.
- **전제**: 서버가 하나다. 두 서버가 겹치는 블루그린 배포를 하면 다시 검토한다(코드 주석에 남김).

### 2. 배포·종료 때 채점이 10초 만에 강제로 잘렸다

- **증상(코드 확인)**: Docker 는 `stop` 뒤 기본 10초에 SIGKILL 을 보낸다. 게다가 `ScoringService` 는 종료 때 `shutdownNow()` 로 채점 스레드를 바로 끊었다.
- **해결**: `server.shutdown=graceful`(요청 마무리 30초) → 채점 풀은 새 작업을 받지 않고 하던 채점을 최대 90초 기다린다. 시작 전 작업은 버리고 1번 복구가 다시 맡긴다. 큐 작업자도 interrupt 대신 하던 작업을 마치고 끝난다. 운영 compose `stop_grace_period: 150s`.
- **확인(측정)**: 부하 테스트 3번 시나리오에서 재시작 신호를 받은 서버가 **41초 동안 하던 채점을 마치고** 내려갔고, 잘린 채점은 0건이었다.

### 3. 동시 채점 수를 늘려도 빨라지지 않았다 (부하 테스트에서 찾음)

- **증상(측정)**: 동시 채점 4와 8의 처리량이 모두 분당 약 5.2건으로 같았다.
- **원인**: 채점 모델 호출 스레드(`ScoringService.judgePool`)가 8개로 고정돼 있었다. 채점 1건 = 호출 3번 × 30초 = 90초 분량이므로 90초 ÷ 8 ≈ 11초에 1건, 곧 분당 약 5.3건에서 막힌다. 측정값(1144초 ÷ 100건 = 11.4초)과 맞는다.
- **해결**: 호출 스레드 수를 "동시 채점 수 × 채점 1건의 호출 수"(기본 4 × 3 = 12)로 바꿨다.
- **확인(측정)**: 동시 4 → 분당 6.8건(888초), 동시 8 → 분당 13.3건(450초). 동시 채점을 2배로 하자 처리량도 2배가 됐다.

### 4. 큐 모드에서 서버가 강제로 죽으면 하던 작업이 15분 뒤에야 살아났다

- **원인**: Redis 스트림의 처리 중 목록에 남은 작업은 `stale-after`(15분)가 지나야 되살린다.
- **해결**: 작업자 이름은 프로세스마다 새로 정해지므로, 시작할 때 처리 중 목록에 있는 작업은 모두 이전 프로세스가 남긴 것이다. 작업자가 시작할 때 기다리지 않고 바로 되살린다.
- **확인(측정)**: 4번 시나리오(큐 + SIGKILL)에서 잘린 4건이 서버가 다시 뜨자 모두 완료됐고, 전체 시간은 재시작이 없을 때보다 약 1분만 늘었다.

### 5. 후속 질문을 동시에 제출하면 채점이 두 번 시작될 수 있었다

- **원인**: `followUps` 가 상태를 읽어 확인한 뒤 따로 저장해서, 두 요청이 모두 확인을 통과할 수 있었다. 응시자가 두 번 누르거나, 시험 종료 자동 마무리와 응시자 제출이 겹치는 경우다. 큐가 꺼져 있으면 AI 비용이 두 번 들고 재채점 한도도 두 번 줄었다.
- **해결**: `FOLLOWUP → SCORING` 을 조건부 UPDATE 한 문장(`startScoring`)으로 바꿔, 바꾼 행 수가 1인 요청만 답을 저장하고 채점을 맡긴다(재채점의 `startRescoring` 과 같은 방식). 자동 마무리가 응시자에게 밀린 경우는 실패로 세지 않는다. 처음에는 예외를 모두 삼켰는데, 기존 테스트가 "진짜 실패를 숨긴다"고 잡아 줘서 상태를 다시 읽어 확인하도록 좁혔다.
- **확인(테스트)**: 8개 스레드가 같은 응시에 동시에 제출하면 1건만 성공하고 답도 하나만 저장된다(`FollowUpsConcurrencyTest`).

### 6. CI 가 가끔 `RemoteDockerRunnerProtocolTest` 포트 충돌로 실패했다

- **원인**: 테스트용 샌드박스 서버가 사용자 포트는 무작위(`server.port=0`)였지만, 관리(지표) 포트는 `application.yml` 기본값 8181 을 그대로 썼다. 같은 JVM 의 다른 컨텍스트가 8181 을 쓰고 있으면 `PortInUseException`.
- **해결**: 테스트 서버에 `--management.server.port=0` 을 함께 넘겼다. 다시 돌리기 대신 원인을 고쳐서, 다른 병합도 이 테스트에 막히지 않는다.

### 7. 큐를 켠 첫 배포가 실패했다 (운영)

- **증상(로그)**: 팀원의 `main` 배포(Release `45760865601`)가 "백엔드가 올라오지 않았습니다"로 실패했다. 백엔드 로그에는 `UnknownHostException: redis`.
- **원인**: `APP_SECRET_YML` 에 큐 설정을 넣어 큐가 켜졌는데, 운영 compose 의 Redis 는 `profiles: ["redis"]` 로 묶여 있어 배포가 만들지 않았다. Redis 상태 점검도 큐 설정을 따라 켜져서 `/actuator/health` 가 DOWN 이 됐고, 배포가 UP 을 기다리다 실패했다. 제출·채점은 서버 안에서 바로 채점하는 방식으로 계속 동작했다(설계대로).
- **해결**: 서버에서 `docker compose --profile redis up -d redis` 로 Redis 만 켜자 백엔드가 알아서 붙고 health 가 UP 이 됐다. 재발 방지로 운영 compose 에서 Redis 의 프로필을 빼서 배포가 항상 만들게 했다.
- **주의(논리)**: 서버에서 손으로 `docker compose up -d` 를 할 때는 **서비스 이름을 붙인다**. 이미지 태그가 `${BACKEND_TAG:-latest}` 라 서버 셸에서 그냥 부르면 백엔드·프런트가 `latest` 로 다시 만들어질 수 있다.

### 8. 팀원이 `main` 에 바로 올린 작업과 develop 이 충돌했다 (아래 9는 이어지는 문제)

- **원인**: 팀원의 환경 점검 사진 작업과 AI 비용이 같은 `ExamConsoleController` 생성자에 서비스를 하나씩 추가했다.
- **해결**: `chore/sync-main` 에서 `origin/main` 을 develop 쪽으로 먼저 받아 둘 다 넣는 것으로 풀고(`f882b93`), CI 를 거쳐 develop 에 병합했다. 그 뒤 `main ← develop` 은 충돌 없이 끝났다. 팀원의 새 사진 API 2개도 회사 분리 테스트에 넣어 다른 회사 404 를 확인했다(`d4ce28e`).

### 9. Redis 가 잠깐 없어도 배포가 막혔다 (7번의 재발 방지)

- **원인**: 큐를 켜면 Redis 상태 점검도 켜지고, 그 점검이 전체 `/actuator/health` 에 들어 있어서 Redis 하나만 죽어도 DOWN 이 됐다. 배포 확인이 이 주소를 봤다.
- **해결**: Redis 만 뺀 상태 그룹 `core`(`/actuator/health/core`)를 만들어 배포 확인이 이것을 보게 했다. 전체 상태는 그대로 Redis 까지 본다. Redis 장애는 작업자가 큐에서 꺼낼 수 있는지를 지표 `pair_scoring_queue_up`(1/0)으로 내고, 2분 넘게 0 이면 Prometheus 경고 `ScoringQueueDown` 을 띄운다. 큐가 꺼진 설정(테스트·기본)에는 redis 점검이 없어 "없는 점검을 뺀다"고 시작이 막혀서, 그룹 구성원 검사(`validate-group-membership`)를 껐다.
- **확인(측정)**: 부하 테스트 compose 에서 실제 Redis 를 끄자 전체 DOWN·core UP·지표 0, 다시 켜자 지표 1. 운영 Release `ca2e332` 가 새 주소로 상태 확인을 통과했다.

### 10. 관리자가 자가진단을 확인하려면 크레딧이 필요했다

- **원인**: 관리자에게도 응시 시작·AI 채팅·롤백 크레딧 검사와 차감이 그대로 걸렸다.
- **해결**: `CreditService` 의 검사·차감 6곳에서 관리자면 건너뛴다(원장에도 남기지 않는다). 잔액 API 에 `unlimited` 를 더하고, 화면은 관리자에게 잔액 칩·충전 버튼·대시보드 크레딧 칸을 보이지 않는다. 구매·환불은 그대로다.
- **확인(테스트)**: 잔액 0 인 관리자가 응시 25번·채팅 2번을 해도 막히지 않고 원장이 비어 있다.

### 11. 휴대폰 폭에서 자가진단 화면이 옆으로 밀렸다

- **증상(측정)**: 375px 폭에서 과제·대시보드·복기·충전·마이페이지 5개 화면 모두 문서가 905px 더 넓어 가로로 밀렸다(Playwright 로 `scrollWidth - clientWidth` 측정).
- **원인**: 머리(`SelfShell`)가 아니라 `index.css` 의 `body { min-width: 1280px }` 였다(375 + 905 = 1280). DESIGN.md 3.2 의 "앱 화면 최소 1280px, 모바일 미지원" 규칙이고, 로그인·휴대폰 보조 캠 화면만 풀려 있었다. 머리만 고치면 안 되는 이유: `md:` 같은 반응형 규칙은 문서 폭이 아니라 **화면 폭**을 보므로, 1280px 문서 안에 휴대폰용 머리가 들어가는 어색한 결과가 된다.
- **해결**: 자가진단 셸이 있는 화면은 `body:has(.self-shell)` 로 최소 폭을 푼다(로그인 화면과 같은 방식). 768px 미만에서 머리를 두 줄(로고·크레딧·충전·아바타 / 탭 3개)로 나누고, `SELF-CHECK` 배지는 숨기고 콘솔 버튼은 아이콘만, 크레딧 알약은 숫자만 보인다("크레딧"은 화면 읽기용으로 남김). 과제 화면은 추천 카드 제목이 한 글자씩 줄바꿈되던 것을 고쳐 한 열로 쌓았다. 데스크톱(768px 이상) 클래스는 그대로다. 응시·콘솔·채점 툴은 계속 데스크톱 전용이다.
- **확인(측정·테스트)**: 고치기 전 5개 화면 모두 실패 → 고친 뒤 넘침 0. `e2e/self-shell-mobile.spec.ts` 가 375px 넘침과 1280px 머리 한 줄(높이 56px) 배치를 같이 검사한다. 운영 CSS 에 새 규칙이 들어간 것도 확인했다.

### 12. e2e 2개가 원래 코드에서도 실패하고 있었다

- **원인**: 화면을 바꾸고 테스트를 고치지 않았다. ① 관리자 크레딧 무제한(10번)으로 관리자 머리에서 충전 버튼을 숨겼는데 `company-self-diagnosis` 는 관리자에게도 충전 버튼을 기대했다. ② 휴대폰 캠을 쓰지 않기로 하면서(11-24) 증거 구간 창의 휴대폰 줄이 "휴대폰 (이전 기록)"으로 바뀌고 예전 기록에만 보이는데, `evidence-console` 은 "휴대폰 N장"을 찾았다. CI 는 e2e 를 돌리지 않아 드러나지 않았다.
- **해결**: ① 역할별로 USER 는 머리에 충전·크레딧이 있고 ADMIN 은 없음을 검사한다. ② 새 표기를 검사하고, 휴대폰 사진이 없는 구간에는 휴대폰 줄·사진 버튼이 없는지 검사를 더했다(처음엔 "휴대폰" 글자 전체를 막았는데 이벤트 종류 "휴대폰 감지"와 겹쳐 사진 줄·버튼으로 좁혔다).
- **확인(테스트)**: 두 파일 데스크톱 1440·1280 모두 통과. 전체 e2e 에서 남은 실패는 `home-practice`(팀원 4 영역) 하나다.

## 결정

- **채점 큐**: 운영에서 켰다(`PAIR_SCORING_QUEUE_ENABLED=true`, Redis AOF). Redis 가 잠시 없어도 제출은 막히지 않는다.
- **내 정보 수정**: 이름만 바꾼다(1~50자, 로그인 유지). 이메일은 로그인 ID 라 바꾸지 않는다.
- **회차 AI 비용**: 관리자만 본다(매니저·감독관 403, 화면에서도 숨김). 승인된 기업은 무료라 원가를 보여 주지 않는다. 회사·회차 ID 를 Prometheus 라벨로 내면 값 종류가 끝없이 늘어나므로 지표가 아니라 DB 에서 계산한다. 금액은 설정 단가 기준 추정이고 캐시 할인을 빼지 않은 **상한**이다.
- **부하 테스트는 가짜 AI 로**: 실제 AI 로 100건을 돌리면 비용이 들어서, 호출 1번에 30초(±30%)를 기다리고 빈 판정을 주는 가짜 AI 모드를 만들었다(기본 꺼짐, 부하 테스트 compose 에는 AI 키를 넣지 않는다).
- **환불 정책(구현은 11-27)**: 지금 `POST /api/credits/purchases/{orderId}/refund` 는 크레딧만 빼고 토스 결제 취소를 부르지 않는 "모의 환불"이다. 실제 환불을 이렇게 만든다.
  - **전액만** 환불한다(부분 취소 없음, 토스 취소에 `cancelAmount` 를 보내지 않는다).
  - **결제 승인 시각(`paidAt`) + 168시간 전까지**만 환불한다(한국 날짜 기준보다 단순하고 시간대 문제가 없다).
  - **잔액이 구매한 크레딧 이상이면 환불**한다(지금 `refundPurchase` 의 검사 그대로). 크레딧은 잔액 하나로 합쳐져 결제 건별로 "그 결제분을 썼는지"는 알 수 없다. 알려면 결제별 남은 양이나 사용 연결 테이블과 차감 순서 규칙이 필요해 하지 않는다. "결제 뒤 한 번이라도 쓰면 불가"(원장 순서로 판단 가능) 안도 검토했지만 쓰지 않는다. 금액 계산은 어느 쪽이든 맞는다.
  - 토스 취소는 외부 호출이라 결제 승인(`confirm`)처럼 나눈다: 잠그고 확인·차감 후 `REFUNDING` → 토스 취소(멱등 키) → 성공이면 `REFUNDED`, 명확한 거절이면 크레딧을 되돌리고 `PAID`, 결과를 모르면 토스 조회로 확인. 결제 수단은 카드뿐이라 가상계좌 환불 계좌 입력은 필요 없다.
- **자가진단 화면은 휴대폰 폭 지원**: 과제·대시보드·복기·리포트·충전·마이페이지는 375px 에서도 가로로 밀리지 않게 한다. 응시 시작은 여전히 PC 를 전제로 한다(DESIGN.md 3.2·7 공통 셸에 반영).
