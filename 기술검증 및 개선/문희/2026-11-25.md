# 2026-11-25 응시 목록 API 성능 개선 (N+1 제거)

- 대상: `GET /api/attempts` (대시보드와 복기 화면이 처음에 부르는 API)
- 저장소: pAIr-back, 커밋 `8d03eac` (브랜치 `perf/attempt-list-batch`, 수정 전 기준 커밋 `8a4f4fa`)

## 증상

대시보드와 복기 화면의 조회가 오래 걸렸다. 두 화면 모두 이 목록을 받은 뒤에야 다음 요청을 시작한다.

| 수정 전 실제 사용 환경 (로컬 백엔드 → 원격 DB) | 값 | 수준 |
|---|---|---|
| 목록 API 평균 / 최대 (26회) | 2.37초 / 8.09초 | 로그 (`/actuator/prometheus` 누적. 호출마다 응시 수와 서버 상태가 다를 수 있다) |

## 원인

채점이 끝난 응시마다 리포트 전체를 다시 만들었다. 목록에 필요한 것은 총점과 항목 점수뿐인데, 응시마다 저장된 리포트 JSON(대화 기록 포함)과
채점 표(채점, 체크 결과, 기준표, 모델 호출, 판정, 근거)를 따로 읽었다. 그래서 **DB 문장 수가 응시 1건당 약 11개씩** 늘었다(측정).

슬로우 쿼리(느린 쿼리 하나)가 아니라 빠른 쿼리를 여러 번 보내는 N+1 문제로 판단했다. 원격 DB 에서는 문장마다 왕복 시간이 붙는다.
쿼리별 실행 계획(`EXPLAIN`)은 확인하지 않았다.

## 해결

- `AttemptStateRepository.readScores(ids)` 를 추가하고, 목록 API 는 채점이 끝난 응시의 점수를 반복문 **밖에서 한 번에** 읽는다.
- `ScoringReportRepository.scores(ids)`: 채점, 체크 결과, 체크 기준, 항목 기준을 `IN` 조건으로 **4번에** 읽는다.
- 채점 표에 기록이 없는 응시(옛 형식)만 저장된 JSON 을 `findAllById` 한 번으로 읽는다.
- 항목 점수 계산은 리포트 조회(`overlay`)와 같은 함수(`itemScore`, `byItem`)를 쓴다. 점수 규칙이 두 벌이 되지 않는다.
- API 응답 형식, DB 스키마, 프론트는 바꾸지 않았다. 인덱스와 캐시도 추가하지 않았다.

## before / after (측정)

| 완료 응시 수 | 응답 시간 before → after | 단축 | DB 문장 수 before → after |
|---|---|---|---|
| 10건 | 1,746ms → **258ms** | 85% (6.8배) | 133 → 25 |
| 30건 | 4,788ms → **262ms** | 95% (18배) | 360 → 25 |
| 60건 | 8,956ms → **255ms** | 97% (35배) | 695 → 21 |

수정 전에는 응시 수에 비례해 늘었고, 수정 후에는 10~60건에서 거의 일정하다.

시간의 최소~최대 (10회):

| 완료 응시 수 | before | after |
|---|---|---|
| 10건 | 1,644 ~ 1,828ms | 237 ~ 308ms |
| 30건 | 4,650 ~ 4,892ms | 226 ~ 298ms |
| 60건 | 8,875 ~ 9,630ms | 239 ~ 303ms |

### 측정 조건

- **공용 RDS 가 아니라 로컬 재현이다.** Docker `pgvector/pgvector:pg16` 앞에 방향마다 5ms 를 늦추는 프록시를 두었다(왕복 10ms 추가).
  이 PC 에서 팀 RDS 까지 TCP 연결 시간이 약 10ms 였던 것에 맞췄다.
- 수정 전후 jar 를 같은 DB, 같은 데이터, 같은 PC 에서 실행했다.
- 데이터: 회원마다 채점 완료 응시 10 / 30 / 60건. 응시 1건에 리포트 JSON(대화 16턴), 체크 결과 30개, 채점 호출 3번, 모델별 판정과 근거.
- 워밍업 3회 뒤 10회를 재서 중앙값을 썼다. DB 문장 수는 Postgres `log_statement=all` 로 1회 호출을 셌다
  (트랜잭션 시작·종료와 인증 조회 포함. 시간 측정 중에는 로그를 껐다).
- 가짜 데이터라 실제 응시의 리포트 크기와 다를 수 있다. **수정 후 실제 원격 DB 환경의 시간은 아직 재지 않았다.**

## 남은 것

- 풀이 중(`SOLVING`) 응시는 빈 응시인지 확인하느라 아직 응시마다 대화와 작업 기록을 읽는다. 이런 응시가 많으면 그만큼 느려진다.
- 복기의 트리 API 는 갈래마다 리포트를 만든다. `readScores` 로 점수를 읽는 방식을 적용할 수 있다(항목 이름과 배점은 추가로 필요).
- 대시보드는 목록 뒤에 최근 6개 리포트를 따로 부른다.
