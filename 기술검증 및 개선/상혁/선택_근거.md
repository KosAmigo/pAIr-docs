# 기술·모델 선택 근거 (팀원 4: 실전 시험 흐름)

> 근거 수준: **측정** = 직접 재 봄 / **로그** = 재현 로그로 확인 / **테스트** = 자동 테스트로 확인 / **논리** = 장단점으로 판단 / **추정** = 기록이 없어 코드·문서로 짐작
> 후보 여러 개를 같은 조건으로 돌려 비교한 실험은 이 영역에 없다. "논리" 항목은 선택 당시 문서와 코드 주석에 적힌 이유를 옮긴 것이다. 후보 비교 실험은 채점·RAG 영역에 있다 ([기술검증_보고서_정현.md](../../기획/기술검증_보고서_정현.md)).

## 1. 감독 구조

| 결정 | 선택 | 왜 | 수준 |
|---|---|---|---|
| 분석 위치 | 응시자 PC 브라우저 안 (영상은 서버로 안 보냄) | 영상 전송이 없어 트래픽·저장·개인정보 부담이 사라지고, 서버 GPU 가 필요 없다. 한 회차 300명 이상 동시 응시를 목표로 하면 서버가 영상 300명×3채널을 상시 분석하기 어렵다 | 논리 (데이터 절감률 99% 목표는 실제 회차에서 아직 측정 전) |
| 서버로 보내는 것 | 이상 순간의 이벤트 1건 + 사진 1장 | 감독관이 확인할 근거는 남기면서 영상 대비 데이터를 크게 줄임. 얼굴로 사람을 식별하지 않아 생체정보를 다루지 않음 | 논리 |
| 감독관 영상 | 감독관이 응시자를 열었을 때만 WebRTC P2P, 서버는 시그널링만 | 상시 300명×3채널 전송·저장을 피하고 영상이 서버를 지나지 않게 함 | 논리 |
| 분석을 도는 스레드 | 얼굴·포즈 분석을 **Web Worker** 에서 돌림. 메인 스레드의 모델은 Worker 가 안 될 때(생성·초기화 실패, 응답 없음 10초)의 **폴백**으로만 늦게 불러옴 (**구현됨, 프론트 브랜치 `feat/11-23jusang`, main 미merge**) | 간격 제한만으로는 느린 PC 에서 메인이 막힘. 코어 제한 측정에서 메인 방식은 막힘 76~87%·화면 9~15fps, Worker 방식은 1% 이하·111~119fps. 대가는 느린 코어에서 분석 속도 저하(초당 3.7~6.9회). 폴백은 Worker 미지원·CSP 에 대비 → [Worker 설계](Worker_분리_설계.md) | **측정** (조건당 1회, 정지 얼굴 입력, 실제 웹캠 아님) |
| 휴대폰 보조 캠 | 영상만 보내고 분석은 응시자 PC 가 함. **단, 11-21 에 스위치로 꺼 둠(현재 웹캠 + 화면 공유 필수, 휴대폰 보조 캠만 꺼짐)** → [사용 중단 정리](휴대폰_보조캠_사용중단.md). **재개 방향(예정, 설계만 2026-11-23): 영상 대신 JPEG 프레임 서버 중계, 분석은 PC Worker** | 휴대폰에서 모델을 돌리면 아이폰이 메모리·메인 스레드 부족으로 연결이 끊김. 중단 이유는 TURN·운영 릴레이 미비 등 | **로그** (11-21 재현 로그) |

## 2. 감독 모델

모두 `@mediapipe/tasks-vision` (브라우저 WASM/GPU) 로 응시자 PC 에서 실행한다. 설정은 `frontend/src/proctor/vision/models.ts`.

| 모델 | 무엇을 보나 | 왜 | 수준 |
|---|---|---|---|
| MediaPipe **Face Landmarker** (최대 3명) | 얼굴 점 478개, 얼굴 변환 행렬(고개 각도), 눈 블렌드셰이프(시선, 눈 감김) | 한 모델로 "얼굴 없음·여러 얼굴·고개 돌림·시선 이탈" 네 가지를 모두 계산할 수 있음. 사람을 알아보지 않고 있는지·어디를 보는지만 봄 | 논리 |
| MediaPipe **Pose Landmarker** (lite) | 어깨·몸통 위치 | 자리 이동·몸 돌림. 몸통은 천천히 움직여 가벼운 lite 로 충분하고 드물게 돌려도 됨 | 논리 |
| MediaPipe **Hand Landmarker** | 손 위치 | 휴대폰 영상에서 양손이 화면 밖으로 나가는지, 환경 점검에서 손목 확인 | 논리 |
| MediaPipe **Object Detector (EfficientDet-Lite0)** | 휴대폰·노트북·책 등 일반 물체 | 책상 위 스캔과 휴대폰 영상 감시. 가장 작은 모델이라 PC 에서 한 번만 불러와 재사용함 | 논리 |
| **OWL-ViT** (시도 후 제거) | 메모지·이어폰·스마트워치처럼 일반 물체 모델에 없는 것을 글로 지정해 찾기 | 점검 사진 몇 장에만 쓰려던 "정밀 분석". 코드 주석에 "무거운 모델"이라 적혀 있었고 11-20 에 의존성째 제거. **제거 사유(작성자 확인): 수치(탐지 기준값)를 조정해도 너무 빡세게 잡히거나 너무 허술해서 쓸 만한 균형점이 없었다.** 현재 정책은 "귀·손목 사진은 자동 분석하지 않고 감독관이 사진으로 확인" | 작성자 증언 (조정 전후 수치 기록은 없음) |
| 연산 장치(delegate) | GPU 우선, 실패하면 CPU, **아이폰은 CPU 고정** (메인 방식 기준. Worker 안의 기본값은 임시로 CPU 먼저, GPU/CPU 실측 뒤 확정) | 아이폰 사파리는 GPU 로 여러 번 돌리면 WebGL 메모리가 쌓여 탭이 죽음("이 페이지에 문제가 반복적으로 발생했습니다") | 로그 |

## 3. 경고 판정과 이벤트 전송

| 결정 | 선택 | 왜 | 수준 |
|---|---|---|---|
| 경고 판정 | 개인별 보정(시작 3초 자세를 기준으로) + 지속 시간 + 쿨다운 + 0.4초 안 끊김 이어 붙이기 | 고정 기준값은 카메라 각도가 사람마다 달라 오탐이 난다. 한 프레임 튀는 값은 무시 | 논리 (조건별 오탐률 실측은 아직) |
| 오탐 관리 | 기준값을 한 파일(`PC_THRESHOLDS`)에 모으고 `/proctor/lab` 에서 조건별 분당 오탐 수 집계 | 조정 전후를 같은 조건으로 비교하려고 | 테스트 (집계 테스트 3개) |
| 브라우저 이벤트 | 탭·창·마우스·전체 화면 이탈과 외부 붙여넣기를 상태 머신으로 하나로 묶음 | 한 번의 이탈에서 신호가 여러 개 나옴 | 테스트 |
| 이벤트 전송 | 브라우저 아웃박스, 네트워크 오류·5xx 만 재전송, 4xx 는 버림, `clientId` 로 중복 저장 방지 | 인터넷이 끊겨도 이벤트를 잃지 않고, 다시 보내도 결과가 같아야 함 | 테스트 |
| 환경 점검 실패 | 실패·경고여도 결과를 저장하고 입장 허용, 감독 기록에 남겨 감독관이 확인 (11-22) | AI 모델 판단은 틀릴 수 있는데 통과를 필수로 걸어 두면 환경이 맞는 응시자가 막힘. 기준값 조정으로는 해결되지 않았음(11-18·11-20). 입장은 열고 콘솔 점검 카드·안내 메시지로 대응 | 논리 (사람이 확인하는 흐름은 실제 동시 사용 미확인) |
| 점검 상태·안내 | 점검 진행 3초마다 서버 저장(대상자당 1건 덮어쓰기), 안내 메시지는 일방향·최대 500자·읽음 표시 | 막힌 응시자를 감독관이 볼 수 있고 말할 수 있어야 함. 답장·정해진 문구는 범위 밖으로 둠 | 테스트 (`EnvNoticeIntegrationTest`) |
| 사진 보관 | 회차 종료 7일 뒤 삭제 (11-23 확정, 서버 설정값은 코드 기본값·`application.yml` 모두 30 → 7 변경 필요). **예정: 삭제 2일 전부터 감독관·매니저가 7일씩 최대 2번 연장, 이력 기록** | 동의 문구와 같게. 7일이면 충분하다고 봤지만 완료된 회차에서 늦게 검토하는 경우가 있어 한정된 연장을 허용(무제한은 개인정보 부담이라 하지 않음) | 논리 |
| 증거 구간 (예정) | 이벤트 앞 8초·뒤 4초 사진(웹캠+휴대폰, 최대 24장)을 응시자 PC 가 로컬 버퍼에 두었다가 이벤트 때만 업로드, 감독관·매니저가 완료된 회차에서도 확정/기각 | 사진 1장은 맥락이 부족하고 연속 녹화는 개인정보·저장 부담이 큼. 모델은 선별만, 판단은 사람 | 논리 (구현·측정 전) |
| 환경 점검 성능 자가 측정 | 점검에서 분석 1회 시간·초당 횟수·메인 막힘을 재서 pass/warn, 느리면 분석 간격 100→200→300ms, **입장은 막지 않음** (**구현됨**, 같은 브랜치) | 느린 PC 를 입장 전에 알리되 기존 정책(점검 실패여도 입장)과 같게. 임계값(p95 130ms·250ms, 초당 4회)은 잠정 | 측정 (코어 제한 5조건, 실기기 아님) |
| 감독관 알림 | 새 이벤트 알림음(Web Audio, 음원 파일 없음) + 새 이벤트만 모음 | 다른 화면을 보고 있어도 새 이벤트를 놓치지 않게 | 로그(실기기에서 사람이 확인) |
| 책상 위 감지 | 경고만 하고 통과, 사진과 물체 목록을 감독관에게 전달 | 응시자 본인의 손·팔이 사람으로 잡히는 등 오탐이 있어, 모델이 응시를 막으면 부당함 | 논리 |
| 연결 끊김 | 프론트 15초 + 서버 5분의 두 층 | 15초는 순간 끊김을 넘기고 화면을 바로 막는 용도, 5분은 브라우저를 닫았다 다시 여는 경우까지 이어 푸는 서버 기준 | 논리 |

## 4. 시험 진행 백엔드

| 결정 | 선택 | 왜 | 수준 |
|---|---|---|---|
| 시각 기준 | 서버 `Clock` 한 곳 | 응시자 PC 시계가 틀려도 모두 같은 순간에 시작·종료 | 테스트 (자동 제출 지연 테스트 0.8초) |
| 중복 시작 방지 | 대상자 행 잠금 (`SELECT … FOR UPDATE`) | 시작을 두 번 눌러도 응시는 하나. 별도 분산 잠금이 필요 없음 | 테스트 |
| 자동 제출 | Spring `@Scheduled` 2초 주기 (서버가 여러 대면 ShedLock 예정) | 종료 시각 5초 이내 처리 목표 | 테스트 |
| 초대 토큰 | `SecureRandom` 32바이트, DB 에는 SHA-256 해시만 | DB 가 새도 링크를 만들 수 없음. 재발송하면 새 토큰으로 이전 링크 무효 | 논리 |
| 초대 메일 | 커밋 뒤 이벤트(`AFTER_COMMIT`) + `@Async` | 메일 서버가 느리거나 죽어도 회차 저장은 성공, 롤백되면 메일도 안 나감 | 논리 |
| 사진 저장 | S3(비공개, SSE-S3) / 로컬 폴더를 설정으로 선택 (Strategy) | 개발은 로컬, 운영은 S3 | 테스트 |
| 사진 업로드 | 트랜잭션 밖에서 업로드하는 3단계 | DB 연결을 오래 쥐지 않으려고 | 테스트 |
| DB 변경 | Flyway 마이그레이션 | 서버가 켜질 때 순서대로 자동 적용 | 테스트 (H2). 실제 PostgreSQL 에 V1~V19 순서 적용은 아직 확인 전 |
