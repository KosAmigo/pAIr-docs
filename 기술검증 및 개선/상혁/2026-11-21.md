## 문제와 해결

### 1. 카메라 감독 중 시험 화면 입력이 끊김 (부하 감축)

- **증상**: 웹캠 감독이 도는 동안 코드 편집기·채팅 입력이 버벅였다.
- **원인**: 얼굴(약 32ms)·포즈(약 21ms) 모델이 브라우저 **메인 스레드에서 동기로** 돌았다. 영상 프레임마다(약 30회/초) 둘을 연달아 돌려 한 작업이 50ms 를 넘겼고, 그동안 입력이 막혔다.
- **해결** (`a81b0cf`)
  1. 분석 간격을 최소 100ms(초당 최대 10회)로 제한. 감독 규칙의 가장 짧은 지속 시간이 1초라 초당 10회면 충분하다. 분석이 느린 PC 는 걸린 시간의 두 배를 쉬어 점유율을 절반 이하로 묶는다.
  2. 한 번에 모델 하나만 실행(얼굴 3번에 포즈 1번). 안 돌린 쪽은 직전 결과를 쓴다. 몸통은 천천히 움직여 포즈는 드물어도 된다.
  3. 화면 갱신 간격 200ms → 500ms.
- **확인 (측정)**: 이 PC(GPU), 8초 기준

  | | 이전 | 현재 |
  |---|---|---|
  | 메인 스레드 점유 | 80% | 29% |
  | 지연 상위 5% | 51ms | 27ms |
  | 50ms 넘는 긴 작업 | 15건 | 0건 |

  측정은 얼굴 사진 한 장을 영상처럼 반복해 넣은 것이라 실제 앱과 다를 수 있다. 간격 계산은 `frameBudget` 테스트로 확인했다.
- **남은 일**: 이것으로도 부족하면 모델을 Web Worker 로 옮긴다(제안 단계).

### 2. 휴대폰 보조 캠이 시험 중 됐다 안 됐다 함

- **증상**: 감시 시작 10초쯤 뒤 페이지가 갑자기 닫히거나(code 1006) 연결이 끊겼다.
- **원인 (로그 확인)**: 11-21 재현 로그에서 아이폰 CPU 추론이 메인 스레드를 8~20초 잡아 상태 신호가 밀렸다. WebSocket 은 멀쩡한데(재연결 0회) 무신호 기준 6초를 넘겨 "응답 없음"이 8초 주기로 반복됐다. 처음 의심한 후보는 릴레이 판정, WebSocket 재연결, 개발 터널 불안정이었다.
- **해결** (`7f584b3`)
  - 휴대폰에서 모델과 추론을 없애고 영상만 보낸다. PC 가 받은 영상을 WebRTC 로 분석한다. 휴대폰 부하가 사라진다.
  - 무신호(stale) 기준을 6초 → 15초로 늘렸다. 실제 화면 꺼짐·앱 전환은 `phone_hidden` 이벤트가 즉시 알린다.
  - 아이폰은 GPU 로 여러 번 돌리면 WebGL 메모리가 쌓여 탭이 죽으므로 CPU 로 고정(`models.ts`).
  - 책상 스캔용 고화질 영상은 스캔하는 동안만 보낸다(최대 3.5Mbps), 평소는 1.2Mbps·15fps.
- **확인**: 위 로그와 `phoneStale`·`peerLink` 테스트. **실제 아이폰으로 시험 내내 유지되는지는 아직 사람이 확인하지 못했다**(체크리스트 A3·A4).

### 3. 사진 업로드가 DB 연결을 오래 쥠, 재전송하면 이벤트 중복

- **증상(우려)**: 이벤트 저장과 S3 업로드가 한 트랜잭션이라 시험 중 이벤트가 몰리면 작은 서버·연결 수가 적은 DB 에서 연결이 고갈될 수 있었다. 업로드가 실패해 브라우저가 다시 보내면 이벤트가 두 건이 될 수 있었다.
- **해결** (back `f6578e6`, front `37e454b`)
  1. 짧은 트랜잭션에서 검증하고 이벤트를 저장해 바로 커밋 → 2. 트랜잭션 밖에서 사진을 S3 에 업로드(키는 `회차/이벤트 번호`) → 3. 이벤트에 사진 위치만 UPDATE(담당자가 그사이 저장한 판정을 덮지 않도록 다른 컬럼은 건드리지 않음).
  4. 브라우저가 이벤트마다 만든 `clientId`(UUID)로 재전송을 알아보고 사진만 다시 연결한다(V16 마이그레이션).
  5. PC 시계 오차는 5분까지 시험 시간 안쪽으로 맞춰 저장하고, 종료 뒤 30분까지 늦게 도착한 이벤트를 받는다. 대상자당 사진 300장 상한.
- **트레이드오프**: 11-19 에 정한 "업로드가 실패하면 이벤트도 롤백"을 "이벤트는 남기고 사진은 다시 올리게 한다"로 바꿨다.

### 4. 새로고침하면 대기실에서 멈춤

- **증상**: 이미 시작한 응시자가 새로고침하거나 링크로 다시 들어오면 "웹캠이 연결되면 시험을 시작합니다"에서 영영 멈췄다.
- **원인**: 웹캠은 환경 점검과 응시 화면에서만 열렸고, 새로고침 뒤 곧바로 가는 대기실에는 여는 코드가 없었다.
- **해결**: 대기실에서도 웹캠을 다시 열고, 실패하면 오류와 "웹캠 다시 연결" 버튼을 보여 준다. (`a81b0cf`)
- **남은 일**: 연결 신호(heartbeat)는 시험 화면에서만 보내므로, 대기실에서 멈춰 있으면 90초 뒤 `CONNECTION_LOST`, 5분 뒤 링크 만료가 남을 수 있다(대기실에서도 신호를 보내는 개선은 제안 단계).

### 5. 시작 요청이 StrictMode 에서 버려져 "시험을 시작하는 중입니다"에서 멈춤

- **원인**: 개발 모드(StrictMode)가 대기실 효과를 두 번 돌리는데, 첫 요청의 결과가 버려지고 두 번째 실행은 "이미 시작함"으로 건너뛰었다.
- **해결**: 효과가 정리될 때 시작 표시와 재시도 타이머를 풀어 다시 시도하게 했다. 서버는 두 번 불러도 응시를 하나만 만든다(대상자 행 잠금). (`a81b0cf`)

### 6. 입장 마감을 넣었다가 되돌림

- 감독관이 책상 사진을 확인할 시간을 위해 "시작 10분 전까지 입장" 마감을 넣었다가(`d7a8fb1`) 되돌리고(`3241cb4`) 완전히 없앴다(`1cd4f98`, 백엔드 `7d7ae6d`·`03dabf3`). 지금은 시작 전이면 언제든, 시작 시각이 지나도 종료 전이면 입장해 시작할 수 있다(늦게 들어와도 종료 시각은 그대로). 통합 테스트 `lateEntryAfterStartIsAllowed`.

### 7. 콘솔 회차 목록

- 진행 중 회차 수가 늘면 "진행 중" 탭으로 자동 이동한다. 예정·종료 탭을 눌러 둔 채 카드 숫자만 오르던 문제. (`a81b0cf`)

### 8. 방 360도 스캔 제거

- 각도 전환이 애매하고 방향 센서·권한이 필요해 뺐다. 책상 위 스캔만 남겼고, 책상 위에서 휴대폰·책·화면이 감지돼도 경고만 하고 통과시킨다(감독관이 사진으로 판단). (`7f584b3`)
