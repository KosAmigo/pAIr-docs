# 2026-11-24 화면 공유 이벤트 서버 저장, 점검 미통과 입장자 탭, 감독관 실시간 보기 운영 릴레이

> 의도 문서: [docs/intent/남은-코드-3건-마무리.md](../../docs/intent/남은-코드-3건-마무리.md)
> 커밋: 확정 전 (pAIr-back 브랜치 `feat/console-env-screen-events`, pAIr-front `feat/1124jusang`)

## 한 일

- **API §7 최적안 3종은 이미 코드에 있었다.** 문서가 "구현 필요"로 적어 둔 항목(채널별 12장·1초 간격·본문 2MB, 종료된 회차만 보관 연장, PC → 휴대폰 `quality` 중계)을 코드로 확인하니 `EvidenceClipService`·`SnapshotRetentionService`·`ProctorRelayService` 에 이미 들어가 있었다. 새로 만든 것은 없고 문서의 "구현 필요" 표시만 고쳤다.
- **화면 공유 이벤트를 서버에 저장한다.** `source=SCREEN`, 유형 `SCREEN_STOPPED`(중단) · `SCREEN_PARTIAL`(창·탭만 공유) · `SCREEN_RESTARTED`(끊겼다 다시 시작). 종류와 시각만 저장하고 **사진은 받지 않는다**(결정). 콘솔 이벤트 목록에 다른 이벤트와 함께 보인다.
- **회차 화면에 "점검 미통과" 탭을 추가했다.** 점검에서 실패한 항목이 있는데도 입장한 응시자를 모아 응시자·실패 항목(사유)·입장 시각·안내 보냄 여부를 보여 준다. 진행 중인 회차에서는 행을 누르면 실시간 현황의 감독 기록 서랍으로 가고, 그 밖의 단계에서는 아래에 점검 결과와 안내 보내기를 연다.

## 문제와 해결

### 1. 문서와 코드가 어긋났다

- **증상**: 11-23 문서(API §7)는 채널별 12장 검사·본문 2MB·연장 대상 제한·`quality` 중계가 "아직 없다"고 적었지만 코드에는 모두 있었다.
- **원인**: 11-23 오후에 "최적안으로 정함"과 구현을 같은 날 진행했고, 문서의 "구현 필요" 표시를 구현 뒤에 지우지 않았다.
- **해결**: 코드를 읽어 네 항목을 확인한 뒤 문서를 구현 상태로 고쳤다. 앞으로 문서에 "구현 필요"를 적으면 구현과 같은 변경에서 지운다.

### 2. 기존 `source` 검사가 새 출처를 카메라로 취급할 뻔했다

- **증상(우려)**: 코드 곳곳에 `source != BROWSER` 를 "카메라 이벤트"로 읽는 곳이 있었다(서버 `ProctorEventResponse`·콘솔 `isCameraEvent`). `SCREEN` 을 추가하면 화면 공유 이벤트가 "사진 업로드 실패"로 표시되거나 증거 구간을 받을 수 있었다.
- **해결**: 서버 `Source.isCamera()` 한 곳으로 모아 사진 허용·증거 구간·"사진 없음" 사유 표시가 같은 규칙을 쓰게 했고, 콘솔 `isCameraEvent` 도 `PC_CAM`·`PHONE_CAM` 만 카메라로 본다.

## 확인

- 백엔드: `./gradlew build`(테스트 + 패키지 구조 검사) 통과. 새 테스트 — 점검 미통과 입장자(실패 항목만·입장한 사람만·안내 보냄 표시·모양이 다른 JSON), 화면 공유 이벤트(세 유형 저장·사진 거절·증거 구간 거절).
- 프론트: `tsc -b`, `npm run test:proctor`(301개 통과), Playwright `e2e/env-failures.spec.ts`.
- **실제 카메라·화면 공유로는 확인하지 않았다.** 마이그레이션 V25(제약 이름 `proctor_event_types_source_check`)는 테스트(H2)에서는 못 돌렸지만, 같은 날 개발 서버를 켜자 개발 DB(AWS RDS PostgreSQL)에 `Successfully applied 1 migration … now at version v25` 로 정상 적용됐다(제약 이름 가정이 맞았다).

## 열린 문제

- 점검 미통과 탭은 동의와 함께 **저장된** 결과만 본다(입장 전 점검 중 진행 상태는 보지 않는다).
- 운영용 휴대폰 릴레이 확장과 감독관 영상 시그널링은 이번 범위에서 뺐다.

## 추가 (같은 날 오후): 감독관 실시간 보기를 운영 서버에 구현

> 의도 문서: [docs/intent/감독관-실시간-보기-운영-시그널링.md](../../docs/intent/감독관-실시간-보기-운영-시그널링.md) · API: [§6-11](../../API/실전시험_감독_API.md)

### 한 일

- 개발용 Vite 릴레이에만 있던 감독관 영상 시그널링(`watch`·`unwatch`·`view-rtc`, 서버 → 응시자 PC `viewer-request`·`viewer-gone`)을 운영 Spring WebSocket(`/ws/proctor`)에 구현했다. 서버는 쪽지(시그널링)만 전달하고 영상은 응시자 PC → 감독관 브라우저로 직접 간다.
- 서버 1대·TURN 없음 기준. 감독관은 응시자를 한 명씩 열고, 응시자 1명당 동시에 2명까지 본다.
- 직접 연결이 안 되면 콘솔 채널 상태 문구가 "영상 연결 안 됨 (네트워크 때문에 직접 연결하지 못했습니다)"로 보인다.

### 문제와 해결

#### 1. 브라우저 WebSocket 은 연결할 때 로그인 헤더를 못 붙인다

- **문제**: 운영 서버는 REST 처럼 헤더로 로그인 확인을 하는데 WebSocket 은 처음 연결에 `Authorization` 을 못 싣는다. 개발 릴레이는 이 때문에 백엔드 REST 를 대신 불러 확인하는 임시 방식을 썼다.
- **해결**: 프론트가 이미 `watch` 메시지에 로그인 헤더를 싣고 있어서, 서버가 그 값을 REST 와 같은 규칙으로 확인한다(`WebSocketUserResolver`: bearer 는 액세스 토큰 검증, 개발용 header 모드는 `X-Pair-*`). 권한은 콘솔 API 와 같은 `ConsoleAccessService` 를 쓴다.

#### 2. sdp 가 기본 텍스트 한도보다 크다

- **문제**: 기존 중계는 텍스트 메시지를 4,096바이트로 제한하고 컨테이너 버퍼도 8KB 라서, sdp(최대 32,000자)를 실은 `view-rtc` 가 조용히 버려질 뻔했다.
- **해결**: hello 를 보낸 PC 연결과 감독관 연결에만 40,000바이트까지 허용하고 컨테이너 텍스트 버퍼도 키웠다. 그 밖의 연결(휴대폰 등)은 그대로 4,096바이트다.

#### 3. 신호가 다른 응시자에게 새면 안 된다

- **해결**: 감독관 연결은 연 응시자 한 명에 고정되고, 응시자 PC 가 보낸 신호는 그 짝을 보는 감독관(`viewer` 번호)에게만 간다. 방향마다 보낼 수 있는 종류를 제한하고(감독관은 offer 불가, PC 는 answer 불가) 알려진 필드만 새로 만들어 넘긴다.

#### 4. 전체 테스트가 `Java heap space` 로 실패했다

- **증상**: 새 통합 테스트 클래스(`ViewerAccessIntegrationTest`)를 따로 만들었더니 `./gradlew build` 의 테스트 JVM 이 힙 부족으로 죽었다. 해당 테스트들은 따로 돌리면 통과했다.
- **원인**: 통합 테스트마다 설정이 다르면 Spring 컨텍스트(+H2)가 따로 캐시되고, 한 JVM 에 쌓인 컨텍스트가 이미 한계(약 33개)에 가까웠다. 컨텍스트 하나를 더한 것이 한계를 넘겼다.
- **해결**: 같은 설정을 쓰는 `EnvNoticeIntegrationTest` 로 권한 테스트를 옮겨 컨텍스트를 늘리지 않았다. 앞으로 통합 테스트를 새 클래스로 만들 때는 기존 클래스와 설정(`@MockitoBean`·`@TestPropertySource`)을 맞춰 컨텍스트를 재사용할지 먼저 본다. 근본 해결(테스트 JVM 힙 상향이나 컨텍스트 정리)은 하지 않았다.

### 확인

- 백엔드 새 테스트 18개 추가 후 통과: `ViewSignalServiceTest`(형식·방향·크기, 6개), `EnvNoticeIntegrationTest` 의 영상 열기 권한 테스트(로그인·회사·회차 상태·입장 여부, 5개), `ProctorRelayIntegrationTest`(7개 추가, 실제 WebSocket: 열기→요청→신호 전달→닫기, 권한 없음, 정원 초과, PC 재접속, 잘못된 방향·모르는 viewer, 연습 짝).
- **개발 PC 두 대로 연결 확인(2026-11-24 오후, 사용자 확인)**: 응시자 PC(웹캠·화면 공유)와 감독관 PC 에서 감독관 영상이 연결됐고, 백엔드 로그에 열기(감독관 12·회차 35·응시자 34)와 닫기(11초)가 한 번씩 남았다. 개발 서버를 `PAIR_RELAY=backend`(Spring 릴레이)로 띄워 확인했다. **정원 초과·PC 재접속·권한 거절(체크리스트 H2~H9)과 다른 네트워크 환경은 아직 확인하지 않았다.**

### 열린 문제

- 서버가 여러 대가 되면 짝·시청 정보를 공유할 수 없다(Redis 등 필요). TURN 이 없어 일부 네트워크에서는 영상이 안 나올 수 있고 실제 비율은 모른다.
- 열람 기록은 서버 로그에만 남는다. 감사용으로 DB 에 남길지는 정하지 않았다.
- 시그널링 상한(초당 60개, 텍스트 40,000바이트, `watch` 500ms 간격)은 임시값이다.
