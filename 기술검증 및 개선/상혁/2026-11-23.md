# 2026-11-23 감독 이벤트 알림음, 화면 공유 재활성화, 인증 메일 템플릿 통일

> 커밋: pAIr-front `03053d3` / pAIr-back `53e4bd5`

## 한 일

- 감독관 콘솔에 새 감독 이벤트가 들어오면 알림음을 내고, 확인할 때까지 새 이벤트를 모아 보여 준다.
- 감독관 영상 보기에서 영상을 눌러 크게 볼 수 있게 했다.
- 화면 공유 스위치(`SCREEN_SHARE_ENABLED`)를 다시 켰다.
- 회원가입 이메일 인증 메일을 시험 초대 메일과 같은 서식으로 맞췄다.

## 문제와 해결

### 1. 감독관이 새 이벤트를 놓침 → 알림음과 새 이벤트 모음

- **증상(우려)**: 콘솔이 폴링으로 이벤트 목록만 갱신하므로, 다른 화면을 보고 있으면 새 이벤트가 떠도 모른다.
- **해결** (`03053d3`)
  - `useNewEvents`: 처음 불러온 목록은 **기준선**으로만 쓰고 알리지 않는다. 그 뒤 새로 생긴 이벤트만 감독관이 확인(dismiss)할 때까지 모은다. 응시자(회차·대상자)가 바뀌면 기준선을 새로 잡아 다른 사람의 이벤트가 섞이지 않는다.
  - `alertSound`: 음원 파일 없이 Web Audio 로 짧은 두 음(880Hz, 660Hz)을 낸다. 딸깍 소리가 나지 않게 짧게 올렸다 내리고, 음량은 0.12 로 작게 했다.
  - 소리 켜기·끄기는 브라우저에 저장한다(`localStorage`, 기본 켜짐). 저장소를 못 쓰면 그 화면에서만 동작한다.
  - 브라우저는 사용자가 페이지를 한 번 만지기 전에는 소리를 막는다. 막혀 있으면 조용히 건너뛴다(콘솔을 쓰는 중이면 대개 풀려 있다).
- **확인**: 실기기에서 사람이 직접 확인했다. 자동 테스트는 이 변경에 추가하지 않았다.

### 2. 감독관 영상 확대 보기

- 영상 칸에 마우스를 올리면 확대 버튼이 나오고, 누르면 전체 화면 팝업으로 키운다. 같은 `MediaStream` 을 한 번 더 붙일 뿐이라 연결을 새로 만들지 않는다. Esc·바깥 클릭·닫기 버튼으로 닫고, 열릴 때 포커스가 닫기 버튼으로 간다.
- 휴대폰 보조 캠이 꺼져 있는 동안은(`PHONE_CAM_ENABLED=false`) 휴대폰 칸을 숨기고 2칸 배치로 바꿨다.

### 3. 화면 공유 스위치 재활성화 (정책 변경)

- 11-21 16:29 에 `SCREEN_SHARE_ENABLED` 를 `false` 로 꺼서 "웹캠만 필수"로 갔는데, 11-23 에 `true` 로 되돌렸다.
- 그 결과: 입장·시험 중 연결 조건에 화면 공유가 다시 포함되고, 감독관 영상 보기에는 웹캠과 화면 공유 두 칸이 보인다. 휴대폰 보조 캠은 계속 꺼져 있다.
- **문서 정리**: 현재 값은 `PHONE_CAM_ENABLED=false`, `SCREEN_SHARE_ENABLED=true`(웹캠 + 화면 공유)이다. [휴대폰_보조캠_사용중단.md](휴대폰_보조캠_사용중단.md), 11-21 문서, 기획 결정사항·기술명세·정리·역할 분담, 감독 API 문서, 선택 근거에 이 정책을 반영했다.
- **켠 이유**: 웹캠만으로는 부정행위를 탐지하는 범위가 좁아 화면 공유가 있어야 한다고 판단했다. 11-21 에 "웹캠만 필수"로 간 것은 휴대폰 보조 캠 문제 때문이었고, 화면 공유는 그때 함께 꺼졌던 것이다.

### 4. 인증 메일과 초대 메일의 서식 불일치

- **증상**: 회원가입 인증 코드 메일은 글자뿐인 `SimpleMailMessage` 였고, 시험 초대 메일은 로고 머리띠·표가 있는 HTML 이라 같은 서비스에서 온 메일로 안 보였다.
- **해결** (back `53e4bd5`)
  - `MailLayout` 을 공개로 열고 로고(`LOGO`)와 `html(...)` 에 **맨 아래 문구(footer) 인자**를 추가했다. 기본 문구는 시험 안내용이라, 인증 메일은 "회원가입 인증을 위해 자동으로 발송"으로 바꿔 넣는다.
  - 인증 메일을 HTML + 글자 본문 둘 다 담은 `MimeMessage` 로 보낸다(글자 본문에도 코드가 있어 HTML 을 못 보는 메일 앱에서도 코드를 읽을 수 있다). 인증 코드와 유효 시간을 표로 보여 주고, "본인이 요청하지 않았다면 무시" 안내를 넣었다.
- **확인**: `verificationMailUsesInviteLayout` 테스트(로고 인라인 참조, 제목, 코드, 유효 시간, 푸터 문구). 기존 인증 테스트는 메일 캡처 방식을 `MimeMessage` 로 맞췄다. 실기기 확인도 마쳤다.

## 추가 (같은 날 오후): 카메라 분석 Worker 분리, 성능 자가 측정, 휴대폰 JPEG 실측, 새 방향 확정

> 코드: pAIr-front `main` 에 merge 됨(원래 브랜치 `feat/11-23jusang`, 실제 카메라 검증 전). 설계·측정 전체는 [Worker_분리_설계.md](Worker_분리_설계.md).

### 5. 응시 화면 끊김 → 카메라 분석을 Web Worker 로 분리 (1·2단계 구현)

- **증상(우려)**: 얼굴·포즈 분석이 메인 스레드에서 동기로 돌아, 느린 PC 에서 입력이 끊기고 모델을 올리는 동안 화면이 멈춘다.
- **원인**: 하네스 측정(`측정`): 메인 방식은 메인 스레드 막힘 55%·화면 69fps, Worker 방식은 0%·120fps (DevTools 스로틀은 Worker 에 안 걸리므로 믿을 수 있는 것은 "메인이 안 막힌다"뿐).
- **해결**: `VisionBackend` 인터페이스에 Worker/메인 두 구현을 두고(Worker 실패 시 자동 메인 폴백), 1단계 감독 루프와 2단계 환경 점검을 Worker 로 옮겼다. Vite 모듈 Worker 에서는 기본 wasm 로더가 실패해(`ModuleFactory not set.`) 모듈용 로더를 직접 지정하고, 모델이 둘 이상이면 로더 주소에 `?instance=` 를 붙인다 (Worker 설계 10장).
- **확인**: 단위 테스트·빌드 통과(`테스트`). 저사양 흉내(코어 제한) 측정에서 1코어 약 2.5배 느림 기준 메인 방식 막힘 87%·9fps, Worker 1%·116fps. 대신 Worker 도 분석이 초당 3.7회·p95 265ms 로 느려진다 (12장, 조건당 1회·정지 얼굴 이미지 입력, `측정`). **실제 웹캠·Firefox·Safari·운영 번들(CSP)은 미확인.**

### 6. 느린 PC 를 입장 전에 알기 → 환경 점검 "이 PC의 분석 속도"

- 점검에서 분석을 약 4초 돌려 1회 시간·초당 횟수·메인 막힘을 재고, 느리면 분석 간격을 100→200→300ms 로 늘리고 결과에 사유를 남긴다. **입장은 막지 않는다**(pass/warn). `envCheck` JSON 의 항목 하나라 서버 계약 변경이 없다. 임계값(p95 130ms·250ms, 초당 4회)은 잠정이며 실제 저사양 PC 로 확정해야 한다 (11장).

### 7. 휴대폰 보조 캠을 다시 켠다면 → JPEG 프레임 크기 실측 (갤럭시·아이폰 각 1대)

- 480×360·화질 0.5 기준 JPEG 갤럭시 13.4KB, 아이폰 22.0KB(1.6~1.8배), 만드는 시간 8~20ms. 변화 감지(평균 변화량 0.04)로 정지 구간 20~30% 만 전송 (13·13-1장, `측정`/시뮬레이션). 작은 물체 변화는 평균 변화량으로 놓칠 수 있어 영역별 변화량이 필요하다(미측정).

### 8. 새 방향 확정과 같은 날 구현 (백엔드 `develop`·프론트 `main`, 실기기 확인 전)

- 휴대폰 보조 캠을 **영상 대신 JPEG 프레임 서버 중계**로 다시 켜고(PC Worker 가 분석, 웹캠·휴대폰 Worker 둘로 분리), 이벤트 **앞 8초·뒤 4초 사진**을 파일 저장소에 저장해 감독관·매니저가 **완료된 회차에서도 확정/기각**한다. 사진은 회차 종료 7일 뒤 삭제하되 삭제 2일 전부터 **7일씩 최대 2번 연장**(이력 기록)한다. 연속 녹화·서버 추론·새 알림 시스템은 하지 않는다. 근거: [docs/intent/실전시험-감독.md](../../docs/intent/실전시험-감독.md), API: [API §7](../../API/실전시험_감독_API.md).
- 구현 전 확인(백엔드 코드): 콘솔의 이벤트 조회·판정·사진 API 는 회차 종료 여부를 보지 않아 완료된 회차에서도 동작한다. 서버 `snapshot-retention-days` 는 **코드 기본값도 `application.yml` 도 30** 이었다(구현하면서 7 로 바꿈).
- **구현 결과(같은 날):** 백엔드 — 보관 7일 설정, 보관 연장 API·이력(V23), 증거 구간 업로드·조회(V24, `/clip`), 운영 WebSocket 프레임 중계 `/ws/proctor`(서버 상한은 임시값), 삭제 배치가 연장 반영. 프론트 — 휴대폰 캠 재개(`PHONE_CAM_ENABLED=true`), JPEG 프레임 송신·휴대폰 분석 Worker, 링 버퍼·변화 감지·화질 조절·구간 업로드(이벤트 후 약 5초), 동의 문구 v2, 콘솔 증거 구간 타임라인·삭제 예정 표시·연장 버튼, 환경 점검에 휴대폰 분석 비용 포함. 확인은 자동 테스트와 Playwright 까지이고 **실제 휴대폰·카메라로는 아직 안 했다.**

## 이 날 기준 열린 문제

- 11-21 에 정리한 열린 문제(운영용 릴레이·시그널링)는 그대로다. 운영용 릴레이는 오후에 구현했다(서버 상한은 임시값). 사진 보관 기간은 7일로 확정하고 서버 설정값도 바꿨다.
- Worker 분리·성능 자가 측정은 프론트 `main` 에 들어갔다. 실제 카메라·저사양 PC 확인이 남아 있다.
- 증거 구간·휴대폰 프레임 중계·보관 연장은 구현했으나 실기기 확인 전이다. 서버 상한 값 실측이 남아 있다. `quality` 신호 전달·24장(채널별 12장, 1초 간격)·요청 크기 상한·연장 대상(종료된 회차만)은 최적안으로 정했고 코드 반영이 필요하다([API §7](../../API/실전시험_감독_API.md)).
