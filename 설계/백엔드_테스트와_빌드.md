# 백엔드 테스트와 빌드

## 언제 무엇을 돌리나

| 할 때 | 명령 (IntelliJ 실행 목록) | 도는 테스트 | 시간 |
| --- | --- | --- | --- |
| 작업 중·머지 전 | `./gradlew build` (빠른 빌드) | 빠른 테스트만 | 약 1분 |
| 전체 확인 | `./gradlew fullTest` (전체 테스트) | 전체 | 약 5분 |
| 테스트 하나 | 테스트 옆 ▶ | 고른 것만(slow도 돎) | 몇 초 |
| push | GitHub Actions (자동, 모든 브랜치) | 전체 | 약 4분 |

## 머지 순서

1. 내 브랜치 push → CI ✓ 확인: `gh run list --branch 브랜치`
2. `git switch develop && git pull && git merge --no-ff 브랜치 && ./gradlew build && git push`
3. develop CI가 ✗면 머지한 사람이 바로 고친다.

## 테스트 작성 규칙

- 스프링 통합 테스트는 `ExamIntegrationTest`(개발용 헤더 로그인) 또는 `BearerIntegrationTest`(토큰 로그인)를 상속한다.
- 상속한 테스트에 `@MockitoBean`, `@DynamicPropertySource`, `@TestPropertySource`, `properties=`, `@ActiveProfiles`를 넣지 않는다. 하나라도 다르면 스프링이 새로 떠서 느려진다. mock 동작은 `@BeforeEach`에서 `when(...)`.
- 테스트끼리 DB(H2)를 같이 쓴다. 다른 테스트가 남긴 데이터에 기대지 않는다.
- 느린 테스트는 `@Tag("slow")`: 스프링 테스트(베이스에 이미 있음), 실제 코드 실행, 10초 넘는 것. 스프링 테스트에 빠지면 `ArchitectureTest`가 빌드를 막는다.

## 건드리지 않는 설정

- `src/test/resources/spring.properties`의 컨텍스트 캐시 64 (줄이면 공유 DB 테이블이 지워져 테스트가 깨진다)
- `build.gradle` 테스트 메모리 2GB, 병렬 3개, `gradle.properties` 빌드 캐시
