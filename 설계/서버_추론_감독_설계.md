## 0. 한눈에 보기

- 응시자 PC는 **사진만 보낸다.** 웹캠은 PC가, 휴대폰은 휴대폰 페이지가 JPEG를 **백엔드(Spring)** 로 보내고, 백엔드가 **추론 서버(RunPod GPU)** 로 넘긴다. 분석은 추론 서버에서만 한다. PC 폴백은 없다.
- **웹캠·휴대폰 사진은 응시 중 각각 초당 1장씩 백엔드가 파일 서버(S3)에 10초 묶음으로 상시 저장한다**(결정, 2026-11-25). 추론 서버가 죽어도 저장은 계속된다. 상시 저장분은 **시험 종료 후 3일** 보관한다.
- 이상 판정은 **추론 서버가 낸 "이벤트 후보"**(종류·시각·신뢰도·지속시간)를 백엔드가 받아 기존 `proctor_events`에 저장한다. **사진은 이벤트에 붙여 보내지 않는다.** 이벤트 시각으로 파일 서버의 상시 저장분에서 앞 8초·뒤 4초를 **끌어온다.** 감독관 콘솔·확정/기각은 그대로다.
- 이벤트가 난 구간(앞 8초·뒤 4초)은 **승격 복사**하고 **3일 보관, 3일 단위로 연장**할 수 있다(연장 최대 2번·삭제 1일 전부터, 확정 2026-11-26, §6-3. 상시 저장분 자체의 연장은 미정). 서버 추론 스위치가 꺼진 회차는 기존 규칙(7일, 7일씩 최대 2번)이 **그대로**다.
- 휴대폰 **라이브 영상**은 응시자·감독관 어디에도 표시하지 않는다(응시자 미리보기 포함). 이벤트 구간·감독 중단 구간에 한해 감독관이 **사후 사진**으로 볼 수 있다(D-23 확정, 2026-11-26). 입장 점검은 서버가 돌려주는 판정 결과(키보드·마우스·두 손 인식 여부)만 보여 준다.
- 추론 서버가 죽으면 시험은 계속되고 그 구간은 **"감독 중단"** 이벤트로 기록한다. 그 구간의 웹캠·휴대폰 사진은 저장되어 있어 사람이 사후에 볼 수 있다(§6-5).
- 해외 서버(RunPod) 처리는 **동의 문구로 고지하고 진행**한다(§13). 실응시자 파일럿 전에 법무 확인을 한 번 권한다.
- 모든 새 동작은 스위치(`SERVER_VISION_ENABLED`)로 끌 수 있다. **끄면 지금의 PC 분석 동작이 그대로**다(배포·롤백 안전판, §14).

> 주의 하나: 의도 문서의 "PC 폴백 없음"은 **스위치를 켠 상태**의 규칙이다. 스위치를 끄면 기존 PC 분석 코드가 그대로 돈다. 롤백(§14)이 이 조건에 기대므로, **기존 PC 분석 코드는 이번 작업에서 지우지 않는다**(지우는 것은 안정화된 뒤 별도 결정).

## 2. 전체 데이터 흐름

```
[응시자 PC 브라우저]                                  [휴대폰 페이지]
  웹캠 → 사진(JPEG) 1~2장/초 ──┐                       카메라 → 사진(JPEG) 1~2장/초 ──┐
                               │ WSS (binary)                                       │ WSS (binary)
                               ▼                                                    ▼
                   ┌────────────────── 백엔드 (Spring) ───────────────────┐
                   │ /ws/vision  입장 토큰 확인 · 짝 확인 · 속도 제한      │
                   │ ① 웹캠·휴대폰 사진 각 초당 1장, 10초 묶음 S3 상시 저장 │──→ 파일 서버(S3)
                   │ ② 최신 프레임만 추론 서버로 전달 (우편함, 대기열 없음) │      exam-stream/…
                   │ ③ 추론 서버 상태 감시 → 죽으면 "감독 중단" 이벤트      │
                   └───────────┬───────────────────────────▲──────────────┘
                  HTTPS/WS     │ 프레임 + 메타              │ 이벤트 후보 / 판정 결과
                               ▼                           │
                   ┌────────── 추론 서버 (RunPod GPU, 1대 → 필요 시 2대) ─┐
                   │ 응시자별 세션: 최신 프레임만 분석, 보정 기준 보관     │
                   │ 웹캠: 얼굴·고개·시선·몸통 / 휴대폰: 손·키보드·마우스  │
                   │ 규칙 엔진(지속시간·쿨다운). 사진은 저장하지 않는다     │
                   │ (이벤트는 사진 없이 콜백(HMAC)으로만 전달)            │
                   └───────────────────────────────────────────────────────┘
                               │ 이벤트 (종류·시각·신뢰도·지속시간, HMAC 서명)
                               ▼
                    백엔드: proctor_events 저장 → 이벤트+약 5초 뒤
                            상시 저장분(웹캠·휴대폰)에서 앞 8초·뒤 4초 승격 복사(proctor_event_frames)
                               ▼
                    감독관·매니저 콘솔 (기존 타임라인, 확정/기각)
```

### 2-1. 왜 백엔드를 거치나 (추론 서버로 직접 안 보내고) **[제안]**
- 입장 토큰·회차 상태·감독 사용 여부 검증이 백엔드에 이미 있다(`RelayAuthService`, `ExamSession.isProctoring`).
- 추론 서버 주소·키를 브라우저에 노출하지 않는다(응시자가 추론 서버를 직접 두드리거나 주소를 알게 하지 않는다).
- 추론 서버 교체·2대 이상 분산·장애 감지를 백엔드 한 곳에서 한다.
- 단점: 백엔드를 지나는 대역폭 증가, 한 번 더 건너는 지연. 용량은 §11에서 따진다. **백엔드 서버 크기·대역폭 한도는 [미확인].**

> **결정 필요 D-1:** 브라우저→추론 서버 직접 연결(백엔드가 단기 토큰만 발급)과 비교하면 백엔드 부하는 줄지만 보안·운영이 복잡해진다. 이 문서는 **백엔드 경유**를 기본안으로 한다.

### 2-2. 이벤트와 사진은 누가 저장하나 **[제안]**
- **사진 저장은 백엔드, 판정은 추론 서버**로 역할을 나눈다. 추론 서버는 DB와 S3를 직접 건드리지 않는다. 이렇게 하면 추론 서버가 죽어도 사진 저장은 계속되고, 사진과 판정이 서로 의존하지 않는다.
- 추론 서버는 이벤트(종류·시각·신뢰도·지속시간·`clientId`)를 백엔드 내부 API로 보낸다. 백엔드가 기존 규칙(`clientId` 멱등, 한도 검사, 회차 상태 검사)을 지켜 `proctor_events`에 저장한다.
- 이벤트에는 사진이 없다. 사진은 **이벤트 시각으로 상시 저장분에서 끌어온다**(§6).
- 휴대폰 이벤트도 사진을 붙이지 않는다. 휴대폰 사진도 상시 저장되므로 웹캠과 똑같이 이벤트 시각으로 꺼내 승격한다(2026-11-25 개정: 이전의 "최신 휴대폰 사진 1장 첨부"는 폐기).

## 3. 프로토콜과 API (계약)

> 이 절이 **프론트·백엔드·추론 서버가 따르는 계약**이다. 같은 내용을 노트 폴더 `contract.md` 에도 둔다. 계약을 바꾸면 이 절과 `contract.md` 를 같이 고치고 `contract.md` 위쪽에 변경 이력을 적는다.
> 값이 **(임시)** 인 것은 실측(§12 M1~M6) 전의 출발값이다. 계약의 모양(필드·상태 코드)은 바뀌지 않고 값만 설정으로 바뀐다.

### 3-0. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 적용 조건 | **세 조건이 모두 참일 때만** 서버 추론 모드: ① 백엔드 `PAIR_SERVER_VISION_ENABLED=true` ② 회차 `exam_sessions.server_vision=true` ③ 회차 `proctoring=true`. 하나라도 거짓이면 이 절의 경로는 닫혀 있고(`/ws/vision` 은 4403) 기존 PC 분석 동작이 그대로다 |
| 모드 판정 | 프론트는 `GET /api/entry/{invite}` 의 `serverVision`(§3-7)을 보고 모드를 고른다. 프론트 스위치 `VITE_SERVER_VISION_ENABLED` 도 켜져 있어야 한다 |
| `visionKey` | 응시자(대상자)마다 백엔드가 만드는 **불투명 키**. 22자 base64url(무작위 16바이트), `exam_participants.vision_key`(UNIQUE)에 저장, 처음 필요할 때 만들고 이후 같은 값을 쓴다. 추론 서버에는 이 키만 알려 주고 이름·메일·대상자 번호는 알리지 않는다. 설계 초안의 "HMAC 파생 `sessionKey`"는 **폐기**(콜백에서 되돌려 찾기 어려워서). 문서·코드에서 `sessionKey` = `visionKey` |
| 시각 | 서버가 정한다. 프레임 시각 = **백엔드가 프레임을 받은 시각**(epoch ms). PC·휴대폰 시계는 쓰지 않는다. 공개 API 의 시각은 ISO-8601 UTC, 내부(백엔드↔추론 서버) 의 시각은 epoch ms(정수) |
| 채널 | `webcam`(노트북 웹캠, 이벤트 `source=PC_CAM`) · `phone`(휴대폰, `source=PHONE_CAM`) |
| 모드 | `check`(입장 점검: 판정 결과만 돌려주고 **저장·이벤트 없음**) · `exam`(시험 중: 상시 저장·이벤트). 백엔드가 대상자 상태(시험 시작 여부)로 정한다 |
| 오류 본문 | 공개 HTTP: `{"message":"한국어 문장","code":"UPPER_SNAKE"}`(기존 `message` 규칙에 `code` 추가). WebSocket: `{"type":"error","code":"...","message":"..."}` 뒤에 닫는다 |
| 로그 | 프레임·사진·키·서명·`invite`·`pairCode` 를 로그에 남기지 않는다 |

### 3-1. 응시자 PC·휴대폰 → 백엔드 (WebSocket `/ws/vision`)

기존 `/ws/proctor` 는 그대로 둔다(스위치 꺼짐일 때 사용). 새 경로는 같은 Spring WebSocket 기반이며 `ProctorRelayService` 의 구조(최신 한 장 우편함, 속도 제한, hello 제한 시간, 소켓당 hello 1회, `ConcurrentWebSocketSessionDecorator`)를 참고한다. 한 응시자에 **웹캠 소켓 1개 + 휴대폰 소켓 1개**.

**연결과 hello** (연결 후 10초 안에 hello 가 없으면 닫는다, 소켓당 hello 1회)

| 방향 | 메시지 | 설명 |
|---|---|---|
| PC → 서버 | `{"type":"hello","role":"webcam","invite":"<입장 토큰>"}` | 토큰 검증, 대상자·회차 조회. 시험 시작 전이면 `mode:"check"`, 시작 후면 `exam`. `invite` 는 `/ws/vision` 연결 주소가 아니라 이 메시지에만 담는다(접근 로그에 남지 않게) |
| 휴대폰 → 서버 | `{"type":"hello","role":"phone","pairCode":"<짝 코드>"}` | 짝 코드로 같은 응시자에 연결. 짝 코드는 아래 `paired` 로 PC 가 받는다(기존 방식) |
| 서버 → PC | `{"type":"paired","pairCode":"...","phoneUrl":"<entry-base-url>/proctor/phone?p=<pairCode>"}` | 웹캠 hello 직후. 휴대폰 QR 용 |
| 서버 → 둘 다 | `{"type":"ready","mode":"check"\|"exam","vision":"up"\|"down","rate":{...},"serverTimeMs":1764000000000}` | hello 수락. 이후 프레임을 보내도 된다 |
| 서버 → PC | `{"type":"peer","phone":"connected"\|"disconnected"\|"stale"}` | 휴대폰 상태. 15초 무신호면 `stale` |
| 서버 → PC | `{"type":"mode","mode":"exam"}` | 시험 시작(`/start`)으로 모드가 바뀜. 소켓은 유지 |

**프레임** (binary, 둘 다 같은 형식)

```
offset 0   uint32 BE   seq        소켓 안에서 1씩 늘어나는 번호(재연결하면 다시 시작해도 됨)
offset 4   ...         JPEG       첫 3바이트 FF D8 FF 필수
```
- 전체 최대 100KB(= 헤더 4바이트 + JPEG). 넘으면 그 프레임을 버리고 `{"type":"error","code":"FRAME_TOO_LARGE"}`(소켓 유지, 10초에 1번만 알림). JPEG 시작 바이트가 아니면 `BAD_FRAME` 로 같은 처리.
- 캡처 시각은 보내지 않는다(서버 수신 시각을 쓴다).
- 서버는 소켓마다 **최신 한 장 우편함**(대기열 없음)으로 추론 서버에 넘긴다. 상시 저장은 이 우편함과 별개로 받은 **모든 프레임에서 1초마다 처음 온 한 장**을 쓴다(§6-1).
- 속도 제한: 소켓당 초당 3장까지 처리(넘는 프레임은 조용히 폐기), 1초에 30장 넘으면 닫는다(4429).

**제어 메시지** (text JSON)

| 방향 | 메시지 | 규칙 |
|---|---|---|
| 서버 → 둘 | `{"type":"rate","fps":1,"maxEdge":400,"quality":0.55}` | 보낼 간격·크기·화질. `ready` 에 처음 값이 들어 있고, 부하 조절 때 다시 보낸다. 받은 **다음 프레임부터** 적용. **(임시)** 웹캠 `fps:1,maxEdge:400,quality:0.55`(기존 증거 링 값 재사용), 휴대폰 `fps:1,maxEdge:512`, `quality` 는 휴대폰이 장당 약 13~15KB 가 되게 기존 자동 조절을 쓰고 이 값은 상한. `fps` 범위 0.5~2 |
| 서버 → PC | `{"type":"status","vision":"up"\|"down","phone":"connected"\|"disconnected"\|"stale"}` | 상태가 바뀔 때, 그리고 30초마다. `vision:"down"` 이면 "감독 시스템이 일시 중단되었습니다" 배너(시험은 계속) |
| 서버 → PC | `{"type":"check","items":{"keyboard":true,"mouse":true,"leftHand":false,"rightHand":false,"desk":true},"hints":["LEFT_HAND_MISSING"],"holdMs":1200,"passed":false}` | **`check` 모드에서만, 휴대폰 프레임을 분석할 때마다 최대 초당 2번.** 영상·사진 없음. `hints` 는 코드 목록(아래), 문장은 프론트가 만든다. `holdMs` = 모든 항목이 연속으로 참인 시간, `passed` = `holdMs ≥ 3000`(임시) |
| 클라이언트 → 서버 | `{"type":"ping"}` → `{"type":"pong"}` | 5초마다. 휴대폰은 기존 `heartbeat` 와 같은 주기. 15초 무신호면 상대에 `stale` |
| 서버 → 클라이언트 | `{"type":"error",...}` | 아래 오류 코드표 |

`hints` 코드(**잠정**, D-9 방향 힌트 수준 확정 전): `KEYBOARD_MISSING` `MOUSE_MISSING` `LEFT_HAND_MISSING` `RIGHT_HAND_MISSING` `DESK_PARTIAL` `KEYBOARD_LEFT` `KEYBOARD_RIGHT` `KEYBOARD_TOP` `KEYBOARD_BOTTOM`. 코드가 추가될 수 있으므로 **프론트는 모르는 코드를 무시**한다.

**닫기 코드·오류 코드**

| 코드 | `code` | 뜻 | 프론트 동작 |
|---|---|---|---|
| 4400 | `BAD_REQUEST` | hello 형식 오류, 두 번째 hello, 모르는 `role` | 재시도 안 함 |
| 4401 | `UNAUTHORIZED` | 입장 토큰·짝 코드 틀림, 회차 종료 30분 뒤 | 재시도 안 함 |
| 4403 | `VISION_DISABLED` | §3-0 적용 조건이 거짓(스위치 꺼짐) | 서버 모드를 쓰지 않음(PC 분석 경로로) |
| 4403 | `CONSENT_REQUIRED` | `proctor_consents.consent_version` 이 `v3` 가 아님 | 동의 화면으로 |
| 4409 | `REPLACED` | 같은 응시자·같은 역할의 새 소켓이 붙어 옛 소켓을 닫음 | 재연결 안 함 |
| 4429 | `RATE_LIMITED` | 속도·연결 수 초과 | 5초 뒤 재연결 |
| 4500 | `INTERNAL` | 서버 오류 | 지수 재연결(1·2·4·8초, 최대 30초) |
| (소켓 유지) | `FRAME_TOO_LARGE` `BAD_FRAME` | 프레임 거절 | 다음 프레임부터 정상 |

재연결: 끊기면 프론트가 같은 hello 로 다시 붙는다(기존 `RelaySocket` 재연결 재사용). 시험 중 재연결은 `mode:"exam"` 으로 곧바로 `ready` 가 온다. 재연결 중 못 보낸 구간은 사진이 없을 뿐 시험은 계속된다.

### 3-2. 백엔드 → 추론 서버 (WebSocket `/v1/stream`)

백엔드 **인스턴스마다 추론 서버 인스턴스 하나당 장수명 연결 1개**(응시자별 연결을 만들지 않는다). 인증은 §3-5.

**프레임** (binary, 백엔드 → 추론 서버)
```
offset 0   uint8       version     = 1
offset 1   uint8       channel     1=webcam, 2=phone
offset 2   uint32 BE   seq         백엔드가 소켓(응시자·채널)마다 매기는 번호, 같은 번호는 버림
offset 6   uint64 BE   recvMs      백엔드가 받은 시각(epoch ms) = 규칙 계산에 쓰는 프레임 시각
offset 14  16 bytes    visionKey   22자 base64url 을 푼 원본 16바이트
offset 30  ...         JPEG
```
- 추론 서버는 `visionKey` 가 `start` 로 등록되지 않았으면 프레임을 버리고 `{"type":"error","code":"UNKNOWN_SESSION","sessionKey":"..."}` 를 보낸다(키마다 10초에 1번). 백엔드는 이 오류를 받으면 §3-6 의 복구를 한다.
- 응시자·채널마다 **큐 길이 1**(최신만). 처리 못 한 이전 프레임은 폐기하고 지표로 센다. 응답을 프레임마다 기다리지 않는다(비동기 푸시).

**추론 서버 → 백엔드** (text JSON)

| 메시지 | 설명 |
|---|---|
| `{"type":"state","sessionKey":"…","calibration":"pending"\|"done","webcam":"ok"\|"idle","phone":"ok"\|"idle","analysisFps":{"webcam":1.0,"phone":1.0},"lastAnalyzedMs":1764000000000}` | **`exam` 으로 등록된 활성 세션마다 2초마다.** 백엔드는 이것을 **생존 신호**로 쓴다(§10-1). `idle` = 최근 5초 프레임 없음 |
| `{"type":"check","sessionKey":"…","items":{…},"hints":[…],"holdMs":1200,"passed":false}` | `check` 모드 세션의 판정(§3-1 `check` 와 같은 본문). 백엔드가 `sessionKey` 만 떼고 PC 로 그대로 전달 |
| `{"type":"error","code":"UNKNOWN_SESSION"\|"OVER_CAPACITY"\|"BAD_FRAME","sessionKey":"…"}` | 프레임 거절 |

이벤트는 이 연결로 보내지 **않는다**(HTTP 콜백, §3-4 — 재시도·서명·멱등이 필요해서).

### 3-3. 추론 서버 REST API

모든 요청에 `Authorization: Bearer <키>`(§3-5). **`/healthz` 만 인증 없이 열린다**(RunPod 상태 확인용). `/readyz`·`/metrics` 는 Bearer 필요(백엔드·Prometheus 가 붙인다). 오류 본문은 `{"code":"...","message":"..."}`(추론 서버 내부 계약이라 영어 `message` 가능).

| 메서드 | 경로 | 요청 → 응답 |
|---|---|---|
| POST | `/v1/sessions/{key}/start` | `{"mode":"check"\|"exam","startedAtMs":1764000000000,"rulesProfile":"default","recalibrate":false}` → 200 `{"accepted":true,"resumed":false,"sessions":12,"maxSessions":40}`. **멱등**: 이미 있는 키면 200 `resumed:true`(보정·타이머 유지, **`drain` 중에도** 받는다 — 백엔드 재시작 복구용). 이미 있는 키에 다른 `mode` 로 `start` 해도 모드는 바뀌지 않는다. `startedAtMs` 가 없으면 서버 현재 시각. `recalibrate:true` 면 보정만 다시 시작. 자리가 없으면 **503** `{"code":"OVER_CAPACITY"}` + `Retry-After: 5`. 서버가 `drain` 중이면 **503** `DRAINING`. 키 형식 틀림·모르는 `mode` 는 400 `BAD_REQUEST` |
| POST | `/v1/sessions/{key}/mode` | `{"mode":"exam","startedAtMs":…}` → 200. `check`→`exam` 전환(**`exam` 만 받는다**): 웹캠 보정(3초, 임시; 웹캠 프레임 `recvMs` 간격 기준) 시작, 이벤트 발행 시작. **휴대폰 손 규칙은 보정과 무관하게 `exam` 즉시 동작**한다. 모르는 키면 404 `UNKNOWN_SESSION`(백엔드는 `start` 부터 다시) |
| POST | `/v1/sessions/{key}/end` | 빈 본문 → 200 `{"flushedEvents":0}`. 진행 중이던 이상 상태를 `final:true` 로 마무리해 콜백을 보낸 뒤 메모리를 비운다. **모르는 키도 200**(멱등) |
| GET | `/healthz` | 200 `{"ok":true}` (프로세스) |
| GET | `/readyz` | 준비되면 200, 모델·GPU 문제로 준비 안 되면 503. **`drain` 중에도 200 + `draining:true`**(503 이면 백엔드가 인스턴스를 죽은 것으로 보고 감독 중단으로 오인하므로). 백엔드는 `draining:true` 인 인스턴스에 새 응시자를 배정하지 않는다. 본문 `{"ready":true,"modelsLoaded":true,"gpu":true,"sessions":12,"maxSessions":40,"draining":false,"version":"…","rulesVersion":"…"}`. **`maxSessions` 값은 [미확인, M4·M5 실측 후]**. 백엔드가 5초마다 호출, 연속 3회 실패하면 그 인스턴스 제외 |
| GET | `/metrics` | Prometheus 형식(프레임 지연·폐기율·GPU 사용률·세션 수·이벤트 수·콜백 실패) |
| POST | `/v1/admin/drain` | 새 세션을 받지 않고(`start` 503 `DRAINING`) 기존 세션이 끝나길 기다림 → 202 |

### 3-4. 추론 서버 → 백엔드 이벤트 콜백

`POST /internal/vision/events` (백엔드 공개 주소의 같은 서버에 있지만 **응시자·콘솔 API 와 같은 인증을 쓰지 않는다**. HMAC 서명만 인정하고, 가능하면 인그레스에서 추론 서버 IP 만 허용 — RunPod IP 고정 방식은 [미확인])

요청 헤더(전부 필수): `X-Vision-Key-Id: k1` · `X-Vision-Timestamp: 1764000000`(epoch **초**) · `X-Vision-Signature: <hex>` · `Content-Type: application/json`.
서명 = `hex( HMAC-SHA256(콜백 비밀, timestamp + "." + 원본 본문 바이트) )`.

```json
{
  "clientId": "v3b7c1f0a9d2e4458a1c0f6e7d2b9a41c",
  "sessionKey": "Zk3xQmV0aGlzSXNBS2V5MQ",
  "type": "HANDS_OUT",
  "source": "PHONE_CAM",
  "startedAtMs": 1764000123456,
  "durationMs": 7040,
  "confidence": 0.82,
  "detail": { "state": "BOTH_OUT", "handsSeen": 0 },
  "final": false,
  "rulesVersion": "2026-11-25.1"
}
```

| 필드 | 규칙 |
|---|---|
| `clientId` | 필수. 결정적 값: `"v" + hex(SHA-256(sessionKey + "\|" + type + "\|" + floor(startedAtMs/1000)))` 앞 32자(총 33자, 영숫자). 기존 `clientId` 규칙(8~36자 영숫자·`-`)과 호환 |
| `sessionKey` | 필수. 백엔드가 `exam_participants.vision_key` 로 대상자를 찾는다 |
| `type` | 필수. 서버 추론이 만드는 유형: `NO_FACE` `MULTI_FACE` `HEAD_TURN` `HEAD_DOWN` `GAZE_AWAY`* `TORSO_SHIFT` `TORSO_TURN`(웹캠, `source=PC_CAM`; *`GAZE_AWAY` 는 유형만 남기고 **서버 추론은 만들지 않는다**, 2026-11-26 사용자 결정) · `HANDS_OUT` `HAND_OUT_ONE` `PHONE_MOVED`(`PHONE_CAM`) · `TABLET` `NOTE` `SMARTWATCH`(`PHONE_CAM` 만; 웹캠 `PC_CAM` 에서는 이 세 유형을 만들지 않는다 — 확정 2026-11-26). `SUPERVISION_PAUSED` 는 **받지 않는다**(백엔드가 만든다, §10-1). 목록 밖은 400 |
| `source` | 필수. 위 표의 값과 맞아야 함(`HANDS_OUT` 이 `PC_CAM` 이면 400) |
| `startedAtMs` | 필수. **이상 상태가 시작된 프레임의 `recvMs`**. 검증: 대상자가 시험을 시작한 시각 이후, 서버 현재 시각 + 5초 이내 |
| `durationMs` | 필수, 0 ~ 3,600,000. 처음 보낼 때는 규칙이 성립한 시점의 값(예: `HANDS_OUT` 이면 7000 이상) |
| `confidence` | 선택, 0~1 |
| `detail` | 선택, 객체, 직렬화 4,000자 이하. 사진·영상·개인 정보 금지 |
| `final` | 선택(기본 false). 이상 상태가 끝났을 때 마지막 `durationMs` 로 한 번 더 보내며 true |
| `rulesVersion` | 필수. 규칙·임계값 버전(`rulesProfile` 과 함께 기록용) |

**응답**

| 상태 | 본문 | 뜻 · 추론 서버 동작 |
|---|---|---|
| 201 | `{"id":12,"duplicate":false}` | 새 이벤트 저장 |
| 200 | `{"id":12,"duplicate":true,"updated":false\|true}` | 같은 `clientId` 가 이미 있음. 새 `durationMs` 가 **더 크면** 갱신(`updated:true`), 아니면 그대로. 지속시간은 줄어들지 않는다. `final` 이어도 이미 사진 구간은 건드리지 않는다 |
| 400 | `{"code":"INVALID_EVENT","message":"…"}` | 필드 오류. **재시도하지 않고** 버린다(경고 지표) |
| 401 | `{"code":"MISSING_SIGNATURE"}` | 서명 헤더 없음 |
| 403 | `{"code":"BAD_SIGNATURE"\|"STALE_TIMESTAMP"\|"UNKNOWN_KEY_ID"}` | 서명 불일치·타임스탬프가 서버 시각 ±60초 밖·모르는 키 번호 |
| 404 | `{"code":"UNKNOWN_SESSION_KEY"}` | 모르는 `sessionKey`. 재시도하지 않는다 |
| 409 | `{"code":"SESSION_NOT_ACTIVE"}` | 시작하지 않은 응시자·감독 없는 회차·서버 추론이 아닌 회차·종료 30분 뒤. 재시도하지 않는다 |
| 413 | `{"code":"TOO_LARGE"}` | 본문 16KB 초과 |
| 422 | `{"code":"LIMIT_REACHED"}` | 대상자당 이벤트 한도 초과(기존 한도 규칙). 이벤트는 만들지 않는다 |
| 429·5xx·연결 오류 | | **재시도**: 1·2·4·8·16·30초, 이후 30초 간격, 10분까지. **401·403(시계 오차·키 교체 중일 수 있음)도 같은 일정으로 재시도**한다. 400·404·409·413·422 는 재시도 없이 버린다. 같은 `clientId`·같은 본문(타임스탬프·서명만 새로). 추론 서버 안의 대기 큐는 최대 1,000건(넘으면 가장 오래된 것부터 버리고 지표) |

저장 규칙: 기존 `proctor_events` 와 같다(`attempt_id` 없음, `received_at` = 서버 수신 시각, `snapshot` 없음 — **이벤트에는 사진을 붙이지 않는다**). 저장 뒤 §6-2 의 구간 승격을 예약한다.

### 3-5. 인증·서명

| 구간 | 방식 |
|---|---|
| 응시자 PC·휴대폰 → 백엔드 `/ws/vision` | 입장 토큰·짝 코드를 hello 에서 검증(기존 `RelayAuthService` 방식). 서버 추론 적용 조건·동의 v3 확인(§3-1) |
| 백엔드 → 추론 서버(REST·`/v1/stream`) | `Authorization: Bearer <VISION_API_KEY>`. 키 **두 개 동시 유효**(`VISION_API_KEY`, `VISION_API_KEY_NEXT`)로 무중단 교체. 틀리면 401 `UNAUTHORIZED`(스트림은 연결 거절). 추론 서버는 응시자 토큰을 받지 않는다 |

| 비밀 보관 | 환경 변수·RunPod 시크릿. 저장소·로그·프론트 번들에 넣지 않는다 |
| 환경 변수 이름 | 추론 서버: `VISION_API_KEY`·`VISION_API_KEY_NEXT`(백엔드가 보내는 Bearer), `VISION_CALLBACK_URL`·`VISION_CALLBACK_KEY_ID`(기본 `k1`)·`VISION_CALLBACK_SECRET`(콜백 서명용, 한 번에 비밀 하나; `k2` 로 바꿀 때는 KEY_ID·SECRET 을 바꿔 다시 띄움), `VISION_MAX_SESSIONS`(기본 40 — **[미확인, M4·M5]**), `VISION_MAX_FRAME_BYTES`(기본 256KB; 백엔드는 헤더 30바이트 + 100KB 이하만 보내므로 그 안쪽 한도는 `/ws/vision` 이 지킨다. 넘으면 `BAD_FRAME`) |

### 3-6. 중복 방지·복구

- **이벤트 멱등**: `clientId` 결정적(§3-4) + 기존 `(participantId, clientId)` 조회. 추론 서버가 2대 사이에서 응시자를 옮기거나 재시도해도 같은 이벤트가 된다.
- **프레임 중복**: 추론 서버가 `(visionKey, channel, seq)` 가 이미 처리한 것이면 버린다.
- **응시자 고정 배정**: 인스턴스 목록 `[a,b]` 중 `visionKey` 해시로 한 대에 고정. 목록 길이가 1이어도 같은 코드로 동작.
- **추론 서버 재시작·`UNKNOWN_SESSION`**: 백엔드가 그 인스턴스의 활성 세션 전부에 `start`(`recalibrate:true`) 를 다시 호출한다. 보정과 규칙 타이머는 다시 시작하고, 진행 중이던 이상 상태는 새로 센다. 상시 저장은 영향이 없다.
- **인스턴스가 죽음**: 같은 목록의 다른 인스턴스로 옮기고 `start`(`recalibrate:true`). 1대뿐이면 그 시간은 감독 중단(§10-1).
- **백엔드 재시작**: 응시자 소켓은 프론트가 재연결, 추론 서버 연결은 백엔드가 다시 맺고 활성 세션에 `start`(`resumed` 이면 보정 유지).
- 사진은 백엔드가 따로 저장하므로 추론 서버가 죽어도 잃지 않는다.

## 4. 프론트(응시자 PC·휴대폰) 변경 **[제안]**

스위치 `SERVER_VISION_ENABLED`(프론트 `VITE_SERVER_VISION_ENABLED`, 백엔드 `PAIR_SERVER_VISION_ENABLED`) 둘 다 켜져야 동작한다. 서버가 꺼져 있으면 서버 모드를 쓰지 않고 지금 동작 그대로.

- **웹캠**: 기존 `captureSnapshot`/`frameLoop` 재사용해 사진을 만든다. MediaPipe 분석·보정·`RuleEngine` 호출은 건너뛴다. 전송 간격·크기는 **서버가 `rate` 메시지로 지시**(기본안은 §11의 실측 전 임시값).
- **휴대폰**: `phoneSender.ts`가 이미 JPEG 송신을 한다(평소 긴 변 512px, 책상 스캔 1280px, 장당 13~15KB 목표). 목적지만 `/ws/vision`으로 바꾼다. **휴대폰 화면에는 영상을 띄우지 않는다**(§9). 현재 휴대폰 페이지가 카메라 미리보기를 보여 주는지는 **[미확인]** — 구현 때 `PhoneCamPage.tsx`·`PhoneVideo.tsx`·`PhonePairCard.tsx`·`CamPreview.tsx`를 확인한다.
- **느린 PC 보호**: 서버 모드에서는 PC가 분석을 안 하므로 환경 점검의 "분석 속도 등급"(`perfCheck`)이 의미가 줄어든다. 대신 **업로드 대역폭 점검**(§9-3)을 넣는다.
- **끊김 처리**: 서버가 `vision:"down"`을 알리면 화면에 "감독 시스템이 일시 중단되었습니다. 시험은 계속 진행됩니다" 배너를 띄운다(응시자 불안 방지). 응시자는 아무것도 할 필요가 없다.
- **증거 링(`EvidenceRecorder`)**: 서버 모드에서는 PC 링 버퍼와 이벤트 후 업로드를 쓰지 않는다(백엔드가 상시 저장). 코드는 남긴다(스위치 꺼짐용).

## 5. 추론 서버 내부 구조 **[제안]**

```
입력(WS) → 응시자별 큐(길이 1, 최신만) → 워커 풀(GPU 배치) → 규칙 엔진 → 이벤트 큐 → 백엔드
                                   (사진은 저장하지 않는다)
```

- **최신 프레임만 처리**: 응시자·채널마다 큐 길이 1. 새 프레임이 오면 처리 못한 이전 것은 버린다(지연이 쌓이지 않는다). 버린 개수는 지표로 기록한다.
- **GPU 배치**: 여러 응시자의 최신 프레임을 모아 작은 배치(예: 최대 8~16, 대기 최대 30~50ms)로 추론해 GPU 효율을 올린다. 값은 측정으로 정한다(**[미확인]**).
- **분석 순서**: (웹캠) 얼굴 수·고개 각도·시선·어깨 → 기존 `pcRules`와 같은 기준 / (휴대폰) 손 랜드마크·키보드·마우스 → §7 / (보조) 태블릿·메모·스마트워치 → §8.
- **보정(calibration)**: 시험 시작 후 3초(`CALIBRATION_MS=3000`, 현재와 동일)의 "정면 자세"를 응시자별로 서버가 계산한다. 기준 자세는 서버 메모리에만 둔다.

### 5-1. 추론 서버 메모리 (링 버퍼 없음) **[제안]**
- 상시 저장 방식이므로 **앞 8초 링 버퍼가 필요 없다.** 추론 서버는 응시자별로 보정 기준 자세, 규칙 타이머 상태만 들고 있다(사진은 처리 중인 최신 프레임 한 장뿐). 사진은 디스크에 쓰지 않는다(스왑·크래시 덤프 방지: 코어 덤프 비활성).
- 서버가 재시작되면 보정과 타이머가 사라지므로 해당 응시자는 보정을 다시 한다(§10). 사진은 백엔드에 저장되어 있어 잃지 않는다.
- 메모리는 응시자 30명 기준 수 MB 수준이라 병목이 아니다. 병목은 JPEG 디코드(CPU)와 GPU 추론이다(§12).

## 6. 사진 상시 저장과 증거 구간 (계약)

> 2026-11-25 사용자 확정: **웹캠·휴대폰 모두 초당 1장 상시 저장**, 상시 저장분 **3일**, 이벤트 구간 **3일 + 3일 단위 연장**. 서버 추론이 꺼진 회차는 기존(7일, 7일씩 연장)이 그대로다.

### 6-1. 상시 저장 (웹캠 + 휴대폰)

**샘플링**: 백엔드가 `exam` 모드 소켓에서 받은 프레임 중 **1초(서버 시계 기준 `floor(recvMs/1000)`)마다 처음 온 한 장**을 그 채널의 묶음 버퍼에 넣는다. `check` 모드(입장 점검)는 저장하지 않는다. 한 장 최대 100KB.

**묶음 단위**: 서버 시계 기준 **10초 정렬 구간**(`startMs = floor(recvMs/10000)*10000`)마다 채널별로 묶음 1개. 정렬하므로 같은 구간을 다시 올려도 같은 키로 덮어쓴다(멱등). 구간이 끝난 뒤 1초 안에 올린다. 소켓이 끊기거나 시험이 끝나면 버퍼를 즉시 올린다(`flush`).

**S3 키**: `exam-stream/{sessionId}/{participantId}/{webcam|phone}/{startMs}.pack` (비공개 버킷, SSE-S3, `Content-Type: application/octet-stream`). 키에 대상자 번호가 있어도 추론 서버에는 노출되지 않는다(추론 서버는 S3에 접근하지 않는다).

**`.pack` 파일 형식** (big-endian)
```
offset 0    6 bytes   magic       "PAIRPK"
offset 6    uint8     version     1
offset 7    uint8     channel     1=webcam, 2=phone
offset 8    uint16    count       들어 있는 사진 수 (1~10)
offset 10   uint64    startMs     구간 시작(epoch ms, 10초 배수)
offset 18   count × { uint32 offsetMs   startMs 로부터의 거리(0~9999, 그 초의 정각이 아니라 실제 수신 시각)
                      uint32 length }   JPEG 바이트 수
offset 18+8·count     JPEG 본문들을 목차 순서대로 이어 붙임
```
읽는 쪽은 `magic`·`version` 이 다르면 그 묶음을 건너뛰고 오류 지표를 올린다.

**실패·유실**: S3 올리기 실패는 1·2·4초 간격으로 3번 다시 시도하고, 그래도 안 되면 그 묶음을 버리고 `stream_pack_failed` 지표·오류 로그(키·대상자 번호만, 사진 없음). 시험은 계속된다. 백엔드가 비정상 종료하면 **최대 10초분이 유실**된다(메모리 묶음).

**테이블 `proctor_stream_packs`** (묶음마다 한 행; 사진마다 행·객체를 만들지 않는다)

| 컬럼 | 설명 |
|---|---|
| `pack_id` BIGSERIAL PK | |
| `session_id` BIGINT FK → exam_sessions | 삭제 배치·보관 기준 |
| `participant_id` BIGINT FK → exam_participants | |
| `channel` VARCHAR(8) | `WEBCAM` / `PHONE` (CHECK) |
| `start_at` TIMESTAMPTZ | 구간 시작 |
| `end_at` TIMESTAMPTZ | 구간 끝(= `start_at` + 10초) |
| `frame_count` SMALLINT | 1~10 |
| `size_bytes` INT | `.pack` 크기 |
| `storage_key` VARCHAR(255) | S3 키(지운 뒤에도 남김) |
| `created_at` TIMESTAMPTZ | |
| `deleted_at` TIMESTAMPTZ NULL | 보관 기간이 지나 파일을 지운 시각 |

UNIQUE(`participant_id`, `channel`, `start_at`), 인덱스 (`session_id`) WHERE `deleted_at IS NULL`. 행 수: 30명 · 2시간 · 2채널 약 **4.3만 행**.

### 6-2. 이벤트 구간 꺼내기·승격

**구간**: 이벤트 `startedAt`(= `startedAtMs`) 기준 **앞 8초·뒤 4초**, 1초 간격 **12장/채널**(offset `-8000, -7000, …, 0, …, +3000`). 해당 초에 사진이 없으면 그 칸은 건너뛴다. 이벤트가 난 채널 하나만이 아니라 **웹캠·휴대폰 두 채널 모두** 꺼낸다(최대 24장). **가정**: 구간 기준은 `startedAt`(이상 상태가 시작된 시각)이다. `HANDS_OUT`(7초)·`HAND_OUT_ONE`(10초)처럼 길게 이어지는 이벤트는 판정 시점이 `startedAt` + 7~10초라서 구간(+3초까지)이 이상 상태의 앞부분만 담는다 — 판정 시점 기준으로 바꿀지는 **결정 필요**(§17-1 D-22).

**승격 시점**: `promoteAfter = max(이벤트 수신 시각, startedAt + 4초) + 12초`(마지막 묶음이 올라갈 시간). 두 가지로 승격된다.
1. **백그라운드 승격**: 이벤트 저장 때 예약, `promoteAfter` 가 되면 1분 주기 작업이 처리.
2. **콘솔 요청 시 승격(lazy)**: 콘솔이 `GET …/events/{eventId}/clip` 을 열었을 때 아직 승격 전이고 `promoteAfter` 가 지났으면 그 자리에서 승격하고 응답한다. 같은 이벤트를 두 곳이 동시에 승격해도 UNIQUE(`event_id`,`source`,`offset_ms`)로 한 번만 저장된다(멱등).

**승격 동작**: `proctor_stream_packs` 에서 `(participant, channel, start_at < to AND end_at > from)` 인 묶음(채널당 최대 3개)을 읽어 12장을 뽑고, 기존 증거 구간 저장과 같은 방식으로 `exam-clips/{sessionId}/{eventId}/{frameId}.jpg` 에 쓰고 `proctor_event_frames` 에 행을 만든다(`source=PC_CAM` 또는 `PHONE_CAM`). 승격분의 보관·연장·삭제는 §6-3.

**콘솔 조회 응답** (기존 `GET /api/console/sessions/{id}/events/{eventId}/clip`, 필드 추가만)
```json
{ "eventId": 12, "status": "READY", "availableAt": null,
  "frames": [ { "id": 301, "source": "PC_CAM", "offsetMs": -8000, "sizeBytes": 14203, "deleted": false } ] }
```
`status`: `READY`(승격 끝) · `PENDING`(`promoteAfter` 전, `availableAt` = ISO 시각, `frames` 는 빈 배열) · `EXPIRED`(상시 저장분도 승격분도 보관 기간이 지났거나 지움) · `NONE`(사진을 만들 수 없음: 서버 추론이 아닌 회차의 이벤트, 감독 중단 이벤트, 묶음 유실). 사진 본문은 기존 `…/clip/{frameId}/image`(그대로).

**검증**: 기존 증거 규칙을 그대로 적용한다 — 1초 간격, 한 장 100KB, 채널당 12장, 대상자당 증거 이벤트 100건. 100건을 넘은 이벤트는 저장은 되지만 사진을 승격하지 않고 `status:"NONE"`.

### 6-3. 보관 기간 (서버 추론 회차만; 서버 추론이 아닌 회차는 기존 규칙 그대로)

| 대상 | 보관 | 연장 |
|---|---|---|
| **상시 저장분**(`proctor_stream_packs`, S3 `exam-stream/…`) | 시험 **종료 후 3일** | **연장 없음 (가정)** — 연장은 의심 구간(승격분)만 길게 두려는 장치라서. 사용자가 상시 저장분 연장을 원하면 결정 필요 |
| **이벤트 구간 승격분**(`proctor_event_frames`)과 이벤트 대표 사진(`exam-snapshots`) | 시험 **종료 후 3일** | **3일 단위**, **최대 2번**(총 9일) **(확정 2026-11-26: 기존 규칙 유지)**, 연장 가능 시점 **삭제 예정 1일 전부터 (확정 2026-11-26; 기존은 2일 전)**. 감독관·매니저·관리자, 종료된 회차만, 회차 단위(기존과 같음) |
| 서버 추론이 꺼진 회차 | 7일 | 7일씩 최대 2번, 삭제 2일 전부터 (**변경 없음**) |

- 삭제 예정 시각 = `회차 종료 + 기본일수 + 연장 횟수 × 연장일수`. 기본일수·연장일수는 **회차의 `server_vision` 에 따라** 정해진다(서버 추론 3·3, 아니면 7·7). 이 플래그는 시험 시작 뒤에 바꿀 수 없으므로(§3-7) 같은 회차의 기준이 중간에 바뀌지 않는다. "회차 종료"는 기존 삭제 배치(`purgeExpiredSnapshots`)가 쓰는 값과 **같은 것**을 쓴다(`ends_at` 인지 `closed_at` 인지 **미확인** — 구현 때 기존 코드와 맞춘다).
- 삭제 배치는 기존 1시간 주기 작업을 확장한다: ① 기존 사진·승격분 ② `proctor_stream_packs`(S3 객체를 지우고 `deleted_at` 기록). 상시 저장분 삭제 기준에는 연장 횟수를 반영하지 않는다.
- 승격은 상시 저장분이 살아 있는 동안에만 된다. 늦게 도착한 이벤트(종료 30분 안)도 마찬가지(종료 3일 안이면 충분).
- `snapshot_retention_extensions.days` 에는 그 연장으로 늘린 일수(서버 추론 3, 아니면 7)를 저장한다.

### 6-4. 휴대폰 사진 (D-21 확정 + 가정 하나)

- **상시 저장한다**(사용자 확정 2026-11-25). 휴대폰 라이브 영상은 응시자·감독관 어디에도 **표시하지 않고, 응시자 미리보기도 하지 않는다**(변경 없음).
- **확정(D-23, 2026-11-26)**: 휴대폰 사진은 **이벤트 구간(앞 8초·뒤 4초)에서 감독관이 사후 사진으로 볼 수 있다**. 그래서 서버 추론 회차의 `proctor_event_frames` 는 `PHONE_CAM` 사진도 받는다(백엔드가 승격할 때만 만든다. 응시자 PC 가 올리는 `/clip` 은 계속 `PHONE_CAM` 을 400 으로 거절). 나중에 열람을 허용하지 않기로 바꾸면: 승격 때 `PHONE_CAM` 채널을 빼고 `proctor_event_frames` 에 휴대폰 행이 없게 하면 된다(상시 저장은 그대로, 접근 불가).
- 감독관은 상시 저장분 전체를 열람하지 못한다. 열람 범위는 ① 이벤트 구간(승격분) ② 감독 중단 구간(§6-5)뿐이다.

### 6-5. 감독 중단 구간 사진 열람 (새 콘솔 API)

감독 중단(`SUPERVISION_PAUSED`) 구간은 AI 판정이 없으므로 감독관이 상시 저장분을 사진으로 직접 볼 수 있어야 한다. 이벤트 구간 사진(`/clip`)과 별도로, **그 대상자의 중단 구간 안에서만** 연다.

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/console/sessions/{id}/participants/{pid}/stream?eventId=&channel=webcam\|phone&from=<ISO>&limit=120` | `eventId` 는 해당 대상자의 `SUPERVISION_PAUSED` 이벤트 번호(필수). 응답 `{eventId, channel, from, to, frames:[{t:"ISO", n:1}], next:"ISO"\|null}`. `frames` 는 `from`(없으면 중단 시작)부터 시간순, 각 항목은 그 초의 사진 1장. `limit` 기본 120, 최대 300. `next` 가 있으면 다음 요청의 `from` 으로 쓴다 |
| GET | `/api/console/sessions/{id}/participants/{pid}/stream/frame?eventId=&channel=&t=<ISO>` | 사진 한 장(image/jpeg, `Cache-Control: no-store`). `t` 는 위 목록의 값 |

- 권한: 감독관·매니저·관리자, 자기 회사 회차만(다른 회사 404). **`eventId` 가 `SUPERVISION_PAUSED` 이고 `from`~`to` 가 그 이벤트의 `startedAt`~`startedAt+durationMs` 안일 때만** 허용(밖이면 403 `OUT_OF_ALLOWED_RANGE`). 중단이 진행 중이면 `to` 는 지금까지.
- 오류: 400 형식, 404 없는 이벤트·대상자, 410 `EXPIRED`(보관 기간이 지남), 403 위와 같음.
- **열람 기록**: 프레임 목록·사진 조회마다 `proctor_stream_access_logs` 에 한 행(누가·언제·대상자·채널·범위·건수). 감독관은 이 기록을 못 지운다.
- 이 API 는 §3-0 적용 조건이 거짓인 회차에서 404.

### 6-6. 기존 계약과 달라지는 점

| 항목 | 현재 | 서버 추론 회차 |
|---|---|---|
| 업로드 주체 | 응시자 PC 가 이벤트 후 올림 | 백엔드가 상시 저장 + 이벤트 때 승격 |

## 7. 손 규칙 구현 (두 손 모두 밖 7초 / 한 손만 밖 10초)

### 7-1. 규칙 정의 **[확인: 의도 문서 / 제안: 해석]**
- "영역" = **키보드 영역 ∪ 마우스 영역**(휴대폰 화면 안에서 검출한 박스).
- 한 프레임에서 각 손의 **"영역 안/밖"** 을 판정:
  - 손 랜드마크 21점 중 **손목·손바닥 중심(랜드마크 0, 9) 또는 손가락 끝 5점 중 과반**이 영역 박스(여유 마진 포함) 안이면 "안".
- 프레임 상태: `둘다밖` / `한손만밖` / `정상(두 손 중 하나라도 안이고, 다른 손도 안이거나 안 보임?)`
- 이벤트: `둘다밖`이 **7초 이상 연속** → `HANDS_OUT`(가칭). `한손만밖`(다른 손은 영역 위)이 **10초 이상 연속** → `HAND_OUT_ONE`(가칭).

### 7-2. 모호한 경우 — 확인 필요 **[미확인/결정 필요 D-5]**
의도 문서에 없는 경계 조건. 구현 전에 정해야 한다.
1. **손이 화면에서 아예 안 보이는 경우**(손 검출 0개)는 "밖"으로 보나? 현재 `hand_missing`은 "손 0개 = 이상"(3초)이었다. 이 설계안은 **"안 보임 = 밖"으로 센다**(카메라 밖은 부정행위 의심 위치이므로). 단 손을 화면 아래(무릎)로 내린 경우와 구분이 안 된다는 점이 한계이다.
2. **한 손만 검출되고 그 손이 영역 위**일 때 (다른 손은 안 보임): "한 손만 밖(안 보임)"으로 볼지 "정상"으로 볼지. 기본안: 안 보이는 손은 "밖"으로 세므로 10초 규칙에 해당한다. **오탐 위험**: 한 손으로 타이핑하는 응시자(다른 손은 턱 괴기 등)가 걸린다. 의도 문서가 "한 손만 밖(다른 손은 키보드나 마우스 위)"이라고 했으니 **의도와 일치**. 오탐률은 §12 측정으로 확인.
3. **타이머 리셋 (결정: 끊김 3초 허용)**: 상태가 `정상`으로 돌아와도 **3초까지는 타이머를 유지**하고, 3초를 넘겨 정상이면 리셋한다(현재 `graceMs: 600`보다 훨씬 길다). 주의: 7초 규칙에서 3초 허용이면 정상으로 3초 돌아왔다 다시 나가는 반복을 계속 "밖"으로 합산하므로 규칙이 매우 너그러워지는 쪽이 아니라 **오히려 엄격해진다**(자주 손을 움직이는 응시자 오탐 가능). §7-4 측정에서 이 값의 오탐을 반드시 확인한다.
4. **상태 전환**: 둘다밖 5초 → 한손만밖으로 바뀐 경우 시간을 합산하나? 기본안: **합산하지 않는다**(각 규칙의 조건이 연속으로 유지될 때만 센다). 단, 둘다밖 → 한손만밖 전환 시 한손만밖 타이머는 0부터.
5. **쿨다운**: 이벤트 후 동일 규칙 재발 최소 간격. 기본안 10초(현재 `cooldownMs` 8~10초와 유사).
6. **(결정) 보정·입장 점검에서 키보드와 마우스 영역에 두 손이 모두 인식되어야만 통과**한다. 한 손뿐이면 통과시키지 않고 "두 손을 키보드·마우스 위에 올려 주세요"를 안내한다(예외 처리 없음). 한 손만 쓸 수밖에 없는 응시자(장애 등)를 어떻게 입장시킬지는 정하지 않았다 → **[미확인, 결정 필요: 감독관 수동 승인 같은 별도 경로가 필요한지]**.

**시간 계산 확정(2026-11-25, 구현 확인 반영)**: 끊김 허용 3초 구간은 타이머에 포함해 흐른다(정상 구간을 빼고 합산하지 않음). 이벤트 `final.durationMs` = 마지막 밖 프레임 − 시작. 쿨다운 10초는 이벤트가 끝난(마지막 밖 프레임) 시점부터. 프레임이 3초 넘게 비면 새로 센다. 상세는 `contract.md` §9.

### 7-3. 구현 방법 **[제안]**

**모델 선택 확정(사용자 결정 2026-11-25, 조건: "그림자 모드 후 재확정")** — 아래 "두 단계"의 후보 서술보다 이 표가 우선한다. 근거 측정은 §8-5·§12-3.

| 대상 | 모델 | 주기 | 시작 기준값(전부 설정으로 조정) |
|---|---|---|---|
| 키보드·마우스·노트(COCO `book`) | **D-FINE-s**(Apache-2.0) | 휴대폰 프레임 매번 | 마우스 0.4 |
| 태블릿·스마트워치·(다른) 휴대폰 | **OWLv2** `google/owlv2-base-patch16-ensemble`(Apache-2.0) | 몇 초마다(시작값 5초) | 태블릿·스마트워치 0.5 |
| 손 | **MediaPipe Hands** | 휴대폰 프레임 매번 | 감지 기준값 0.5, 최대 손 4 |

- **손 규칙 입력**: 7초·10초 규칙은 **점수 상위 2개 손만**으로 판정한다. 가까운 손 중복은 하나로 합친다. **손이 3개 이상**이면 별도 의심 신호로 보고, 몇 초 지속될 때만 이벤트 후보(새 유형 필요 → D-7 에 포함)로 하며 **처음에는 그림자 모드**(기록만, 콘솔 비표시)로 운영한다.
- **제외**: RT-DETR-r18(휴대폰 1/8), Grounding DINO. **YOLO 계열은 AGPL 이라 쓰지 않는다.** 손의 GPU 모델 교체(D-FINE 에 hand 클래스 학습 통합 등)는 **나중 선택지**로만 기록하고 지금은 MediaPipe 를 유지한다.
- **웹캠(얼굴·포즈)**: 이번에 측정하지 않았다. **현재 MediaPipe 얼굴·포즈 유지로 가정, 서버 CPU 부하 [미측정]**.
- **구현 확인 결과(2026-11-26, pAIr-vision `feat/real-models`, 커밋 전, 책상 사진 8장 + 웹캠 사진 10장, 이 PC CPU)**: 손·물체·웹캠 이벤트가 서명된 콜백으로 도착하는 것까지 확인. 실제 발생 확인: `HANDS_OUT` `HAND_OUT_ONE` `TABLET` `NOTE` `SMARTWATCH` `NO_FACE` `HEAD_TURN`. **못 한 것**: `HEAD_DOWN`(숙이면 얼굴을 놓쳐 `NO_FACE` 로 셈), `MULTI_FACE`·`TORSO_*` 는 합성 값 시험만, GPU 에서의 OWLv2 는 미검증(CPU 에서 프레임당 약 3초라 로컬은 OWLv2 주기 30초 설정 사용). 사진이 적어 정확도 **확정 아님**.
- **모델 5개**: D-FINE-s, OWLv2, MediaPipe Hands·Face·Pose(lite). 가중치는 `configs/models.lock`(sha256)으로 검증하고 **시작 시 불일치하면 서버가 시작하지 않는다**.
- **서버 추론의 웹캠 이벤트는 6종**: `NO_FACE` `MULTI_FACE` `HEAD_TURN` `HEAD_DOWN` `TORSO_SHIFT` `TORSO_TURN`(`PC_CAM`). 임계값·지속·쿨다운은 프론트 `pcRules.ts` 와 같다. **`GAZE_AWAY`(시선)는 서버가 만들지 않는다**(사용자 결정, 기본 꺼짐): 웹캠 계약 해상도(400px·q55)에서 시선 값이 640px 대비 절반 이하(±0.3 vs ±0.7)이고 기준값 0.45 를 거의 못 넘으며 정면 `gaze_y` 도 ±0.15~0.3 흔들린다(본인 사진 1명, **확정 수치 아님**). 되살리려면 웹캠 `maxEdge` 640 안팎(대역폭·100KB 한도 검토)과 기준값 재측정이 필요하다. **서버 모드에서는 PC 분석과 달리 시선 이벤트가 없다.**
- **`MANY_HANDS`(손 3개 이상)**: 계약에 없는 유형이라 **그림자 모드**(콜백 없음, 지표 `pair_vision_shadow_events_total`·로그만). 정식 이벤트로 쓰려면 D-7 에 유형 추가. "다른 휴대폰" 검출도 OWLv2 로는 하지만 이벤트 유형이 없어 기록하지 않는다.
- **구현 세션이 임시로 정한 값 — 전부 (가정), 그림자 모드·측정 후 재확정**:

| 항목 | 지속(끊김 허용, 쿨다운) |
|---|---|
| `TABLET` | 10초 (10초, 30초) |
| `NOTE` | 10초 (3초, 30초) |
| `SMARTWATCH` | 15초 (10초, 60초) |
| `MANY_HANDS`(그림자) | 5초 |

  검출 기준값(가정): 키보드 0.3, 마우스 0.4, 노트 0.3, 태블릿·스마트워치·(다른) 휴대폰 0.5, 손 0.5. 손 병합 거리 0.06(프레임 비율). 웹캠: 끊김 허용 2.5초(프론트의 0.4초는 초당 1장에서 무의미), 보정 최소 표본 3장(프론트 5장), 보정 실패 시 오류 대신 재수집. 프론트의 "경고 간격 두 배" 반복은 서버에서 쓰지 않고 같은 `clientId` 갱신으로 대신한다. 얼굴·포즈는 프레임마다 둘 다 돌린다(프론트는 얼굴 3 : 포즈 1). **서버 CPU 부하 [미측정]**.

- **입력 구도 주의**: 흰 여백이 있는 사진에서는 손이 11/16 으로 덜 잡히고 같은 손이 중복됐다. 운영에서 휴대폰 프레임에 **불필요한 여백이 없도록 해상도·구도**를 정한다(§9 거치대 안내).
- 이 선택은 **임시 확정**이다: 그림자 모드(§14-2 D-16) 결과로 재확정한다.

**검출 구성(두 단계)**
1. **키보드·마우스 검출**: 객체 검출 모델. 기존 COCO 학습 모델에 `keyboard`·`mouse`가 이미 있다(COCO 80클래스 중 `keyboard`, `mouse`, `laptop`, `cell phone`, `book`). → **사전학습 모델로 시작**(확정: D-FINE-s, YOLO 계열은 AGPL 이라 제외; 학습 없이 실측 후 부족하면 미세조정). 마우스는 작아서 놓치기 쉽다 → 휴대폰 해상도와 거치대 위치가 중요하다(§9). 한 번 검출하면 **책상 위 위치는 거의 고정**이므로 검출 결과를 **시간 평활(이동 중앙값)** 하고 **정지 상태 박스를 캐시**해 프레임마다 다시 맞추지 않는다(마우스는 움직이므로 마우스만 계속 추적).
2. **손 랜드마크**: MediaPipe Hands 계열(서버에서 실행, 최대 2손). 현재 휴대폰 분석이 이미 MediaPipe 손 검출을 쓴다고 읽었으므로(**[확인: `phoneAnalysis.ts`·`phoneBackend.ts` 구조상 손·객체 분석 존재, 상세 모델 이름은 읽지 않음 — 구현 때 확인**) 같은 계열을 서버로 옮기면 정확도 기준선을 이어받는다. 서버 GPU에서 돌리는 방법(MediaPipe GPU 또는 ONNX/RTMPose 대체)은 **D-6** (MediaPipe는 서버 GPU 지원이 제한적이라 **측정 후 선택**).
3. **판정**: 위 7-1 규칙. 프레임 → 상태 → 지속시간 카운터(`RuleEngine`과 같은 `durationMs`/`cooldownMs`/`graceMs` 구조를 Python으로 포팅). 규칙 값은 **설정 파일**로 빼서 배포 없이 조정(프로필·`thresholdsVersion` 개념 유지).

**왜 하나의 모델이 아니라 두 단계인가**: 키보드·마우스는 정적 물체라 "영역" 정의가 쉽고, 손은 랜드마크 정밀도가 필요하다. 분리하면 각각 교체·평가가 쉽다.

**보정 단계(휴대폰)**: 입장 점검(§9)에서 키보드·마우스·두 손이 모두 인식된 순간의 박스를 **기준 영역**으로 저장. 시험 중 거치대가 밀려 박스가 크게 벗어나면 "휴대폰 위치 변경" 신호를 낸다(이벤트 후보 `PHONE_MOVED`, 새 유형이므로 **D-7**).

### 7-4. 평가
- 정답이 있는 영상으로 평가한다: 규칙 판정(두 손 밖/한 손 밖)의 **이벤트 단위 재현율·오탐**. 데이터는 §8-3(수집)과 같은 촬영에서 얻는다. 정확도 목표 수치는 아직 없음(의도 문서) → **측정 후 결정**.

## 8. 태블릿·메모·스마트워치 탐지: 직접 학습 vs open-vocab 비교 계획

### 8-1. 두 방식 **[제안]**
| 구분 | A. 직접 학습 | B. open-vocab (문장 기반) |
|---|---|---|
| 개요 | 객체 검출기(후보였던 YOLO 계열은 AGPL 이라 제외, D-FINE 등 Apache-2.0 모델)를 `tablet`·`note(paper)`·`smartwatch`(필요하면 `phone`)로 **미세조정** | 문장으로 클래스를 지정하는 검출기(예: Grounding DINO, OWL-ViT/OWLv2, YOLO-World 계열)에 `"a tablet"`, `"handwritten notes"`, `"a smartwatch on wrist"` 같은 프롬프트를 준다 |
| 장점 | 빠름(실시간), 작은 모델, 우리 환경 특화로 정확 | 학습 데이터 없이 시작, 클래스 추가가 문장 수정으로 끝남 |
| 단점 | **데이터·라벨링 비용**, 새 물체마다 재학습 | **느림·무거움**, 오탐 많음(손목시계·메모 같은 작은 물체), 프롬프트 민감 |
| 예상 운영 | 상시 실행 | 상시 어려우면 **트리거 방식**(손 규칙 이벤트 후보, 또는 N초마다 한 번)으로 호출 |

> 모델·라이선스·성능 수치는 **[미확인]**. 위 모델 이름은 후보이며, 실제 선정은 §8-4 평가로 한다. 상업 이용 라이선스를 반드시 확인한다(특히 학습 가중치).

### 8-2. 이벤트 유형 추가 **[제안]**
`TABLET`, `NOTE`(또는 `PAPER`), `SMARTWATCH`(휴대폰 기준 `PHONE_CAM` 만, 확정 2026-11-26)를 `ProctorEvent.Type`에 추가(유형 코드표 `proctor_event_types` 마이그레이션 필요, 심각도 지정). 사용자가 보는 문장은 "태블릿이 감지되었습니다" 식. 자동 확정 없음(감독관이 판단).

### 8-3. 학습 데이터 확보 **[제안]**
1. **시작은 모델 없이 라벨 없는 수집이 아니라 "의도된 촬영"**: 사내 인원이 시험 환경(책상·거치대 위치·조명 3가지·노트북/데스크톱·키보드 종류)을 재현해 **휴대폰 거치대 시점**으로 촬영한다. 항목: ① 정상(양손 타이핑·마우스) ② 태블릿 놓기 ③ 메모지·포스트잇·책 ④ 스마트워치 착용(손목 보임/소매에 가림) ⑤ 간섭(컵·휴대폰·리모컨·손목시계처럼 오탐 유발 물체). 한 영상 1~2분, 초당 1~2장 추출.
2. **공개 데이터셋 보강**(라이선스 확인 후): 객체 검출 일반 데이터셋의 `tablet`·`book`·`watch` 관련 클래스. 시험 책상 시점과 도메인이 달라 보조용.
3. **합성**: 책상 배경 위에 물체 이미지 붙이기(copy-paste augmentation). 실데이터 부족할 때 보조.
4. **라벨링**: 자동 사전 라벨(B 방식 open-vocab 결과)을 **사람이 검수**해 정답으로 만든다 → B가 A의 데이터 확보 도구도 된다. 도구는 Label Studio 등 **[미확인: 팀 선택]**.
5. **규모 목표(제안)**: 클래스당 사진 최소 수백 장(최소 300~500) × 환경 변형 + 정상 부정 샘플 비슷한 양. 이 수는 출발점이며 평가 결과로 늘린다.
6. **개인정보**: 촬영 대상은 **동의한 사내 인원**만. 얼굴이 나온 데이터는 학습 후 보관 기간·접근 권한을 정한다(**D-8**). **실제 응시자 사진을 학습에 쓰지 않는다**(동의 문구에 없는 목적. 쓰려면 문구·동의가 필요 → 이 설계에서는 제외).
7. 실제 시험 데이터로 **측정**만 하는 것(의도 문서: "시험 데이터로 먼저 측정한 뒤 목표를 정한다")은, 확정/기각된 이벤트 사진을 **평가 용도로만** 사용하는 것이 동의 범위 안인지 법무 확인 필요(**D-8**).

### 8-4. 비교 평가 계획 **[제안]**
- **평가 세트**: 위 촬영본 중 **학습에 쓰지 않은 사람·환경**으로 구성(사람·환경 단위 분리, 같은 영상 프레임이 학습·평가에 섞이지 않게).
- **지표**: 클래스별 재현율·정밀도(이벤트 단위: "N초 이상 보임"이 정답일 때 이벤트가 났는가), **프레임당 지연·GPU 메모리**, **30명 동시 처리 가능 여부**, 오탐 건수/시간(정상 영상 기준).
- **비교 조건**: 같은 평가 세트, 같은 GPU, 같은 해상도(휴대폰 512px와 1280px 둘 다).
- **결과 해석**: 정확도 목표 수치는 이 결과를 보고 사용자가 정한다(의도 문서). **통과 기준을 미리 만들지 않는다**(A·B 모두 측정 후).
- **운영 방식 후보**: A가 충분하면 A 상시. A가 부족하고 B가 느리면 B는 손 규칙 이벤트 후보나 N초 주기 샘플링에만 쓰는 **2단계 구조**(§5의 워커에서 분리 실행).
- **일정**: [미확인] 일정은 의도 문서에도 미정.

## 9. 입장 점검 (휴대폰 영상 없이)

### 9-1. 원칙
휴대폰 영상은 응시자에게도 보이지 않는다. 대신 **서버가 판정한 결과 체크리스트**만 보여 준다. 판정값은 불리언·짧은 문자열뿐이며(기존 `phone-status`가 `scalarsOnly`로 그렇게 걸러 전달하는 방식과 같은 원칙) 사진을 돌려주지 않는다.

### 9-2. 점검 흐름 **[제안]**
1. 응시자가 QR로 휴대폰을 연결하고 거치대에 세운다(미리보기 없이 카메라만 켠다).
2. PC 화면에 체크리스트가 실시간 갱신된다:
   - ☐ 키보드 인식됨 ☐ 마우스 인식됨 ☐ 왼손 인식됨 ☐ 오른손 인식됨 ☐ 책상 전체가 보임
   - 각 항목이 인식되면 체크. 실패 항목은 **구체적인 조치 문장**을 보여 준다: "키보드가 보이지 않습니다. 휴대폰을 키보드가 화면 안에 들어오도록 조금 뒤로 옮겨 주세요."
3. "두 손 인식됨"은 **응시자가 화면 안내에 따라 두 손을 키보드 위에 올리면** 판정(응시자는 PC 화면의 안내 문구만 보고 따라 한다).
4. 모든 항목이 연속 N초(예: 3초) 유지되면 점검 통과 → 기준 영역 저장(§7-3).
5. **방향 안내**: "휴대폰을 어느 쪽으로 향해야 하는지"를 영상 없이 알리려면 **위치 힌트**(예: "키보드가 화면의 왼쪽에 치우쳐 있습니다")를 서버가 방향 판정 결과로 돌려준다. 상세는 **D-9**.

### 9-3. 같이 점검할 것
- **업로드 대역폭·지연**: 시험 직전에 실제 프레임을 보내 보며 "왕복 지연 p95", "초당 보낼 수 있는 장수"를 측정해 사용 가능 여부를 알려 준다. 기준은 §11 측정 후.
- **추론 서버 상태**: `/readyz` 기준으로 서버가 준비 안 됨이면 입장 단계에서 "감독 시스템 준비 중"을 보이고, 감독이 필수인지/예외로 입장을 허용할지는 **D-10**(서버가 죽어도 시험은 계속한다는 원칙과 일관되게, 기본안은 **입장은 허용하고 감독 중단으로 기록**).

## 10. 장애 처리와 운영

### 10-1. "감독 중단" 이벤트 **[제안]**
- 새 이벤트 유형 `SUPERVISION_PAUSED`(`source=SERVER`, 사진 없음). 시작·끝 시각을 갖고 **구간 이벤트**로 저장(시작 시 `durationMs` 0으로 만들고 복구 시 갱신하거나, 복구 시 한 번에 기록). 감독관 콘솔 타임라인에 "이 시간 동안 AI 감독이 중단되었음"으로 표시, **확정/기각 대상이 아니다**(정보용, 브라우저 이벤트와 같은 취급).
- 판정 기준: 백엔드가 응시자별로 **마지막 판정 수신 시각**을 보고, 일정 시간(예: 프레임이 계속 오는데 판정이 N초 없음) 또는 추론 서버 `/readyz` 실패가 연속 M회면 중단으로 본다. N·M은 **[미확인, 실측 후]**.
- 응시자가 PC·휴대폰 연결을 잃은 경우(프레임이 안 옴)는 기존 `CONNECTION_LOST`·`PHONE_DISCONNECTED`와 **구분**한다(원인이 응시자 쪽 vs 서버 쪽).
- **감독 중단 구간의 웹캠·휴대폰 사진은 상시 저장되어 있다.** 감독관이 그 구간을 사진으로 직접 확인할 수 있게 콘솔에서 연다(API는 §6-5, 콘솔 화면에 "이 구간 사진 보기" 추가, 새 UI 필요).
- 복구되면 종료 시각을 기록하고 보정을 다시 한다.

### 10-2. 안 죽게 하는 운영 **[제안]**
| 항목 | 방법 |
|---|---|
| 최신 프레임만 | 큐 길이 1(§5). 처리 못하면 **쌓지 않고 버림**. 버림률이 임계(예: 30% 이상 1분) 넘으면 경고 지표 + 백엔드에 `rate` 하향 요청 |
| 대수 (결정: **1대 고정**, 부하가 많으면 2대로 증설) | 처음에는 1대로 운영한다. 그래서 **1대가 죽으면 그 시간 전체가 감독 중단**이다(§10-1). 증설을 쉽게 하려고 설계는 2대 이상을 전제로 둔다: 응시자는 `sessionKey` 해시로 한 대에 고정 배정, 인스턴스 목록은 설정으로 받고, 백엔드는 목록 길이 1이어도 같은 코드로 동작. 증설 판단 기준은 아래 Grafana 지표(프레임 폐기율·분석 지연·GPU 사용률)로 정한다(M5 측정에서 기준값 확정) |
| 모니터링 (Grafana) | 추론 서버 `/metrics`(Prometheus 형식)를 수집해 Grafana 대시보드로 본다. 최소 패널: 동시 세션 수, 스트림당 분석 fps, 프레임 폐기율, 분석 지연 p50/p95, GPU 사용률·메모리, 이벤트 수, 감독 중단 시간, 업로드 실패. 시험 시간대에만 수집(서버가 꺼져 있으면 "서버 꺼짐"과 "장애"를 구분하는 표시 필요). Prometheus·Grafana를 어디서 돌릴지(별도 서버·Grafana Cloud 등)는 **[미확인, 결정 필요]** |
| 상태 확인 | `/healthz`(프로세스), `/readyz`(모델·GPU·여유). 백엔드가 5초마다 호출. 연속 3회 실패 → 해당 인스턴스 제외 |
| 자동 재시작 | 컨테이너 프로세스 감시(예: supervisord 또는 RunPod 재시작 정책, **[미확인: RunPod 기능 확인 필요]**). OOM·GPU 오류 시 프로세스가 스스로 종료하고 재시작되게 작성 |
| 과부하 보호 | 최대 동시 세션 상한 초과 요청은 **거절**(503)하고 백엔드가 다른 대로 보냄. 새 세션만 막고 기존 세션은 유지 |
| 무중단 교체 | `drain` 후 교체 |
| 알림 | 감독 중단이 시작되면 운영 담당에게 알림(채널은 **[미확인]**). 시험 시간대에만 |

### 10-3. 백엔드 장애 시
추론 서버가 아니라 **백엔드가 죽으면** 기존 시험 자체가 영향받으므로 기존 대응과 같다(이 설계 범위 밖). 단 백엔드 재시작 후 WebSocket 재연결이 자동으로 되어야 한다(프론트 `RelaySocket`의 재연결 로직 재사용).

## 11. RunPod 운영 절차 (시험 시간에만 켠다)

> RunPod 제품 사양·요금·GPU 확보 정책은 **[미확인]**이다. 아래는 절차 설계이며, 구체 수치는 계정·리전에서 확인한다. **Pod 종류**(Secure/Community, 온디맨드/Spot, Serverless)는 **D-12**.

### 11-1. 절차 **[제안]**
| 시점 | 할 일 | 담당 |
|---|---|---|
| 시험 일정 확정 시 | 시험 시작·종료 시각을 백엔드가 알고 있음(`exam_sessions`) | 자동 |
| **시험 1일 전** | 운영자가 "이 일정에 GPU를 쓴다"를 확인, 필요 GPU 수 점검 | 사람 |
| **시험 30분 전**(기본안) | 추론 서버 Pod 기동(API 또는 콘솔). 모델 적재·워밍업 | 스크립트 + 사람 확인 |
| 기동 후 | `/readyz` 통과 확인, 샘플 프레임으로 **스모크 테스트**(가짜 응시자 1명) | 스크립트 |
| 시험 시작 15분 전 | 백엔드가 추론 서버 상태를 감시하기 시작, 입장 허용 | 자동 |
| 이상 시(기동 실패·GPU 없음) | **백업 계획**: 다른 리전/다른 GPU 종류 시도, 안 되면 감독 없이 진행하고 모든 구간을 "감독 중단"으로 기록하고 담당자에게 알림 | 사람 |
| 시험 종료 후 | 남은 이벤트 업로드 확인 → `drain` → Pod **종료**. 종료 시각 = 시험 종료 + 30분(늦게 오는 이벤트 유예 `LATE_GRACE`와 맞춤) | 스크립트 |
| 여러 회차가 가까울 때 | 간격이 짧으면(예: 1시간 이내) 끄지 않고 유지 | 사람 판단 |

### 11-2. 자동화 **[제안]**
- 백엔드 스케줄러(`ExamSchedulerService` 같은 곳)가 시험 시각 30분 전에 **RunPod API로 Pod 기동**을 호출(키는 환경 변수, **[미확인: RunPod API 사용 가능 여부]**). 첫 단계는 **수동 절차 + 체크리스트**로 시작하고, 안정되면 자동화(**D-13**).
- 모델 가중치는 **네트워크 볼륨 또는 컨테이너 이미지**에 둬 기동 시 다운로드 지연을 줄인다. 기동 시간 실측 필요(**[미확인]**).
- 비용 방어: 종료 누락 방지를 위해 **최대 가동 시간 타임아웃**(예: 시험 종료 + 2시간)을 Pod에 설정.

### 11-3. GPU 확보 실패 위험 대응
- 30분 전 기동은 확보 실패를 알아차릴 여유를 위한 것. **기동 확인 데드라인**(예: 시험 10분 전)까지 실패하면 비상 절차로 전환.
- 2대 운용이 비싸면 **1대 + 예비 1대(필요 시만 켬)** 도 가능하지만 확보 실패 위험이 커진다 → D-11에서 비용과 함께 결정.

## 12. 용량 산정과 측정 계획 (30명 동시)

### 12-1. 가정 (모두 **[미확인]** — 실측으로 확정)
- 응시자 30명 = 웹캠 30스트림 + 휴대폰 30스트림 = **60스트림**.
- 전송 사진: 웹캠 크기·간격은 **실측 필요**(현재 코드에 있는 값은 증거 링용 400px/0.55/1초뿐이고, 분석용 전송 크기는 아직 없다). 휴대폰은 문서의 실측값(장당 13~15KB, 2fps, 갤럭시 0.21Mbps·아이폰 0.35Mbps)을 출발점으로 한다.

### 12-2. 대역폭 추정(출발점) **[제안]**
- 웹캠을 휴대폰과 같은 규모(15KB·2fps = 약 30KB/s = 0.24Mbps)로 가정하면 응시자 1명 합 ≈ 0.5Mbps, **30명 ≈ 15Mbps(백엔드 입력) + 같은 양이 백엔드→추론 서버**.
- 백엔드는 입력 15Mbps + 출력 15Mbps. 서버 NIC·인스턴스 한도는 **[미확인]**.
- 시간당 데이터: 30명 × 0.5Mbps × 3600초 ≈ 6.75GB/시간(한 방향). 2시간 시험 약 13.5GB, 백엔드→추론 포함 두 배. 클라우드 전송 요금은 **[미확인]**.

### 12-3. GPU·CPU 용량 **[미확인 — 측정으로]**
병목 후보: ① JPEG 디코드(CPU), ② 검출·랜드마크 추론(GPU), ③ 규칙 엔진(미미). 60스트림 × 2fps = **120프레임/초**. 한 프레임에 필요한 모델 호출은 웹캠(얼굴·포즈) + 휴대폰(객체 검출 + 손). 모델별 처리량(장/초/GPU)은 측정 전에는 알 수 없다. **최신 프레임만 처리하므로 처리량이 모자라면 응시자당 실제 분석 fps가 내려갈 뿐 쌓이지는 않는다**(안전하게 열화).
- 측정 후 **분석 fps 하한**을 정한다: 가장 짧은 규칙이 1~2초 단위이므로 응시자당 분석 1fps 이상이면 규칙이 성립한다(현재 PC 분석은 초당 10회까지, 저사양 3.7회). 하한은 **D-14**.

**첫 측정값(2026-11-25, 한 장씩 순서대로)**: §8-5 표. **동시 처리량(여러 응시자 동시, 배치)은 [미측정]**이다. 아래는 **단순 추정**이다(측정이 아님).
- 응시자 1명당 GPU 시간: D-FINE-s 97.5ms × 1fps + OWLv2 154.8ms ÷ 5초 ≈ **약 130ms/초**.
- 30명이면 약 3.9초/초 → **한 줄 처리로는 부족**하다. 병렬·배치(§5)가 필요하고 배치 효과는 측정 전이다.
- 손 검출(MediaPipe, Pod CPU 77.3ms)을 30명이 1fps 로 하면 초당 약 2.3 CPU초. **Pod 코어 수는 [미확인]**이라 가능 여부를 말할 수 없다.
- 웹캠 얼굴·포즈 CPU 부하는 **[미측정]**.

### 12-4. 측정 계획 **[제안]**
| 단계 | 내용 | 얻는 값 |
|---|---|---|
| M1 | 실제 웹캠(노트북 3종·USB캠)으로 해상도(320/400/480/640)·품질(0.5~0.7)별 JPEG 크기, 얼굴·어깨 검출 정확도 | **웹캠 전송 크기·권장 해상도** (현재 400px/0.55 기준이 분석에도 충분한지) |
| M2 | 간격(0.5/1/2fps)별로 기존 규칙(최단 1초 `multi_face`)이 놓치는지 | **웹캠 전송 간격** |
| M3 | 실제 갤럭시·아이폰으로 휴대폰 장당 크기·프레임 간격(기존 문서의 §7-5 항목 1) | 휴대폰 크기 |
| M4 | 후보 GPU 1종(RunPod에서 시간 단위 임대)에서 모델별 처리량·GPU 메모리 | **GPU 1장당 스트림 수** |
| M5 | 가짜 클라이언트 60스트림 부하 시험(실제 JPEG 재생): 서버 CPU·GPU·지연 p95·프레임 폐기율 | **30명 가능 여부, 여유율** |
| M6 | 백엔드 `/ws/vision` 경유 부하(연결 60 + 이벤트 폭주) | 백엔드 영향 |
| M7 | 장애 훈련: 추론 서버 강제 종료·네트워크 차단, 감독 중단 기록·복구 확인 | 운영 절차 검증 |
| 합격 기준(제안) | 서버 CPU·GPU 사용률 70% 이하, 분석 지연 p95 1초 이하, 프레임 폐기율 5% 이하(기존 §7-5 기준 재사용) | |

> 합격 기준 수치는 기존 휴대폰 중계 부하 시험(§7-5-3)과 같은 값을 **임시로 차용**했다. 이 서비스에 맞는 값인지는 측정 후 사용자가 정한다.

### 12-5. 상시 저장 용량 **[추정, 실측 전]** (2026-11-25 개정: 웹캠·휴대폰 모두 저장)
- 웹캠·휴대폰 각 초당 1장, 한 장 15~20KB 가정: 스트림 하나 2시간 약 108~144MB. **30명 × 2채널 = 60스트림 약 6.5~8.6GB**(웹캠만이던 이전 추정 3.3~4.3GB의 두 배). 초당 2장이면 두 배, 프레임별(초당 30장)은 비현실적이라 채택하지 않는다. 3일 보관이므로 같은 시간대 회차가 겹치지 않으면 동시에 쌓이는 양은 회차 하나 분량.
- 백엔드→S3 업로드 대역폭: 스트림당 약 15~20KB/s, 60스트림 약 0.9~1.2MB/s(약 7~10Mbps). 백엔드가 추론 서버로 보내는 양(§12-2)과 **별개로 더해진다**. 백엔드 서버 한도는 **[미확인]**.
- S3 요청 수: 10초 묶음이면 스트림당 시간당 360회, 60스트림·2시간 약 4.3만 PUT. DB `proctor_stream_packs` 행도 약 4.3만. 비용은 미미할 것으로 보이나 **[미확인]**.
- 승격 복사(이벤트당 최대 24장)와 삭제 배치 부하: 이벤트 수에 비례(작음). 상시 저장분 삭제는 묶음 단위로 지운다.
- 이벤트 구간 승격분: 대상자당 최대 100건 × 24장 × 20KB ≈ 48MB(최악), 3일 보관 + 연장.

## 13. 동의 문구 v3 초안 **[제안 — 국외 이전은 동의 문구로 고지하고 진행(사용자 결정). 실응시자 파일럿 전 법무 확인 1회 권장]**

현재 v2 문구(`Entry.tsx`)는 "영상은 이 브라우저 안에서만 분석하며 …"이다. 이 문장은 서버 추론에서 **거짓이 되므로 반드시 바꿔야 한다.** 서버 추론 회차는 `CONSENT_VERSION='v3'`, 서버 추론이 꺼진 회차는 **v2 문구 그대로**(문구·보관 7일·연장 21일 안내 변경 없음)다. 상시 저장이라 "이상 없는 사진은 폐기"라는 문장도 쓸 수 없다.
`[대괄호]` 는 사용자 확정 전의 **가정** 또는 RunPod 리전 확정 후 채울 값이다.

> **[필수] 카메라 감독 동의 (v3)**
>
> **1. 무엇을 보내나.** 시험 중 노트북 웹캠과 휴대폰 카메라의 **사진(영상이 아닌 정지 사진)이 서버로 전송**되어, AI가 부정행위 의심 상황(얼굴·시선·자세, 손의 위치, 책상 위 물체)을 분석합니다. 이용 목적은 부정행위 분석입니다.
>
> **2. 국외 이전.** 이 분석은 **대한민국 밖에 있는 서버(업체: RunPod, 위치: [리전 확정 후 기재: 예 일본])에서 처리**됩니다. 전송되는 정보는 웹캠·휴대폰 사진입니다.
>
> **3. 저장과 삭제.** 노트북 웹캠과 휴대폰 카메라의 사진은 **시험 중 초당 1장씩 저장**되며, **시험 종료 3일 뒤 삭제**됩니다. AI가 이상을 감지한 구간(감지 시점 앞 8초·뒤 4초의 웹캠·휴대폰 사진, 최대 24장)은 부정행위 검토 목적으로 별도 보관되어 기업 담당자에게 제공되며, **시험 종료 3일 뒤 삭제**됩니다. 기업 담당자는 삭제 1일 전부터 **3일씩 최대 2번** 보관을 연장할 수 있어 **최대 9일까지** 보관될 수 있습니다.
>
> **4. 누가 보나.** 휴대폰 카메라의 **실시간 영상은 화면에 표시되지 않으며**(응시자에게도, 기업 담당자에게도) AI 분석에만 사용됩니다. 다만 AI가 이상을 감지한 구간과 AI 감독이 중단된 구간의 휴대폰 사진은 기업 담당자가 **사진으로 검토**할 수 있습니다. 그 밖의 시간대 사진은 기업 담당자가 열람하지 않으며 위 기간이 지나면 삭제됩니다.
>
> **5. 판단은 사람이.** AI의 분석 결과는 참고 자료일 뿐이며 부정행위 여부는 담당자가 사진을 직접 확인하여 판단합니다. 얼굴로 신원을 식별하지 않습니다.
>
> **6. 서버 장애.** 서버 장애 등으로 AI 분석이 중단되는 경우 시험은 계속 진행되며, 그 구간은 감독 중단으로 기록됩니다. 이 구간의 사진도 위와 같이 저장되며 담당자가 확인할 수 있습니다.

바뀐 점(이전 초안 대비): ① 휴대폰 사진도 초당 1장 저장 ② 상시 저장·이벤트 구간 모두 **3일** 보관(이전: 이벤트 구간 7일·최대 21일) ③ 연장 단위 3일 ④ 감독 중단 구간도 열람 ⑤ 휴대폰 "이벤트 순간 1장만 제공" 문장 삭제.

확인할 것:
- 위 문구는 **국외 이전 고지에 필요한 항목**(이전되는 국가, 받는 자, 이용 목적, 보관 기간)을 담으려 했으나, 이것만으로 법적 요건이 충족되는지는 **확정하지 못했다.** 실응시자 파일럿 전에 담당자에게 문구를 한 번 보여 준다(사내 테스트는 막지 않는다).
- 연장 횟수 2번·시작 삭제 1일 전·최대 9일은 2026-11-26 **확정**이다(대괄호 제거). 값이 바뀌면 3번 문단만 고친다. 연장 횟수·시작 시점·일수는 화면에서 하드코딩하지 말고 `GET …/retention` 응답을 쓴다(§3-7).
- 휴대폰 사진 열람(4번 문단)은 D-23 으로 확정됐다. 열람을 허용하지 않기로 바꾸면 4번 문단의 "다만 …" 문장을 지우고 승격에서 휴대폰 채널을 뺀다(§6-4).
- 문구의 업체명·국가는 RunPod 리전을 정한 뒤 채운다(한국 리전은 확인되지 않았고, 일본 `AP-JP-1` 후보. 리전 목록은 콘솔·API에서 확인 **[미확인]**).
- 이미 v2에 동의한 응시자: v3 문구 적용은 **새 회차 입장부터**. 진행 중 회차는 스위치를 켜지 않는다(회차별 스위치, §14). 서버가 `consent_version='v3'` 인지 확인한다(`/ws/vision` 4403 `CONSENT_REQUIRED`).
- 학습 목적 미사용을 문구에 명시할지(§8-3의 "실제 응시자 사진 학습 제외") — D-8.
- RunPod 약관의 데이터 처리 조항(학습 미사용, 보관, 삭제)은 **[미확인]**이라 문구에 쓰기 전에 확인한다.

## 14. 배포 전략과 롤백 **[제안]**

### 14-1. 스위치
| 스위치 | 위치 | 기본 |
|---|---|---|
| `SERVER_VISION_ENABLED` | 프론트(`VITE_`) + 백엔드(`PAIR_`) | **꺼짐** |
| 회차 단위 플래그(예: `exam_sessions.server_vision`) | DB(마이그레이션 필요) | 꺼짐 |
| `PHONE_CAM_ENABLED` | 프론트 | 꺼짐(서버 모드에서는 서버 모드 휴대폰 경로가 대신 쓰임 — 두 스위치 관계는 구현 때 명확히 한다) |

- **전부 꺼진 채 배포**: 새 코드는 들어가지만 기존 `/ws/proctor`·PC 분석 경로가 그대로 동작. 기존 API는 필드 **추가만** 하고 제거·이름 변경을 하지 않는다(재배포 호환).
- 스위치 단위를 **회차별**로 두면 한 회차씩 켤 수 있다(전체 일괄 켜기보다 안전).

### 14-2. 단계
1. **로컬**: 추론 서버를 로컬 GPU/CPU 모드로 띄우고(`docker compose`) 백엔드·프론트 `feat/server-vision` 브랜치로 종단 시험. 가짜 웹캠(동영상 재생)으로 규칙·이벤트·사진 저장 확인.
2. **통합**: 백엔드 `develop`(PR), 프론트 `main` merge — 스위치 꺼짐 상태. 기존 시험에 영향 없음 확인(CI·Playwright). 문서는 `main`에 바로(브랜치 전략 기록 기준).
3. **테스트 회차**: 사내 인원이 참여하는 테스트 회차에서만 스위치 켜고 RunPod 실가동(§11 절차 리허설 포함), M5·M7 수행.
4. **파일럿**: 실제 응시자 소규모 회차 1~2개(동의 v3 적용, 법무 확인 후). 이 회차는 PC 분석 결과를 **병행 기록하지 않는다**(폴백 없음 원칙). 단 **비교 평가용 그림자 모드**(서버 결과만 기록, PC 분석 결과도 기록해서 오탐 비교)는 파일럿 전 사내 시험에서만 쓴다 — 응시자 PC 부하가 늘어서 실응시자에게는 쓰지 않는다. **D-16**.
5. **확대**: 문제 없으면 회차 단위로 켜는 범위를 넓힌다.

### 14-3. 롤백
- **즉시 롤백 = 스위치를 끈다**(백엔드 환경 변수 + 새 회차에 적용, 진행 중 회차는 **그 회차가 끝날 때까지 서버 모드 유지**가 안전한지, 아니면 PC 분석으로 즉시 전환할지는 **D-17**). 진행 중 전환은 보정이 다시 필요한 문제가 있어 기본안은 "새 입장부터 적용".
- 코드 롤백: 브랜치 단위로 되돌린다. 마이그레이션은 **추가만**(컬럼·유형 추가, 삭제 없음)이므로 코드를 되돌려도 DB와 호환된다. 새 이벤트 유형이 저장된 뒤 코드를 되돌리면 옛 코드가 알 수 없는 유형을 만난다 → 콘솔이 모르는 유형을 안전하게 표시하도록 **먼저** 프론트·백엔드를 방어적으로 고친 뒤 새 유형을 쓰기 시작한다.
- 롤백 기준(제안): 파일럿 중 ① 감독 중단 비율이 시험 시간의 N% 초과 ② 오탐 건수가 기준 초과 ③ 응시자 입장 실패율 증가 — 수치는 **[미확인, 사용자 결정]**.

## 16. 위험과 한계

- **응시자 PC가 사진을 조작·차단할 수 있다**: 서버 분석으로 옮겨도 "PC가 가짜 사진을 보내는" 공격(가상 카메라, 녹화 영상 재생)은 막지 못한다. 분석 위치만 옮겼을 뿐이다. 완화: 사진에 시간 변화·움직임 일관성 검사, 가상 카메라 장치명 점검(기존 환경 점검 확인 필요 **[미확인]**). 완전한 방어는 아니다.
- **휴대폰 라이브 영상 비표시**: 입장 점검은 판정 결과만 보여 준다(§9). 증거 사진은 상시 저장으로 보강됐다(D-4 해소).
- **GPU 확보 실패·단일 장애**(§11, §10).
- **국외 이전·개인정보**(§13).
- **한 손 규칙 오탐**(타이핑 중 한 손 휴식 자세 등): 측정 전까지 정확도 미지수(§7-4).
- **상시 저장은 개인정보 보관량을 늘린다**: 이상 없는 웹캠·휴대폰 사진도 시험 종료 후 3일 저장된다(휴대폰은 책상·방 안이 찍힌다). 접근 권한(감독관은 이벤트 구간 또는 감독 중단 구간만, §6-5), 열람 기록(`proctor_stream_access_logs`), 삭제 누락 점검이 필요하다.
- **백엔드가 죽으면 최대 10초분 사진을 잃는다**(메모리 묶음, §6-1).
- **대역폭 비용**(§12).
- **모델 라이선스**(§15-2).
- **복잡도 증가**: 추론 서버·RunPod 운영·백엔드 경유 3중 구조. 운영 인력·절차가 필요하다.

#### 17-0-1. 법무 항목 (사용자 결정: 동의 문구로 진행)
이 설계는 법적 판단을 하지 않는다. 동의 문구로 진행하되, 실응시자 파일럿 전에 **법무·개인정보 담당자에게 아래를 한 번 묻기를 권한다.** 질문 목록만 정리한다.
1. 응시자 사진을 해외 사업자(RunPod, 리전 미확인) 서버에서 처리하는 것이 개인정보 국외 이전에 해당하는가. 해당하면 고지·동의 항목과 위탁 계약이 필요한가.
2. 동의 문구 v3 초안(§13)이 사진 전송·AI 분석·웹캠·휴대폰 사진 상시 저장(3일)·이벤트 구간 보관과 연장을 충분히 알리는가.
3. 확정/기각된 이벤트 사진을 모델 평가·학습에 쓸 수 있는가(동의 범위 밖이면 쓰지 않는다. 설계는 쓰지 않는 쪽을 기본으로 한다).
4. 국내 리전에서 처리할 수 있는 대안(국내 GPU 사업자)이 필요한가. 필요하면 RunPod 대신 다른 선택지가 §11을 바꾼다.
**기술팀이 먼저 확인할 수 있는 것**: RunPod 리전 선택지와 데이터가 저장·경유하는 위치(공식 문서 확인), 사업자 약관의 데이터 처리 조항.

### 17-3. 문서에 없는 가정 (이 설계가 깔고 있는 것)
1. 기존 PC 분석 코드는 지우지 않고 스위치 뒤에 남긴다(롤백용).
2. 서버 추론 회차의 보관은 상시 저장분·이벤트 구간 모두 3일, 이벤트 구간 연장은 3일 단위(횟수 최대 2번·시작 "삭제 1일 전" 확정 2026-11-26; 상시 저장분 연장은 미정). 서버 추론이 꺼진 회차는 기존(7일, 최대 21일)을 그대로 쓴다.
3. 확정/기각은 사람이 하며, 새 이벤트 유형도 자동 확정하지 않는다.
4. 추론 서버는 응시자 신원·이름을 모른다(불투명 키만).
5. 규칙 값(지속시간 등)은 설정 파일로 둔다.
6. 정확도 목표 수치는 측정 뒤에 정한다(의도 문서와 동일).
7. 시험 시간대에만 서버를 켠다(회차 종료 + 30분 유예까지).

### 17-4. 미확인 (추측하지 않음)
- 웹캠 사진의 실제 전송 크기·간격(분석용), 휴대폰 실기기 크기(기존 §7-5도 미확인).
- 국외 이전 고지만으로 법적 요건이 충족되는지, RunPod 약관의 데이터 처리 조항, RunPod 한국 리전 유무(검색에서는 확인되지 않음).
- 상시 저장 S3 요청 비용, 10초 묶음의 적정 길이, 백엔드 서버가 초당 60장 입력·저장을 감당하는지, "회차 종료"(삭제 기준)가 `ends_at` 인지 `closed_at` 인지.
- GPU 1장당 처리 가능한 스트림 수, 모델별 처리량, 적정 GPU 종류.
- RunPod: 기동 API·자동 재시작·IP 제한 지원 여부, 기동 소요 시간, 요금, GPU 확보 정책, 리전.
- 휴대폰 페이지가 현재 카메라 미리보기를 보여 주는지, 서버 손 검출에 MediaPipe를 어떻게 쓸지.
- 백엔드 서버 크기·대역폭·동시 WebSocket 한도.
- 정확도(재현율·오탐) 전부, 오탐 허용 수준.
- 각 모델의 상업 이용 라이선스.
- 국외 이전 법적 요건.
- 일정(의도 문서에도 미정).
- 가상 카메라·녹화 재생 공격에 대한 현재 환경 점검의 방어 수준.
