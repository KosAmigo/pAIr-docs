# 과제 생성 파이프라인

> 작성일: 2026-11-24, 개정: 2026-11-25 ('고치기'에서 '다시 만들어 고르기'로)
> 좋은 과제의 기준은 [좋은_과제_기준.md](좋은_과제_기준.md)(E·M·Q 번호), 저장·API·폼은 [AI_과제_생성_설계.md](AI_과제_생성_설계.md)를 따른다. 이 문서는 **어떻게 생성하는지**만 정한다.

## 1. 목표

관문 검사를 통과해 관리자에게 넘어가는 과제 중 **그대로 쓸 수 있는 비율 97% 이상**. 판정은 기준 문서 번호로 한다.

## 2. 원칙

1. **고치지 말고 다시 만들어 고른다.** AI가 문장을 고치면 결함을 아는 채로 손대서 답을 흘리거나 함정을 지운다(2026-11-25 실험). 실패하면 문제를 만든 단계만 다시 생성한다.
2. **응시자에게 보이는 글은 결함을 모르는 단계가 쓴다.** 설명, 자료, 문항 글 모두. 모르는 함정은 설명할 수 없다(M5).
3. **통과·실패는 믿을 만한 검사만 정한다.** 관문은 놓치지 않는 쪽으로 기울인다. 오탐은 다시 생성 비용만 든다.

## 3. 단계

| 단계 | 모델 | 입력 | 출력 | 결함을 |
| --- | --- | --- | --- | --- |
| 1. 설계도 (**직군별**) | sol medium | 폼, 그 직군의 **검증된 결함 유형 목록** | 시나리오, 결함(유형, 위치), 판단 지점과 선택지별 근거 사실, 사실 목록(기록·원자료만), 숫자표(BIZ), 숨은 테스트·문항 사례(입력·기대 결과·자료 근거), **필요한 자료 묶음과 관련 적은 자료 목록(E6)** | 앎 |
| 2. 작성 | sol low | 사실·예 목록(섞음). BIZ 는 **문서마다 따로 동시에** 부르고 그 문서 자리의 사실만 준다 | 설명, 요구사항, NOTES, 문서, CSV(숫자표에서) | 모름 |
| 2'. 코드 (DEV) | sol medium | 설계도 | 시작 코드(결함 포함), 공개 테스트. 주석·글 없음 | 앎 |
| 3. 문항 글 (BIZ) | sol medium | 사례의 "구할 값", 숫자 보기 | 문항 글, 보기(숫자·짧은 결론만, 설명 없음) | 모름 |
| 4. 정답 쪽 | sol medium | 설계도, 완성된 2~3 | 숨은 테스트(사례만), 정답, 다른 풀이, 오답, 정답 키, 채점표 | 앎 |
| 4'. 관련 적은 자료 | 싼 모델(luna·terra) | 시나리오, 관련 적은 자료 목록(헷갈리는 자료 표시), 필요한 묶음의 파일 이름 | 실제 업무처럼 함께 있는 코드·문서, 헷갈리는 자료(결함·답·판단 근거 없음) | 모름 |

- 설계도는 직군마다 프롬프트·형식·형식 검사가 따로다(DEV: 공개 API·예·추가 메서드 틀·코드 파일·NOTES, BIZ: 숫자표·CSV·문서·문항). 사실·판단 지점·E6 묶음·말투 규칙은 공용 조각을 양쪽이 끼워 쓴다. 형식 검사 체크리스트는 직군별 프롬프트 끝에 1:1로 둔다(2026-11-26 g6).
- BIZ 작성: 요청 글(설명·요구사항·후속 질문) 1번 + 문서마다 1번을 동시에 부른다. 문서 사이 숫자·문장 겹침은 기존 결정적 검사(자료 숫자가 숫자표와 같음, 같은 문장 한 번)가 본다.
- 과제별 AI 제한(턴·첨부·맥락)은 저장할 때 제한시간 기본값으로 넣는다(`tasks.settings`).
- 결함 유형 목록: 자료에만 있는 업무 규칙이 AI 기본값과 다른 유형(경계 포함 여부, 업무 기준 시간대·마감, 회사 반올림 규칙, 부가세 포함, 집계 기간 차이, 적용 순서 등)과 유형별 숨은 테스트 모양·답이 새는 예. AI가 다시 짜며 저절로 고치는 일반 버그(정수 넘침 등)는 빼다(E3, g6). 주제는 자유, 결함 유형만 고른다.
- 필요한 묶음 크기(M6)는 공개 테스트를 빼고 센다.
- 숫자(BIZ)는 숫자표에만 정하고, 코드가 정합성과 자료 속 숫자를 대조한다(M1).

## 4. 관문 검사

| 종류 | 검사 | 실행 |
| --- | --- | --- |
| 결정적 | 컴파일, 숨은 테스트(시작 코드·오답 실패, 정답·다른 풀이 통과), 단답형 검산, CSV, 경로, 근거 파일, 숫자표, 테스트=설계도 사례, 보기에 다른 문항 정답(단위 맞춰 비교), 필요한 묶음 = 맥락 한도 40~70%·자료 전체 ≥ 한도 2배·결함 근거가 필요한 파일 2개 이상에 나뉨·헷갈리는 자료 1/3 이상(M6) | 코드 |
| 답 노출 (이중) | 응시자에게 보이는 글·문항·보기·자료 전부 대 결함. Sonnet과 terra가 따로 보고 하나라도 걸면 실패 | Sonnet, terra |
| 정답 키 | 답이 하나로 정해지는지, 단위, 판단 지점을 객관식으로 묻지 않는지 | Sonnet |
| 관련 적은 자료 | 답·결함 근거·판단 근거가 들어 있지 않은지(M6) | 생성과 다른 회사 |
| 테스트 근거 (DEV) | 숨은 테스트 단정마다 자료 근거 | Sonnet |
| 직접 풀기 | BIZ는 terra가 풀기, DEV는 Sonnet이 다른 풀이를 써서 숨은 테스트 실행(M2) | terra, Sonnet |
| 경고만 | 일관성, 품질(Q), 분량. 의도한 함정·판단 지점을 알려 주고 본다 | Sonnet |

- 기계적 수정만 코드가 한다: 정답 키 단위 맞추기.
- 판단 지점은 객관식 문항으로 묻지 않는다. 기획안(BIZ)·구현 선택(DEV)에서 다루고 채점표가 모든 선택지를 인정한다.
- 숨은 결함을 잡는 사례의 근거는 "그 기대 결과를 자료에서 끌어낼 수 있는 사실"(다른 입력의 기록, 영역 규칙 사실)이면 된다. 그 사례의 기대 결과를 그대로 적은 문장일 필요는 없다(그대로 적으면 답 노출, M5).
- 개발 과제에서 응시자가 추가할 메서드는 시작 코드에 틀(예외를 던지는 본문)로 있고, 설계도 사례와 숨은 테스트가 반드시 호출한다.
- AI 단독 풀이는 관문 통과 뒤 항상 돌린다. 결함을 잡으면 경고만 남긴다(난이도 목표: 놓치는 비율 50% 이상, 기준 문서 3장).

## 5. 실패하면

| 실패한 곳 | 다시 만드는 단계 |
| --- | --- |
| 설명·자료의 답 노출 | 2 작성 |
| 문항 글·보기 | 3 문항 글 |
| 정답 키·숨은 테스트·테스트 근거 | 4 정답 쪽 |
| 실행 검사 | 2' 코드 또는 4 |
| 함정이 사라짐, 결함이 안 숨겨짐 | 1 설계도부터 |
| 필요한 묶음이 맥락 한도의 40~70% 밖, 결함 근거가 파일 하나에만 있음(M6, 코드), 필요한 묶음 파일이 안 만들어짐 | 1 설계도 (파일이 안 만들어진 경우는 2' 코드, NOTES.md는 2 작성) |
| 자료 전체가 맥락 한도의 2배에 못 미침(M6, 코드), 관련 적은 자료 파일이 빠지거나 컴파일 실패(DEV) | 4' 관련 적은 자료만 (실패 이유와 부족한 글자 수를 알려 줌) |
| 관련 적은 자료에 답·결함 근거·판단 근거가 있음(M6, AI) | 4' 관련 적은 자료만 |

- 다시 만들 때마다 관문 전체를 다시 돈다. 예산: 글 문제(답 노출·일관성) 단계 다시 생성 2번 + 테스트·정답 문제 2번(종류별로 따로), 설계도 새로 1번(비용 상한 안에서만). 비용 상한: DEV $0.6, BIZ 20분 $0.6·40분 $0.8·60분 $1.0(2026-11-26 g9: BIZ는 첫 시도에 $0.47~0.62를 써서 다시 만들 여유가 없었음). 끝내 실패하면 실패 이유와 함께 검수 전(HIDDEN)으로 저장.
- 모든 단계의 모델·토큰·시간, 관문 결과, 다시 만든 이력을 `_gen/report.json`에 남긴다.

## 6. 실행 방식 (2026-11-26)

관리자가 생성 폼에서 고른다. 두 방식 모두 같은 단계·관문을 거치고, 모델 호출 방식만 다르다.

| 방식 | 호출 | 비용 | 시간 |
| --- | --- | --- | --- |
| 바로 생성 (기본) | `ModelClient` 바로 호출 | 기본 | 과제당 10분 이하 목표 |
| 배치 | 단계마다 여러 과제의 같은 단계를 묶어 배치 API로 보냄(OpenAI·Anthropic) | 약 50% | 몇 분~몇 시간 |

- 동시 생성: 최대 10개. 과제 안에서 서로 기다릴 필요 없는 관문은 동시에 돈다.
- 배치 마감: 관리자는 전체 마감(1·3·6시간, 기본 3)만 고른다. 단계별 최대 대기는 설정값(시작값: 생성 단계 20분, 관문·단독 풀이 10분)이고 관리자 화면에 두지 않는다.
- 단계 대기를 넘으면 안 온 호출만 취소하고 바로 호출로 다시 보낸다. 받은 결과는 그대로 쓴다. 다시 생성 등으로 남은 마감이 모자라면 남은 단계는 모두 바로 호출로 돌려 마감 안에 끝낸다.
- 단계별 기본값은 `report.json`의 실제 배치 대기시간 기록으로 다시 정한다.
- 작업 상태(단계, 배치 id, 받은 결과)는 DB에 저장해 서버를 다시 켜도 이어 간다.
- `report.json`에 호출마다 배치·바로 호출 여부와 단계별 시간을 남긴다.

## 7. 확인 방법

- 독립 감사: 생성기 밖의 검증 세션이 판정표(정현 로컬 `taskgen-runs/_verify/`)로 판정하고, 관문 결과와 항목별로 맞춰 본다(놓침·오탐).
- 개수: 6개로 동작 확인 → 12개 → 30개로 97% 확인. 6개 단위 ±1은 오차로 본다.
- 비용·시간: 과제당 $0.25~0.35, 10분 이하.
