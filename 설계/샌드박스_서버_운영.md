# 샌드박스 서버 운영 체크리스트

> 작성: 문희 · 2026-11-24 · 상태: **초안** (확인한 부분과 아직 확인하지 못한 부분을 구분해 적었다. EC2 확인 결과는 7절)
> 근거: [API/응시_흐름_API.md](../API/응시_흐름_API.md) §11, [기획/담당_기술명세_문희.md](../기획/담당_기술명세_문희.md) 코드 실행 구조·컨테이너 수명
> 샌드박스는 격리 실행 환경을 뜻하는 일반 용어이고, 구현은 일반 Docker 컨테이너다(Docker Sandboxes 제품이 아니다).

## 1. 구성

```
응시자 브라우저 ──▶ 앱 서버(Spring, DB·API 키) ──▶ 샌드박스 서버(8282, 사설망) ──▶ [일회용 컨테이너]
                       PAIR_RUN_MODE=remote            프로필 sandbox-server           빌드·실행마다 1개, 끝나면 삭제
```

- 샌드박스 서버에는 **DB 접속 정보와 AI API 키를 두지 않는다.** 응시자 코드가 도는 서버에 비밀이 없다는 것이 이 구조의 목적이다.
- 두 서버는 공유 토큰(`PAIR_RUN_REMOTE_TOKEN`)으로 연결한다. 토큰이 없으면 샌드박스 서버는 시작하지 않는다.
- 앱과 샌드박스를 한 서버에 둘 때는 `PAIR_RUN_MODE=docker` 이지만, 그 경우 같은 서버에 DB 정보와 키가 있다. 응시자가 불특정 다수인 자가진단은 분리를 권장한다.

## 2. 서버 준비 (한 번)

| 단계 | 내용 | 확인 상태 |
|---|---|---|
| 인스턴스 | 컴퓨팅 최적화 `c7i` 계열. 규모별 크기는 [응시_흐름_API.md §9](../API/응시_흐름_API.md)와 아래 4절. `t` 계열은 CPU 크레딧이 떨어져 쓰지 않는다 | 추정 |
| 소프트웨어 | Docker, JDK 21 | 맥 확인. EC2 에서 서버·컨테이너 동작 확인(2026-11-26, 설치 버전은 따로 확인하지 않음) |
| 이미지 | 서버 안에서 `sh docker/sandbox/build.sh` (`pair-sandbox`). JUnit jar 를 내려받으므로 서버가 인터넷에 나갈 수 있어야 한다 | 로컬(맥) 확인 |
| 코드 | pAIr-back 의 jar 를 올린다. 앱 서버와 같은 jar 를 쓴다 | EC2 에서 실행 확인(2026-11-26, 11-25 에 올린 jar) |

## 3. 환경변수

| 서버 | 변수 | 값 |
|---|---|---|
| 샌드박스 | `PAIR_RUN_REMOTE_TOKEN` | 앱 서버와 같은 긴 무작위 문자열 (필수) |
| 샌드박스 | `PAIR_SANDBOX_PORT` | 기본 8282 |
| 샌드박스 | 동시 상한 `PAIR_RUN_MAXCONCURRENT` (속성 `pair.run.max-concurrent`, 환경변수로는 대시를 뺀 이름) | **서버 vCPU 수 − 2 이하** (기본 4). 코어보다 많으면 정상 코드도 시간 초과로 실패한다 |
| 앱 | `PAIR_RUN_MODE` | `remote` |
| 앱 | `PAIR_RUN_REMOTE_URL` | `http://<샌드박스 서버 사설 주소>:8282` |
| 앱 | `PAIR_RUN_REMOTE_TOKEN` | 샌드박스와 같은 값 |
| 앱 | 빌드·실행 횟수 제한 | `PAIR_RUN_RATELIMITPERMINUTE` (속성 `pair.run.rate-limit-per-minute`, 기본 1분 10번) |

## 4. 실행

- 개발(로컬): `gradlew bootRunSandbox` (맥에서 colima 를 쓰면 `JAVA_TOOL_OPTIONS=-Djava.io.tmpdir=$HOME/<폴더>` 가 필요하다. Docker Desktop·리눅스는 필요 없다) — **확인함**.
- 서버(jar): `java -Dloader.main=com.pair.global.config.SandboxServerConfig -cp <jar> org.springframework.boot.loader.launch.PropertiesLauncher` — **맥에서 jar 로 띄워 확인함(2026-11-24, 기동 2.6초, DB·키 없이 부팅).** `PAIR_RUN_REMOTE_TOKEN` 이 없으면 시작하지 않는 것도 확인했다. EC2(Ubuntu)에서도 기동을 확인했다(2026-11-25, 약 6초). 운영 서버는 아래 4.1 의 systemd 로 띄운다.
- 실행 API(`POST /internal/run`)는 `main` 이 아니라 **JUnit 테스트**를 돌린다. 연결 확인용으로 보낼 코드에는 `@Test` 가 있어야 한다.
- 제한 시간: 테스트 제한(30초)과 별도로 컨테이너 시작·컴파일 여유 15초를 더 기다려서, 무한 루프는 `[TIMEOUT]` 응답까지 **약 45초**가 걸린다(실측 45.2초). 응시자 화면의 안내는 "실행 제한 30초(컨테이너 준비 시간 별도)"로 맞췄다.
- 서버가 다시 켜지면 지난번에 남은 `pair-run-*` 컨테이너를 자동으로 지운다. 컨테이너도 서버 없이 스스로 끝난다(서버 제한 + 20초).

### 4.1 자동 시작 (systemd, EC2 Ubuntu)

재부팅해도 서버가 저절로 뜨게 한다. **재부팅 뒤 `active` 와 8282 수신을 확인했다(2026-11-25).** 아래 명령은 모두 샌드박스 서버에서 실행한다. jar 는 `/home/ubuntu/`, java 는 `/usr/bin/java` 기준이다.

1. 토큰 파일 `/etc/pair-sandbox.env` 를 만든다(앱 서버와 같은 값, `export`·따옴표 없이 한 줄). 토큰은 문서나 git 에 적지 않는다.

   ```bash
   sudo nano /etc/pair-sandbox.env    # PAIR_RUN_REMOTE_TOKEN=<앱 서버와 같은 토큰>
   sudo chmod 600 /etc/pair-sandbox.env
   ```

2. 서비스 파일을 만든다.

```bash
sudo tee /etc/systemd/system/pair-sandbox.service > /dev/null <<'EOF'
[Unit]
Description=pAIr sandbox server
Requires=docker.service
After=docker.service network-online.target
Wants=network-online.target

[Service]
User=ubuntu
SupplementaryGroups=docker
WorkingDirectory=/home/ubuntu
EnvironmentFile=/etc/pair-sandbox.env
ExecStart=/usr/bin/java -Dloader.main=com.pair.global.config.SandboxServerConfig -cp /home/ubuntu/pair-backend-0.0.1-SNAPSHOT.jar org.springframework.boot.loader.launch.PropertiesLauncher --pair.run.max-concurrent=1
SuccessExitStatus=143
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF
```

   - `max-concurrent=1` 은 `c7i-flex.large` 기준이다. `xlarge` 로 올리면 2 로 바꾼다.
   - `PrivateTmp=true` 는 넣지 않는다. 서버가 `/tmp` 에 쓴 코드를 컨테이너에 마운트하는데, 이 옵션을 켜면 Docker 가 그 폴더를 볼 수 없다.

3. `nohup` 으로 띄운 서버가 있으면 끄고 서비스를 켠다(몇 초간 빌드·실행이 안 된다).

   ```bash
   pkill -f SandboxServerConfig; sleep 3
   sudo systemctl daemon-reload && sudo systemctl enable --now docker pair-sandbox
   sleep 10; systemctl is-active pair-sandbox; ss -ltn | grep 8282
   ```

4. `sudo reboot` 뒤 다시 접속해, 직접 실행하지 않아도 `active` 와 8282 가 나오는지 보고 화면에서 빌드를 눌러 본다.

| 용도 | 명령 |
|---|---|
| 로그 | `journalctl -u pair-sandbox -n 50 --no-pager` |
| 재시작 | `sudo systemctl restart pair-sandbox` |
| jar 교체 | 같은 경로에 덮어쓰고 재시작 |
| 토큰 교체 | `/etc/pair-sandbox.env` 를 고치고 재시작 → 앱 서버 `application-secret.yml` 과 GitHub 시크릿 `APP_SECRET_YML`(파일 전체)도 같은 값으로 바꾸고 앱 백엔드를 다시 만든다 |

**설치할 때 막혔던 것 (2026-11-25)**

- `build.sh` 의 `path ".\r" not found`: Windows 에서 올린 파일의 줄바꿈이 CRLF 라서다. 서버에서 `sed -i 's/\r$//' ~/sandbox/*` 를 실행한다.
- 화면의 "실행 서버의 응답이 늦어…": `PAIR_RUN_REMOTE_URL` 에 `:8282` 가 빠져 연결 타임아웃이 났다.

## 5. 네트워크·보안

- 8282 는 **앱 서버의 보안 그룹에서만** 들어오게 연다. 인터넷에 열지 않는다. 응시자 브라우저는 샌드박스 서버에 직접 접속하지 않는다.
- 컨테이너는 인터넷이 막혀 있고(`--network none`), 메모리 512MB·CPU 1·프로세스 128개, 읽기 전용 루트, 일반 사용자, 권한 제거로 돈다. 이 값은 코드(`SandboxRunner`)에 있다.
- 서버에 DB·API 키 환경변수가 없는지 확인한다(`env` 에 `OPENAI`, `ANTHROPIC`, `PAIR_DB` 가 없어야 한다). 접속한 셸이 아니라 서비스 프로세스의 환경변수를 봐야 하므로 아래처럼 이름만 출력한다(EC2 확인 2026-11-26: 시스템 기본값과 `PAIR_RUN_REMOTE_TOKEN` 만 있음).

  ```bash
  sudo cat /proc/$(systemctl show -p MainPID --value pair-sandbox)/environ | tr '\0' '\n' | cut -d= -f1
  ```

- **관리 포트 8181 도 인터넷에 열지 않는다.** 샌드박스 서버도 8282 외에 관리 포트(`PAIR_MANAGEMENT_PORT`, 기본 8181)를 모든 주소에서 열고, `/actuator/health`·`/actuator/prometheus` 는 인증 없이 응답한다(맥에서 확인, 2026-11-26). 이 서버의 지표를 수집하지 않으면 인바운드 규칙을 만들지 않는다.

## 6. 시험 날 순서

1. 시험 전날: 인스턴스를 켠다 → 이미지가 있는지 `docker images pair-sandbox` → 샌드박스 서버가 자동으로 떴는지 `systemctl is-active pair-sandbox` 로 본다.
2. 연결 확인: 앱 서버에서 샌드박스 주소로 토큰 없이 `POST /internal/run` 을 보내 **401** 이 오면 서버가 떠 있는 것이다(별도 상태 확인 API 는 없다). 이어서 시험용 계정으로 빌드·실행을 한 번 눌러 본다.
3. 시험 중: 응시자가 "잠시 뒤 다시 시도해 주세요"(503)를 자주 본다면 동시 상한이 모자란 것이다. 인스턴스를 키우거나 대수를 늘린다.
4. 시험 뒤: 인스턴스를 **중지**한다(켜 두면 계속 과금된다). 자가진단을 상시 운영하면 켜 둔다.

## 7. EC2 확인 결과 (2026-11-26)

대상: 샌드박스 서버(Ubuntu, `c7i-flex.large`, vCPU 2개, 메모리 3.7GB, 스왑 없음), systemd `pair-sandbox`, `max-concurrent=1`. 모두 샌드박스 서버 안에서 `localhost:8282` 로 실행 API 를 불렀다. 확인 스크립트(`isolation_check.py`, `load_test.py`)는 저장소에 넣지 않았다.

### 7.1 격리 (11개 항목 모두 통과)

| 항목 | 확인한 내용 |
|---|---|
| 토큰 | 틀린 토큰은 401 |
| 정상 실행 | 통과 |
| 네트워크 | 외부 주소, EC2 메타데이터(`169.254.169.254`), Docker 호스트의 8282 접속 실패. 루프백 외 켜진 인터페이스 없음 |
| 환경변수 | 컨테이너 안에 토큰·키 이름의 변수 없음 |
| 파일·사용자 | root 아님. `/etc`·`/opt`·소스 폴더 쓰기 실패 |
| 권한 | `CapEff` 0, `NoNewPrivs` 1, `docker.sock` 없음 |
| 자원 제한(cgroup 값) | 메모리 512MB, 스왑 0, CPU 1개, 프로세스 128개 |
| 폭탄 코드 | 스레드·디스크 채우기·메모리 폭탄 차단 (각 실행 약 3초) |
| 무한 루프 | `[TIMEOUT]` 으로 중단 (45.1초) |

### 7.2 서버가 죽었을 때 컨테이너 정리 (2가지 모두 통과)

실행 중인 컨테이너가 있을 때 `systemctl kill -s KILL pair-sandbox` 로 서버를 강제 종료했다.

| 상황 | 결과 |
|---|---|
| systemd 가 서버를 다시 켬 | 15초 뒤 `pair-run-*` 없음, 서비스 `active` |
| 강제 종료 직후 `systemctl stop` 으로 꺼 둠 | 직후에는 컨테이너가 남아 있고, 60초 뒤에는 없음 (컨테이너 안 `timeout`) |

### 7.3 동시 실행 측정

과제 `order-deadlock` 의 정답 코드와 숨은 테스트를 `/internal/run` 으로 같은 순간에 N개 보냈다. 대기 한도 60초, 각 단계 1번씩 측정.

| 동시 요청 | 전체 | 응답 중앙값 | 응답 최대 | 결과 |
|---|---|---|---|---|
| 1 | 6.6초 | 6.6초 | 6.6초 | 성공 1 |
| 4 | 26.5초 | 16.6초 | 26.5초 | 성공 4 |
| 10 | 65.8초 | 36.4초 | 65.8초 | 성공 10 |
| 30 | 66.1초 | 60.0초 | 66.1초 | 성공 10, 503 거절 20 |

- 지금 설정은 **거의 동시에 들어온 요청 약 10건**까지 받는다(1분에 약 9건 처리). 10건이면 절반은 36초 넘게 기다린다. 접속 응시자 수의 한계가 아니다.
- 30명이 동시에 누르면 3명 중 2명이 503 을 받는다. 시간 초과나 실행 실패는 없었다.
- 측정하지 않은 것: 앱 서버를 거치는 시간, [빌드](컴파일만) 요청, 다른 과제, 다른 사양과 동시 상한.
- (계산값, 미측정) 처리량이 동시 상한에 비례한다고 가정하면 30건을 60초 안에 모두 끝내려면 상한 4 이상이 필요하다. 사양을 바꾸면 같은 측정을 다시 한다.

## 8. 아직 확인하지 못한 것

| 항목 | 상태 |
|---|---|
| 환경변수 이름 `PAIR_RUN_MAXCONCURRENT`·`PAIR_RUN_RATELIMITPERMINUTE` 가 실제로 적용되는지 (Spring 규칙대로 적었으나 값을 바꿔 띄워 보지 않았다) | 미확인 |
| jar 로 샌드박스 서버 띄우기 | 맥(2026-11-24)과 EC2(2026-11-25 기동·401·앱 화면 빌드 실행, 11-26 격리·정리 확인, 7절)에서 확인 |
| 시험 인원에 맞는 사양·동시 상한 확정 | 현재 사양(상한 1)은 측정 완료(7.3). 목표 동시 인원이 정해지지 않았고, 상한을 올린 구성은 **미측정** (다른 절·문서의 사양별 인원은 맥 측정 기반 추정) |
| 앱·샌드박스 서버 사이 네트워크 지연, 보안 그룹 | 앱 서버에서 8282 연결 확인(401, 약 6ms). 부하 시 지연과 보안 그룹 규칙(8282·8181) 점검은 미확인 |
| 서버 2대로 나눌 때 앞단 로드밸런서 | 미결정 (`RemoteDockerRunner` 는 주소 1개만 받는다) |
| 상시 가동 시 프로세스 관리(systemd) | 적용·재부팅 자동 시작 확인(2026-11-25, 4.1) |
