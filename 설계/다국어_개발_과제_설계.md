# 다국어 개발 과제 설계

> 2026-11-28 · 상태: **초안** (기획만 함, 구현 전)
> 목표: 개발 과제(과제형: 버그 수정·기능 추가 + 숨은 테스트)를 Java 말고 다른 언어로도 출제·응시·채점한다.

## 1. 지금 Java에 묶인 곳

| 위치 | 묶인 내용 |
|---|---|
| `backend/docker/sandbox/Dockerfile`, `run.sh` | JDK 21 + JUnit만 있음 |
| `SandboxRunner`, `JunitReports` | 오류 줄 정규식이 `.java` 전용, 결과는 JUnit XML |
| `JavaDiagnostics` + 프런트 `liveDiagnostics.ts` | 입력 중 오류 밑줄·자동완성을 서버 javac로 처리 |
| 프런트 `CodeEditor.tsx` | 문법 색칠이 `lang-java`뿐 |
| `domain/taskgen` (`DevCheckService` 등) | 코드 파일 = `.java`, 힌트 주석 검사는 `//`만, 가짜 구현 검사는 Java 문법 기준 |

그대로 쓸 수 있는 것: `CodeRunner` 인터페이스, 실행 1회 = 컨테이너 1개 구조, 통과/실패 수만 보는 검사(시작 통과, 숨은 테스트가 잡음, 정답 통과, 오답 걸러냄, 다른 풀이 통과).

## 2. 언어별 판단

| 언어 | 테스트 도구 | JUnit XML | 에디터 색칠 | AI 출제 품질 | 판단 |
|---|---|---|---|---|---|
| Python | pytest | `--junitxml` | `@codemirror/lang-python` | 아주 좋음 | ✅ 1단계 |
| C | gcc + GoogleTest | `--gtest_output=xml` | `@codemirror/lang-cpp` | 좋음 | ✅ 2단계 |
| C++ | g++ + GoogleTest | 같음 | `@codemirror/lang-cpp` | 좋음 | ✅ 2단계 |
| Go | go test | gotestsum | `@codemirror/lang-go` | 좋음 | ✅ 2단계 |
| C# | dotnet test | JUnit 로거 | legacy-modes clike | 좋음 | ✅ 2단계 (메모리·시작 시간 측정 필요) |
| Rust | cargo test | cargo-nextest | `@codemirror/lang-rust` | 괜찮음 | ⚠️ 3단계 (컴파일 느림) |
| R | testthat | JunitReporter | legacy-modes r | 보통 | ⚠️ 3단계 (데이터 분석 과제 성격) |
| Ada | GNAT + AUnit | XML 리포터 | 직접 작성 | 약함 | ❌ 보류 |

## 3. 설계 규칙

| 항목 | 규칙 |
|---|---|
| 실행 이미지 | 언어마다 따로 (`pair-sandbox-<lang>`). 하나로 합치지 않는다 |
| `run.sh` 규칙 | 모든 언어 같게: 입력 `/workspace/src`, 출력 컴파일 로그 + JUnit XML 폴더 |
| 빌드 파일 | `Cargo.toml`, `go.mod`, `.csproj`, `Makefile` 등은 언어별 고정 템플릿. AI가 만들지 않고 응시자가 고칠 수 없다 |
| 의존성 | 이미지에 미리 넣고 오프라인으로 빌드 (인터넷 차단 유지) |
| 컴파일 오류 표시 | 1단계는 빌드할 때 컴파일러 출력을 파싱 (gcc·GNAT `file:line:col: error`, rustc `--error-format=json`, go, dotnet) |
| 입력 중 밑줄·자동완성 | Java만 유지. 다른 언어는 언어 서버(clangd, pyright, gopls 등)가 상주 메모리를 먹으므로 보류 |
| 데이터 | 과제·응시 상태·채점에 `language` 칸 추가. 에디터 언어는 파일 확장자로 고름 |
| 숨은 테스트 분리 | 지금 Java와 같은 한계(같은 컨테이너). 바꾸지 않는다 |

## 4. 과제 생성 검사 바꿀 것

| 검사 | 바꿀 것 |
|---|---|
| 형식 | 언어별 경로 규칙 (예: Python `src/`·`tests/`, Rust `src/lib.rs`·`tests/`) |
| 힌트 주석 | 주석 기호를 언어별로 (`//`, `#`, `--`) |
| 가짜 구현 | 1단계는 Java가 아니면 건너뜀 → 나중에 tree-sitter로 여러 언어 처리 |
| 시간 | 언어별 제한 시간 (Rust·C#은 더 길게) |
| 함정 종류 `flaw-types-dev.md` | 언어별 함정 추가 (C·C++: 메모리 오류, Go: 고루틴·nil, Rust: 소유권 등) |

기준을 바꿀 때는 [좋은_과제_기준.md](좋은_과제_기준.md)를 먼저 고친다.

## 5. 언어별 주의

| 언어 | 주의 |
|---|---|
| C·C++ | 테스트에 ASan·UBSan을 켠다. 메모리 512MB 안에서 되는지 확인 |
| Rust | 숨은 테스트는 `tests/` 통합 테스트라 `pub` API만 검사 가능 → 과제 설계도에 공개 API를 정해 둔다 |
| C# | dotnet 빌드가 메모리 300~600MB를 씀 → 컨테이너 한도 1GB (6절) |
| Python | 컴파일 단계가 없으므로 빌드 버튼 = `py_compile` 문법 검사 |

## 6. 서버 용량 (샌드박스 EC2, RAM 8GB)

| 항목 | 값 |
|---|---|
| 컨테이너에 쓸 수 있는 메모리 | 약 6.5GB (OS·샌드박스 서버 JVM 약 1.5GB 제외) |
| 컨테이너 메모리 한도 | 언어별로 둔다. 기본 512MB, **C#·Rust는 1GB** |
| 동시 실행 | 메모리보다 **CPU 코어 수가 상한** (`max-concurrent` ≤ 코어 수). 4코어면 1GB × 4 = 4GB라 메모리는 남는다 |
| 디스크 | 언어 이미지 합계 약 5~6GB (Rust·gcc·dotnet이 큼). EBS 여유 공간 확인 |

## 7. 같은 과제를 여러 언어로

과제 1개 = 언어 공통 설계도 + 언어별 코드. 모든 언어를 같은 숨은 테스트로 채점한다.

| 무엇 | 공통 | 언어별 |
|---|---|---|
| 요구사항, 판단 포인트, 버그 내용 | ✅ | |
| 테스트 사례 (입력 → 기대값, JSON) | ✅ | |
| 시작 코드, 정답, 오답 | | ✅ AI가 번역 |
| 테스트 실행기 | | ✅ 고정 템플릿 |

- 실행기: 사례 JSON을 읽어 응시자 함수를 부르고 결과를 JSON으로 출력 → 비교는 서버가 한다.

| 순서 | 할 일 |
|---|---|
| 1 | 기존 Java 파이프라인으로 기준 과제 생성·검사 통과 |
| 2 | 시작 코드·정답·오답을 다른 언어로 번역 (사례 데이터는 그대로) |
| 3 | 언어마다 기존 검사(4절) 다시 실행 |
| 4 | 새 검사 **언어 간 동일성**: 시작 코드가 실패하는 사례가 모든 언어에서 같고, 정답은 모두 통과 |
| 5 | 언어 버전은 응시자가 처음 고를 때 만들고 저장 |

| 제약 | 내용 |
|---|---|
| 버그 종류 | 모든 언어 공통만 (경계값, 상태, 계산, 예외 처리 빠짐). 메모리·소유권 같은 언어 전용 버그 제외 |
| 데이터 | 숫자, 문자열, 리스트, 맵, 레코드 (JSON으로 표현 가능한 것) |
| 난이도 | 같은 기능도 언어마다 코드 양이 다름 → 언어별 제한 시간 여부 결정 |
| 대상 언어 | R·Ada 제외 |

## 8. 단계

| 단계 | 할 일 | 끝난 기준 |
|---|---|---|
| 1 | `language` 칸, 이미지 규칙, 컴파일러 출력 파서, 확장자별 색칠 + **Python** | Python 과제 생성 → 응시 → 채점이 끝까지 됨 |
| 2 | C, C++, Go, C# | 언어별 생성 검사 통과 과제 1개 이상 |
| 3 | Rust, R, 언어별 시간 제한 | 같음 |
| 보류 | Ada, 언어 서버(입력 중 밑줄) | 수요가 생기면 다시 검토 |

## 9. 정할 것

- 샌드박스 EC2 vCPU 수 확인 → `max-concurrent` 결정
- 응시자가 언어를 고르는지, 회사가 과제 만들 때 정하는지
- 같은 과제에서 언어별 제한 시간을 다르게 둘지 (7절)
