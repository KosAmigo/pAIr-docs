# 백엔드 패키지 구조와 이름 규칙

> 2026-11-23 확정. pAIr-back(`backend/src/main/java/com/pair`)의 폴더와 클래스 이름을 이 규칙대로 맞춘다.
> 새 코드는 반드시 이 규칙을 따른다. 기존 코드는 패키지 개편 작업에서 한 번에 옮기고 이름도 바꾼다.

## 한 줄 요약

**기능별로 패키지를 먼저 나누고, 기능 안은 `controller / service / dto / repository / entity / exception` 6개 폴더로 고정한다. 폴더마다 클래스 이름 끝말도 정해져 있다.**
여러 기능이 같이 쓰는 코드는 `global/`, 외부 시스템 연결은 `infra/`에 둔다.

## 왜 이렇게 정했나

- 스프링부트에는 공식 표준이 없다. 많이 쓰는 방식은 계층형(맨 위가 controller/service/…)과 기능별(맨 위가 user/order/…) 두 가지다.
- 계층형은 프로젝트가 커지면 한 폴더에 클래스가 수십 개 쌓이고, 한 기능을 고치려면 여러 폴더를 오가야 한다. 그래서 요즘은 기능별을 많이 추천한다. 스프링이 만든 Spring Modulith도 메인 패키지 바로 아래 패키지 하나를 기능 모듈 하나로 본다.
- 다만 기능 폴더 안까지 자유롭게 두면 지금처럼 기능마다 모양이 달라진다. 예를 들어 `exam`은 `domain/web`으로, `attempt`는 `db/`로 나뉘어 있다. 그래서 **안쪽 폴더 이름과 클래스 이름 끝말을 고정**해, 어느 기능을 열어도 같은 위치에서 같은 것을 찾게 한다.
- `domain/`이라는 하위 폴더 이름은 쓰지 않는다. 맨 위 폴더 이름과 겹치고, 이름만 봐서는 안에 무엇이 있는지 알 수 없다.

## 폴더 이름 규칙

```
com.pair
├─ PairApplication
├─ global/                 여러 기능이 같이 쓰는 것
│  ├─ config/              @Configuration, @ConfigurationProperties, 웹 설정
│  ├─ error/               공통 예외, ApiExceptionHandler
│  └─ security/            현재 사용자(CurrentUser), 리졸버, 인터셉터, JWT
├─ infra/                  외부 시스템 연결
│  ├─ ai/                  Claude·OpenAI 클라이언트, 임베딩, 배치
│  ├─ sandbox/             응시자 코드 실행 (지금의 run/)
│  ├─ storage/             S3·로컬 파일 저장소
│  ├─ payment/             토스 결제 클라이언트
│  └─ mail/                메일 공통 레이아웃·발송
└─ domain/
   ├─ auth/                계정, 로그인, 이메일 인증
   ├─ company/             기업, 초대, 도입 문의
   ├─ credit/              크레딧, 결제 기록
   ├─ task/                과제, 과제 자료, 과제 콘솔(지금의 taskconsole)
   ├─ taskgen/             과제 자동 생성
   ├─ exam/                실전 시험 회차, 감독
   ├─ attempt/             응시, 체크포인트, 복기
   ├─ question/            객관식·주관식 문항
   ├─ scoring/             채점
   └─ grader/              채점 프롬프트 관리
```

- 맨 위는 `global/`, `infra/`, `domain/` 세 개만 둔다.
- 기능 폴더 이름은 영어 소문자 한 단어(또는 붙여 쓴 단어)로 한다. 새 기능은 `domain/` 아래에 추가한다.
- `global/`, `infra/` 안 폴더는 위 목록에 있는 것만 쓴다. 새로 필요하면 팀에서 정하고 이 문서에 추가한다.

### 기능 폴더 안: 6개 고정

```
domain/exam/
├─ controller/   API 입구 (@RestController)
├─ service/      로직. 클래스 이름은 전부 XxxService
├─ dto/          데이터만 담는 클래스 (API 요청·응답 + 내부 데이터)
├─ repository/   데이터 저장·조회
├─ entity/       DB 테이블 클래스 (@Entity)
└─ exception/    이 기능 전용 예외
```

| 폴더 | 들어가는 것 | 들어가면 안 되는 것 |
| --- | --- | --- |
| `controller/` | `@RestController` | 비즈니스 로직, 리포지토리 직접 호출 |
| `service/` | 로직이 있는 클래스 전부 (업무 로직, 계산·파싱·메일·엑셀·스케줄러·웹소켓 처리 등) | 데이터만 담는 클래스, `@Entity`, 예외 |
| `dto/` | 데이터만 담는 클래스: API 요청·응답, 계층 사이에 넘기는 내부 데이터, 이벤트 | 엔티티를 그대로 담은 응답, 로직이 큰 클래스 |
| `repository/` | `JpaRepository` 인터페이스, 직접 만든 저장소 클래스 | 로직 |
| `entity/` | `@Entity` 클래스, 엔티티가 쓰는 enum | 리포지토리, 서비스 |
| `exception/` | 이 기능에서만 쓰는 예외 | 여러 기능이 같이 쓰는 예외 |

규칙:

1. **폴더 이름은 이 6개만 쓴다.** `web/`, `db/`, `domain/`, `model/`, `util/` 같은 다른 이름을 기능 안에 만들지 않는다.
2. **클래스가 없는 폴더는 만들지 않는다.** 예: DB 테이블이 없는 `taskgen`에는 `repository/`, `entity/`가 없다. 빈 폴더는 두지 않는다.
3. **로직이 있으면 `service/`, 데이터만 담으면 `dto/`에 둔다.** 계산기, 파서, 스케줄러는 `service/`, 내부용 record는 `dto/`다.
4. **기능 폴더 바로 아래에는 클래스를 두지 않는다.** 모든 클래스는 6개 폴더 중 하나에 들어간다.

## 클래스 이름 규칙

| 위치 | 이름 규칙 | 예 |
| --- | --- | --- |
| `controller/` | `XxxController` | `ExamController` |
| `service/` | **예외 없이 전부 `XxxService`** (인터페이스, 추상 클래스, static 도우미 포함) | `ExamSessionService`, `InviteMailService`, `CalcParserService`, `ExamSchedulerService` |
| `dto/` | API 요청은 `XxxRequest`, API 응답은 `XxxResponse`, 그 밖의 데이터는 `XxxDto` | `CreateExamRequest`, `ExamDetailResponse`, `AttemptStateDto` |
| `repository/` | `XxxRepository` | `ExamSessionRepository` |
| `entity/` | 끝말 없는 명사. `Record`, `Entity`를 붙이지 않는다 | `ExamSession`, `Company` |
| `exception/`, `global/error/`, `infra/` 예외 | `XxxException` | `LinkExpiredException` |
| `global/config/` | `XxxConfig`(설정 빈), `XxxProperties`(설정값) | `ExamConfig`, `PairProperties` |
| `infra/` | 외부 API 호출은 `XxxClient`, 파일 저장은 `XxxStorage` | `TossPaymentClient`, `S3SnapshotStorage` |
| 테스트 | `대상클래스Test`. 여러 계층을 같이 돌면 `XxxIntegrationTest` | `ExamSessionServiceTest`, `ExamFlowIntegrationTest` |

- 이름은 영어 UpperCamelCase로 쓰고, 약어도 단어처럼 쓴다. 예: `JwtTokens`, `S3Client`(O), `JWTTokens`(X).
- **폴더 이름 = 끝말.** `controller`→`Controller`, `service`→`Service`, `repository`→`Repository`, `exception`→`Exception`, `dto`→`Request`/`Response`/`Dto`. 엔티티만 끝말이 없다.
- `service/`를 예외 없이 `Service`로 정한 이유: 다른 연습 프로젝트(SmartTicketing)에서 도우미 이름을 자유롭게 두었더니 `XxxRanks`, `XxxReports` 같은 애매한 이름이 늘었다. 이름이 조금 어색해도(`XlsxStyleService`) 규칙이 하나인 편이 사람과 AI 모두 지키기 쉽다.
- `Service` 앞부분은 단수 명사로 하는 일을 적는다. `EditProposals`(X) → `EditProposalService`(O).
- **엔티티가 끝말 없는 이름을 가져간다.** 엔티티와 이름이 겹치는 데이터 클래스는 `dto/`에서 `Dto`를 붙인다. 예: 엔티티 `Attempt`, 응시 전체 상태 `AttemptStateDto`.
- 하나의 `XxxDtos` 파일에 여러 요청·응답을 모아 두지 않는다. 요청·응답마다 파일을 나눈다.
- 엔티티 클래스 이름을 바꿔도 테이블 이름은 `@Table(name = ...)`으로 고정되어 있으므로 DB는 바뀌지 않는다. 새 엔티티도 반드시 `@Table(name = ...)`을 적는다.

## 예외는 어디에

| 종류 | 위치 | 예 |
| --- | --- | --- |
| 여러 기능이 같이 쓰는 예외 | `global/error/` | `UnauthorizedException`, `ForbiddenException`, `ConflictException` |
| 한 기능에서만 쓰는 예외 | 그 기능의 `exception/` | `InsufficientCreditException`, `LinkExpiredException`, `TooManyJobsException` |
| 외부 연결 실패 예외 | 해당 `infra/` 폴더 | `AiUnavailableException`, `PaymentRejectedException` |

## global, infra, domain 구분 기준

- **`infra/`**: 외부 시스템(AI API, S3, 토스, 메일 서버, 샌드박스)과 직접 통신하는 코드다. 바깥 시스템이 바뀌면 여기만 고친다.
- **`global/`**: 특정 기능에 속하지 않고 전체에 걸리는 코드다. 설정, 공통 예외 처리, 인증 확인이 여기에 해당한다.
- **`domain/`**: 그 밖의 모든 업무 기능이다.
- 헷갈리면 "이 코드가 어떤 기능 하나에서만 쓰이나?"를 따진다. 하나에서만 쓰이면 그 기능 폴더에 둔다.
  - 예: `InviteMailService`는 시험 초대 메일 내용을 만드므로 `domain/exam/service/`에 둔다. 공통 틀인 `MailLayout`은 `infra/mail/`에 둔다.
- 기능 전용 설정 클래스(`ExamProperties`, `TaskGenProperties` 등)도 `global/config/`에 모은다. 설정은 한곳에서 찾게 한다.
- 인터셉터와 리졸버는 기능 전용이라도 `global/security/`에 둔다. `controller/`에는 컨트롤러만 둔다.

## 테스트 폴더

`src/test/java`도 `src/main/java`와 같은 패키지 구조를 따른다.
예를 들어 `domain/exam/service/ExamSessionService`의 테스트는 `domain/exam/service/ExamSessionServiceTest`에 둔다. 여러 계층을 함께 도는 통합 테스트는 기능 폴더 바로 아래(`domain/exam/ExamFlowIntegrationTest`)에 둔다. 기능 폴더 바로 아래 클래스는 테스트 폴더에서만 허용한다.

## 지키게 하는 방법

폴더와 이름 규칙 검사는 `global/config/PackageRules` 한 곳에만 적고, 아래 세 곳에서 같은 검사를 돌린다.

1. **서버를 켤 때**: 규칙을 어긴 클래스가 있으면 서버가 뜨지 않고, 어긴 클래스 목록을 보여 준다. IntelliJ에서 `PairApplication`을 바로 실행해도 검사가 돈다. 운영 서버에서는 끈다.
   - 예: `@RestController`가 `controller/` 밖에 있거나, `controller/` 안 클래스 이름이 `Controller`로 끝나지 않으면 서버가 뜨지 않는다.
2. **Gradle로 빌드·실행할 때**: `./gradlew build`, `bootRun`, `bootJar`가 실패한다.
3. **CLAUDE.md**: pAIr-back의 `CLAUDE.md`에 이 규칙을 적어 둔다. AI로 코드를 만들 때도 같은 구조로 만들게 하기 위해서다.

GitHub Actions(push할 때 자동 검사)는 쓰지 않기로 했다. 서버를 켜는 순간 걸리므로 따로 두지 않는다.

이동 작업 순서 (커밋을 나눈다):

1. **옮기기만 하는 커밋**: `git mv`로 옮기고 import만 고친다. 동작은 바뀌지 않으며, 전체 테스트가 통과해야 한다. 순수 이동 커밋이어야 git이 이름 변경으로 인식해 팀원 브랜치와 충돌이 줄어든다.
2. **`ApiController` 나누기**: URL은 그대로 두고 컨트롤러만 기능별로 나눈다.
3. **이름 규칙 맞추기**: `Record` 끝말 떼기, `XxxDtos`를 요청·응답별 파일로 나누기 등 이름 규칙에 맞게 바꾼다. 동작과 API 모양은 그대로 둔다.
4. **구조 검사 추가**: 서버 시작, 테스트, Gradle 빌드·실행에 같은 검사를 연결한다.

이동 작업 전에 팀원들이 진행 중인 브랜치를 `develop`에 반영하게 하고, 개편 브랜치가 올라간 뒤에는 각자 `git merge origin/develop`으로 받는다.
