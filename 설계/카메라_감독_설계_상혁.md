# 카메라 감독 설계 (상혁)

> 작성: 상혁 · 2026-11-23
> 정현의 [카메라_감독_설계.md](카메라_감독_설계.md)(서버 GPU 추론 제안)와 **별개의 문서**다. 이 문서는 2026-11-23 확정한 방향을 따른다: **분석은 응시자 PC 브라우저에서 한다.** 어느 설계를 기준으로 삼을지는 팀 결정이 필요하다.
> 근거: [이벤트-증거구간-검토-보관연장.md](../docs/intent/이벤트-증거구간-검토-보관연장.md)(확정 의도), [Worker_분리_설계.md](../기술검증%20및%20개선/상혁/Worker_분리_설계.md)(실측), [실전시험_감독_API.md](../API/실전시험_감독_API.md)

## 1. 한 줄 요약

- 응시자 PC 웹캠(앞)과 휴대폰 후면 카메라(뒤)를 **응시자 PC 브라우저**가 분석하고, 서버는 분석하지 않는다.
- 이벤트(경고)가 나면 **앞 8초·뒤 4초** 사진(최대 24장)을 올려 파일 저장소에 두고, 감독관·매니저가 **완료된 회차에서도** 확정/기각한다.
- 연속 녹화, 영상 스트리밍(휴대폰 → PC), 서버 추론, 휴대폰 분석은 하지 않는다.

## 2. 구현 상태

| 구분 | 내용 | 상태 |
|---|---|---|
| 구현됨 | PC 웹캠 분석(얼굴·포즈, MediaPipe), 규칙 엔진, 이벤트 + 사진 1장 업로드, 감독관 영상 보기(P2P, 개발 릴레이) | main |
| 구현됨 | 분석 Web Worker 분리(감독 루프·환경 점검), 환경 점검 성능 자가 측정(휴대폰 분석 비용 포함) | 프론트 `main`, 실제 카메라 검증 전 |
| 구현됨 | 휴대폰 JPEG 프레임 서버 중계(운영 WebSocket `/ws/proctor`), 휴대폰 분석 Worker(웹캠 Worker 와 분리), `PHONE_CAM_ENABLED=true` | 백엔드 `develop`, 프론트 `main`, 실기기 확인 전, 서버 상한 임시값 |
| 구현됨 | 이벤트 증거 구간 업로드·조회(`/clip`), 콘솔 타임라인·완료 회차 검토 | 백엔드 `develop`(V24), 프론트 `main`, Playwright 시나리오 |
| 구현됨 | 보관 연장(회차 단위, 삭제 2일 전부터 7일씩 최대 2번, 이력), 동의 문구 v2, 보관 기본 7일 | 백엔드 `develop`(V23), 프론트 `main` |
| 미구현 | `quality`(화질) 제어 신호의 운영 중계 전달, 취소·미시작 회차 연장 차단, 입장 토큰 재검증 | 남은 일 |

## 3. 구조

```
응시자 휴대폰 ─(JPEG 프레임)→ 서버(중계, 분석 안 함) ─→ 응시자 PC(브라우저)
                                                         ├─ 웹캠 분석 Worker ─┐
                                                         └─ 휴대폰 분석 Worker ┴→ 규칙 엔진 → 이벤트
 PC 로컬 링 버퍼(웹캠·휴대폰 프레임, 앞 8초) + 이벤트 후 4초 수집
        └─ 이벤트 후 약 5초 뒤 업로드 ─→ 서버/파일 저장소 ─→ 감독관·매니저 콘솔(타임라인, 확정/기각)
```

### 3-1. 휴대폰 → 서버 → PC (구현됨, 실기기 확인 전)
- 해상도를 고정한 JPEG, 장당 약 13~15KB(기종별 화질 자동 조절). 아이폰은 같은 설정에서 갤럭시의 1.6~1.8배라 화질을 더 낮춘다.
- 변화가 없으면 건너뛰고(평균 변화량 약 0.04, 작은 물체를 놓치지 않게 영역별 변화량을 검토) 5초마다 생존 신호를 보낸다.
- 서버는 오래된 프레임을 버리고 최신만 전달하며, 동시 접속·초당 프레임 상한을 둔다. 메시지는 바이너리, 무신호 판정은 15초(생존 신호 5초). TURN 은 필요 없고 운영 릴레이(Spring WebSocket)가 필수다.

### 3-2. 분석 (PC 브라우저)
- 웹캠 분석 Worker 와 휴대폰 분석 Worker 를 **둘로 나눈다**(한쪽 지연·실패가 다른 쪽에 번지지 않게). Worker 가 안 되면 메인 스레드로 폴백(`VisionBackend` 구조 재사용).
- 앞(웹캠) 규칙: 얼굴 없음, 여러 얼굴, 고개 돌림·숙임, 시선 이탈, 자리 이동, 몸 돌림. 뒤(휴대폰) 규칙: 양손 화면 이탈, 휴대폰, 다른 화면, 책 (`core/pcRules.ts`, `core/phoneRules.ts`).
- 느린 PC: 환경 점검에서 분석 속도를 재서 느리면 두 분석의 간격을 함께 늘린다. 저사양 측정 도구(`lowspec-bench`)에 휴대폰 Worker 를 추가했으나 코어 제한에서 Worker 둘이 동시에 돌 때의 측정 결과는 아직 없다.

### 3-3. 증거 구간
- 앞 8초 / 뒤 4초(시간 기준, 최대 24장). PC 가 로컬 링 버퍼에 두었다가 이벤트가 나면 올린다(연속 업로드 없음). 업로드는 이벤트 후 약 5초 뒤.
- 파일은 DB 가 아니라 파일 저장소에, DB 에는 키와 이벤트 정보만 둔다.
- API·테이블: [API §7](../API/실전시험_감독_API.md), [테이블 정의서](erd/테이블_정의서.md)(V23·V24, 이름은 `proctor_event_frames`·`snapshot_retention_extensions`).

### 3-4. 검토와 보관
- 감독관·매니저가 완료된 회차에서 이벤트별 구간을 타임라인으로 보고 확정/기각(기존 판정 `OK`/`SUSPECT`). 모델은 선별만, 판단은 사람이다.
- 사진은 회차 종료 7일 뒤 삭제. 삭제 2일 전부터 **회차 단위**로 7일씩 최대 2번(총 21일) 연장하고, 누가 언제 연장했는지 이력을 남긴다. 알림은 콘솔 표시만(메일·푸시 없음).
- 동의 문구: "7일 뒤 삭제, 최대 2번 연장 가능(총 21일)".

## 4. 실측 근거 요약 (자세한 내용·한계는 Worker 설계 문서)

| 항목 | 결과 | 한계 |
|---|---|---|
| 코어 제한 1코어(약 2.5배 느림) | 메인 방식 막힘 87%·9fps, Worker 1%·116fps (분석은 초당 3.7회로 느려짐) | 조건당 1회, 정지 얼굴 이미지 입력 |
| 휴대폰 JPEG(480×360, 0.5) | 갤럭시 13.4KB, 아이폰 22.0KB, 만드는 시간 8~20ms | 기종별 1대, 장면 1가지 |
| 변화 감지 0.04 | 정지 구간 전송 20~30% | 작은 물체 변화는 평균 변화량으로 놓칠 수 있음(미측정) |

## 5. 미정·위험

- 24장이 채널별인지 합계인지, 프레임 간격, 요청 크기 상한. (확정: 프레임 메시지는 바이너리, 무신호 판정 15초 유지, `quality` 는 평소 낮음·책상 스캔 때만 높음, 서버 동시 접속·초당 프레임 상한과 오래된 프레임 버리기. 상한 값은 임시값으로 구현했고 실측 전. `quality` 신호는 아직 운영 중계에 없다)
- 휴대폰 분석(손·물체)의 PC 비용은 측정 결과가 없다(측정 도구는 준비됨). 코어가 적은 PC 에서 Worker 둘이 코어를 나눠 쓰면 분석 속도가 더 떨어질 수 있다.
- 모든 프레임이 서버를 지나므로 대역폭·무료 한도·대기열 설계가 필요하다(100대 동시 2시간 약 19~32GB, 건너뛰기 전 추정).
- 분석이 응시자 PC 에서 이루어지므로 결과 조작 가능성이 남는다. 사람이 사진 구간을 보는 검토와 브라우저 이벤트·감독관 영상 보기로 줄이되 완전한 방어는 아니다.
