# 블루그린 배포 설계 (검토안)

> 작성: 팀원 1(성진), 2026-11-27
> 상태: **일정 없음.** 적용하기 전에 고칠 것과 설계를 정리한 문서다. 코드는 아직 바꾸지 않았다.
> 기준 코드: pAIr-back `develop` `c8c866e`, 배포 `deploy.yml`·`docker-compose.prod.yml`·`docker/frontend.Dockerfile`

## 1. 왜 이 문서가 필요한가

블루그린은 새 버전(그린)을 옛 버전(블루) 옆에 띄우고, 그린이 정상인 것을 확인한 뒤 요청을 그린으로 돌리는 배포 방식이다.
**전환하는 동안 두 서버가 동시에 떠 있다.** 지금 백엔드는 곳곳이 "서버는 하나"를 전제로 짜여 있어서, 그대로 블루그린을 하면
채점이 두 번 돌고 안내 메일이 두 번 나가는 등의 사고가 난다. 이 문서는 그 전제를 모두 찾아 대응을 정하고, 배포 절차를 설계한다.

## 2. 지금 배포 방식

| 항목 | 지금 |
|---|---|
| 서버 | 앱 서버 EC2 1대(백엔드·프런트·Caddy·Redis·Prometheus·Grafana 를 compose 로), 샌드박스 서버 EC2 1대(코드 실행), DB 는 RDS |
| 요청 경로 | Caddy(443) → 프런트 nginx(`frontend:80`) → `/api/`·`/ws/` 만 백엔드(`backend:8180`) |
| 백엔드 찾기 | nginx 가 Docker 내부 DNS 로 `backend` 이름을 요청 때마다 풀고 10초 캐시(`resolver 127.0.0.11 valid=10s`) |
| 배포 | Release → `deploy.yml`: 새 이미지 받기 → `docker compose up -d --force-recreate backend` → `/actuator/health/core` 가 UP 일 때까지 확인 |
| 끊김을 줄이는 장치 | graceful 종료(요청 30초), 하던 채점 최대 90초 마무리, `stop_grace_period: 150s`, 서버 시작 시 끊긴 채점 복구 |
| 남는 끊김 | 옛 백엔드가 내려가고 새 백엔드가 뜨는 동안(수십 초) API 가 실패한다. 진행 중이던 AI 채팅 스트림과 감독 WebSocket 은 끊긴다 |

## 3. 블루그린 흐름(목표)

```
1. 블루(backend-blue)가 "backend" 이름으로 요청을 받는 중
2. 그린(backend-green)을 새 이미지로 띄운다. 아직 "backend" 이름이 없어 요청은 오지 않는다
3. 그린의 /actuator/health/core 가 UP 이고, 가벼운 확인 요청이 통과하면
4. 네트워크 별칭 "backend" 를 그린에 붙이고 블루에서 뗀다 → nginx 가 10초 안에 그린으로 보낸다(nginx 재시작 없음)
5. 블루는 새 요청이 끊긴 뒤 진행 중인 요청·스트림이 끝나기를 기다린다(드레인, 5분)
6. 블루를 끈다. 문제가 생기면 4번을 거꾸로 해서 블루로 되돌린다(블루를 끄기 전까지)
```

전환 방법은 두 가지를 비교했다.

| 방법 | 장점 | 단점 |
|---|---|---|
| **Docker 네트워크 별칭 옮기기(추천)** | nginx 설정·재시작이 필요 없다. 지금의 10초 DNS 캐시를 그대로 쓴다 | 최대 10초 동안 두 서버로 요청이 섞인다(아래 4장의 대응이 필요한 이유) |
| nginx upstream 바꾸고 reload | 전환 시점이 분명하다 | 프런트 이미지의 nginx 설정을 템플릿으로 바꾸고, 배포 스크립트가 프런트 컨테이너 안을 고쳐야 한다 |

어느 방법이든 **두 서버가 겹치는 시간은 0 이 아니다.** 드레인 5분 동안은 블루도 주기 작업을 계속 돌리므로, 겹침 대응은 필수다.

### 4.1 한눈에 보기

|---|---|---|---|---|---|

### 4.2 채점 복구를 "작업자 생존 신호" 방식으로 (1·2번)

지금 두 복구는 **"시작할 때 남아 있는 것은 죽은 프로세스의 것"** 이라는 가정 위에 있다. 서버가 하나면 빠른 복구지만, 둘이면 살아 있는 서버의 일을 가로챈다.
같은 저장소의 AI 과제 생성 작업자(`TaskGenJobService`)는 이미 맞는 방식을 쓴다: 돌리는 서버가 30초마다 heartbeat 를 남기고, 2분 넘게 끊긴 작업만 다시 줍는다. 채점도 이 방식으로 바꾼다.

- **DB 복구(1번)**: 채점 기록(`scorings`)의 `RUNNING` 행에 `worker_id`·`heartbeat_at` 을 둔다. 채점하는 서버가 30초마다 갱신한다.
  서버 시작 때가 아니라 **주기 작업**으로, heartbeat 가 2분 넘게 끊긴 `RUNNING` 만 닫고 그 응시를 다시 맡긴다. 4.3 의 ShedLock 으로 한 서버만 돌게 한다.
  `RUNNING` 기록이 없는 `SCORING` 응시(큐를 켜기 전 데이터 등)는 만든 지 일정 시간이 지난 것만 맡긴다.
- **Redis 큐 복구(2번)**: 시작할 때의 `recoverStale(Duration.ZERO)` 를 없앤다. 이미 있는 주기 복구(`stale-after`, 기본 15분)만 남긴다.
  강제 종료(SIGKILL) 뒤 복구가 즉시에서 최대 15분으로 늦어진다. 줄이려면 작업자가 처리 중인 작업의 idle 시간을 주기적으로 갱신(`XCLAIM` 으로 자기 자신에게 다시 받기)하고 `stale-after` 를 2~3분으로 낮춘다.
- **마이그레이션**: `scorings` 에 컬럼 2개 추가(4.7 규칙상 안전).

### 4.3 주기 작업을 ShedLock 으로 (3번)

ShedLock 은 DB 에 잠금 표(`shedlock`)를 두고, 같은 이름의 작업을 한 번에 한 서버만 돌게 한다. DB(RDS)가 이미 공용이라 붙이기 쉽다.

| 작업 | 주기 | 잠금 | 겹치면 |
|---|---|---|---|
| `ExamSchedulerService.closeEndedSessions` | 2초 | **필요** | 끝난 회차 마무리가 겹침 |
| `ExamSchedulerService.expireAbsentLinks` | 30초 | 필요 | 링크 만료 처리 겹침 |
| `ExamSchedulerService.sendReminders` | 5분 | **필요** | **안내 메일 두 번** |
| `ExamSchedulerService.purgeSnapshots` | 1시간 | 필요 | 사진 삭제 겹침(결과는 같지만 낭비) |
| `CreditPurchaseCleanupService.expireReady` | 1시간 | 필요 | 조건부 UPDATE 라 결과는 같음 |
| `CreditRefundRecheckService.recheck` | 5분 | 필요 | 행 잠금·전액 취소 1회라 안전하지만 토스 호출이 두 배 |
| `BatchCallService.scheduled` | 2초 | 확인 필요 | 배치 결과 수거가 겹치는지 코드 확인 |
| `TaskGenJobService.tick`·`heartbeat` | 5초·30초 | **걸지 않는다** | 이미 작업자별 heartbeat 로 나눠 줍는 구조. 서버마다 돌아야 한다 |
| `ProctorRelayService.checkStale` | 2초 | **걸지 않는다** | 각 서버가 자기 메모리의 연결을 정리하는 작업 |
| 4.2 의 새 채점 복구 | 1분 | 필요 | |

`lockAtMostFor` 는 작업이 걸리는 시간보다 넉넉히(예: 2초 작업은 30초), `lockAtLeastFor` 는 주기보다 조금 짧게 둔다.

### 4.4 응시별 메모리 잠금 (4번)

`AttemptService` 는 같은 응시의 채팅·파일 저장·제출을 `synchronized (lock(id))` 로 차례로 처리한다. 두 서버면 이 보호가 서버마다 따로다.
중요한 상태 변경은 이미 DB 조건부 UPDATE 로 막혀 있다(제출 `startScoring`, 재채점 `startRescoring`, 크레딧은 회원 행 잠금).
블루그린 전에 **이 잠금에만 기대는 흐름**을 점검한다. 예: 채팅 기록 저장 순서, 체크포인트 번호, 파일 저장과 제출 사이. 필요한 곳만 DB 행 잠금(응시 행 `PESSIMISTIC_WRITE`)으로 옮긴다.
겹치는 시간이 10초 남짓이라, 점검 결과 문제가 없으면 그대로 두어도 된다.

### 4.5 분당 제한을 Redis 로 (5번)

| 제한 | 지금 | 옮길 때 | Redis 가 멈추면 |
|---|---|---|---|
| 로그인 실패 횟수 | 메모리, 재배포하면 초기화 | **1순위**(보안 장치) | 막는다(fail-closed) |
| IP 별 가입·인증 메일·기업 문의 | 메모리 | 2순위 | 메모리 제한으로 대신한다 |
| AI 채팅 1인 10·전체 300 | 메모리 | 3순위 | 메모리 제한으로 대신한다(채팅까지 막지 않게) |
| 빌드·실행 | 메모리 | 3순위 | 메모리 제한으로 대신한다 |

방식은 키마다 정렬 집합(ZSET)에 시각을 넣고 1분이 지난 것을 지우는 이동 창(지금 메모리 방식과 같은 결과), 또는 분 단위 `INCR`+`EXPIRE` 고정 창(간단하지만 경계에서 두 배까지 허용).
전환이 몇 분뿐이라 블루그린만 놓고 보면 꼭 필요하지는 않다. 다만 로그인 실패 제한이 배포마다 초기화되는 것은 지금도 있는 약점이다.

### 4.6 드레인과 배포 금지 시간 (6·7번)

- **드레인**: 별칭을 옮긴 뒤 블루를 **5분 30초** 기다렸다 끈다. nginx 가 API 응답을 최대 300초 기다리므로(채팅 스트림이 가장 길다) 그 안에 끝난다.
  지금 `stop_grace_period: 150s` 는 채팅 스트림을 다 기다리지 못한다. 블루는 기다리는 동안 새 요청을 받지 않으므로 하던 채점(최대 90초)도 이 안에 끝난다.
- **배포 금지 시간**: 진행 중인 실전 회차(시작~종료 사이, 취소 안 됨)가 있으면 배포 스크립트가 **기다리거나 멈춘다.** 감독 WebSocket 은 블루에 붙어 있어 옮겨 갈 수 없다.
  연결 유예(V11)로 응시자가 다시 붙을 수는 있지만, 감독관 실시간 보기와 프레임 중계가 끊기는 것을 시험 중에 일부러 만들 이유가 없다.
  확인은 관리용 내부 API(예: `GET /internal/live-sessions`, 공유 토큰) 또는 DB 조회로 한다.

### 4.7 마이그레이션 규칙(expand → contract)

블루(옛 코드)가 **새 스키마** 위에서 드레인 동안 계속 돈다. 또 블루로 되돌릴 수 있으려면 새 스키마가 옛 코드와도 맞아야 한다.

- **한 배포에 해도 되는 것**: 테이블·컬럼 추가(NULL 허용 또는 기본값), CHECK 에 값 추가(예: V32 의 `REFUNDING`), 인덱스 추가.
- **두 배포로 나눌 것**: 컬럼 이름 바꾸기(새 컬럼 추가·양쪽 쓰기 → 다음 배포에서 옛 컬럼 삭제), 컬럼 삭제(코드에서 먼저 안 쓰기 → 다음 배포에서 삭제), NOT NULL 추가(값 채우기 → 다음 배포에서 제약).
- **하지 않을 것**: 블루가 아직 쓰는 값을 CHECK 에서 빼기, 테이블 이름 바꾸기.
- 마이그레이션은 그린이 뜰 때 Flyway 가 적용한다. 되돌리기(DOWN)는 쓰지 않는다. 문제가 생기면 고치는 새 마이그레이션을 더한다.

## 5. 인프라와 배포 스크립트

- **compose**: `backend` 를 `backend-blue`·`backend-green` 두 서비스로 나누고, 둘 다 같은 이미지 태그 변수(`BLUE_TAG`·`GREEN_TAG`)를 받는다. 지금 손으로 쓰는 절차("서비스 이름을 붙여 `up -d`")와 `BACKEND_TAG` 설명도 함께 고친다.
- **배포 스크립트(`deploy.yml` 의 원격 부분)**:
  1. 진행 중 실전 회차 확인(있으면 대기, 최대 N분 뒤 실패)
  2. 지금 별칭을 가진 쪽(블루)을 찾고, 반대쪽(그린)을 새 태그로 띄움
  3. 그린의 `/actuator/health/core` UP + 가벼운 확인 요청(예: `GET /api/tasks` 401/200) 통과
  4. `docker network disconnect` / `connect --alias backend` 로 별칭을 그린으로
  5. 20초 뒤 HTTPS 로 확인 → 실패하면 별칭을 블루로 되돌리고 실패 처리
  6. 5분 30초 드레인 뒤 블루 중지
- **메모리**: 앱 서버 EC2 한 대에서 백엔드 JVM 두 개가 5분 넘게 같이 뜬다. 인스턴스 메모리와 백엔드 힙 설정으로 백엔드 두 개 + Redis + Prometheus + Grafana 가 버티는지 먼저 확인한다(**앱 서버 사양 확인 필요**). 모자라면 드레인 동안만 Grafana 를 멈추는 것도 방법이다.
- **모니터링**: Prometheus 수집 대상을 두 백엔드로 늘리고, 경고(`ScoringQueueDown` 등)는 서버별로 두 번 뜨지 않게 `max`/`min` 으로 묶는다. 대시보드에 "지금 요청을 받는 쪽" 표시가 있으면 좋다.
- **프런트**: 이번 범위가 아니다. 프런트는 정적 파일이고 `index.html` 을 캐시하지 않게 해 두었다. 다만 배포 직후 이미 열려 있던 탭이 옛 JS 조각 파일을 늦게 불러오다 404 가 나는 문제는 블루그린과 별개로 남아 있다(옛 `assets/` 를 한동안 같이 두면 해결).

## 6. 작업 순서와 크기

| 단계 | 내용 | 크기(대략) |
|---|---|---|
| 1 | ShedLock 도입과 주기 작업 잠금(4.3) | 반나절 |
| 2 | 채점 복구를 생존 신호 방식으로(4.2), 마이그레이션 1개 | 1~2일(가장 위험하고 테스트가 많다) |
| 3 | 응시별 잠금 점검(4.4) | 반나절 |
| 4 | 배포 스크립트·compose·드레인·배포 금지 확인(4.6, 5장) | 1일 |
| 5 | 로그인 실패 제한부터 Redis 로(4.5) | 반나절~1일 |
| 6 | 모니터링 수집 대상·경고 정리 | 반나절 |

1~4 단계가 끝나야 블루그린을 켤 수 있다. 5·6 은 그 뒤에 해도 된다. 1·2 단계는 **블루그린을 안 하더라도** 수동으로 서버를 두 개 띄우는 실수에 대한 안전장치가 되므로 먼저 해 둘 가치가 있다.

## 7. 지금 판단

- 앱 서버가 1대이고, 배포 끊김은 안전한 종료·재시작 복구로 이미 줄였다. 남은 끊김은 수십 초이고 배포 시각을 고르면 피할 수 있다.
- 블루그린을 제대로 하려면 위 1~4 단계(약 3~4일)가 필요하고, 그중 채점 복구 변경이 가장 위험하다.
- 그래서 **12/5 구현 마감 전에는 하지 않는다.** 발표에서는 이 문서의 "서버 하나 전제 목록"과 대응 설계를 확장 계획으로 다룬다.

## 8. 정할 것

- 블루그린을 할지와 시점(실제 서비스 운영을 이어 갈 때)
- 전환 방법: 네트워크 별칭(추천) / nginx reload
- 분당 제한을 Redis 로 옮기는 범위와 Redis 가 멈췄을 때의 정책
- 앱 서버 사양(두 JVM 을 띄울 메모리)
