# 좋은 과제 기준

> 작성일: 2026-11-24
> AI 과제 생성기(프롬프트, 자동 검사)와 검수(관리자, 검증 세션)는 이 문서를 기준으로 한다. 기준을 바꿀 때는 이 문서를 먼저 고치고 코드를 맞춘다. 코드에는 이 문서의 번호(M1, Q2 등)를 주석으로 단다.
> 관련: [AI_과제_생성_설계.md](AI_과제_생성_설계.md), [채점_기준표.md](../평가/채점_기준표.md)

## 1. 핵심 정의

**AI를 쓰면 빨라지지만, AI 답을 그대로 받아들이면 함정에 걸려서, 문제를 나누고 AI 결과를 검증하고 판단하는 사람이 더 높은 점수를 받는 과제.**

pAIr는 AI 협업 역량을 잰다. 정답이 맞는 과제여도 AI 답을 그대로 내서 통과하거나 자료가 답을 알려 주면, 응시자 사이에 역량 차이가 드러나지 않으므로 좋은 과제가 아니다. 반대로 AI를 써도 못 풀 만큼 꼬아 둔 과제도 좋은 과제가 아니다(Q2, Q3).

## 2. 필수 조건 (하나라도 어기면 쓰지 않는다)

| # | 조건 | 자동 검사 |
| --- | --- | --- |
| M1 | **풀 수 있다.** 응시자에게 주는 자료만으로 무엇이 맞는 결과인지 정할 수 있고, 빠진 정보나 서로 모순되는 내용이 없다. | 정답 실행(DEV), 단답형 검산·다른 회사 모델이 풀기(BIZ) |
| M2 | **맞는 풀이는 모두 인정한다.** 정답과 다른 방식이라도 요구사항을 지킨 풀이는 통과한다. 테스트와 인정 답안은 결과만 보고, 특정 구현 구조를 전제하지 않는다. | 다른 방식의 올바른 풀이도 통과(DEV), 인정 답안(BIZ) |
| M3 | **함정이 결과를 가른다.** 함정에 빠진 풀이는 DEV에서는 숨은 테스트에 걸리고, BIZ에서는 결론(추천안, 통과 여부)이 달라진다. | 그럴듯한 오답을 걸러냄(DEV), 함정이 결론을 바꿈(BIZ) |
| M4 | **답을 알려 주지 않는다.** 아래 '명세와 답 노출의 경계'를 지킨다. | 함정 핵심어 노출, 힌트 주석, 해법 문장, 지시문 말투, 정답 노출 (일부만 자동, 나머지는 검수) |
| M5 | **AI 답을 그대로 내면 함정에 걸린다.** 과제 설명과 자료를 그대로 AI(응시 화면과 같은 모델)에 붙여 넣고 나온 답을 손대지 않고 내면 M3의 함정에 걸린다. 실전(LIVE)과 자가진단(SELF) 모두 지킨다(자가진단도 AI 답을 그대로 내서 통과하면 역량을 잴 수 없다). | AI 혼자 풀기(DEV), AI 답을 그대로 내면 함정에 걸림(BIZ). 둘 다 실패 처리 |

**명세와 답 노출의 경계 (M1과 M4)**
- 줘도 되는 것(명세): **무엇이 맞는 결과인지.** 입력과 기대 출력의 예, 항상 성립해야 하는 조건, 현상과 재현 값, 측정 범위나 집계 정의 같은 사실.
- 주면 안 되는 것(답 노출): **왜 틀렸는지, 어디를 어떻게 고칠지.** 원인, 버그 위치, 고치는 방법, 계산 순서나 절차, "~해야 한다/~만으로 판단하지 않는다" 같은 지시.
- 함정을 피하는 데 꼭 필요한 기대 결과(예: 끝나는 시각에 바로 시작하는 예약)는 여러 예 가운데 하나로 둔다. 따로 떼어 규칙 문장으로 강조하지 않는다.

## 3. 품질 조건 (어기면 고쳐서 쓴다)

| # | 조건 |
| --- | --- |
| Q1 | **분량이 제한시간에 맞다.** 5장의 기본값을 따른다. 난이도는 제한시간으로 정한다(5장). |
| Q2 | **현실적이다.** 실제 업무에서 볼 법한 상황, 자료, 말투다. 일부러 만든 티가 나는 오답이나 어색한 설정이 없고, 읽기 어렵게 꼬아 둔 코드나 문장이 없다. |
| Q3 | **함정은 꼼꼼히 확인하면 피할 수 있다.** 함정의 근거가 응시자 자료에 사실로 들어 있다. 속임수나 자료 밖의 지식이 필요한 함정은 쓰지 않는다. |
| Q4 | **검증하는 행동이 결과로 이어진다.** AI 답을 자료나 테스트와 대조하면 함정이 드러나고, 한 번의 질문으로 끝나지 않고 나눠서 확인할 거리가 있다. 그래서 통제력, 문제 분해력, 위임 판단력에서 점수 차가 난다. |
| Q5 | **특정 업계 지식이 없어도 풀 수 있다.** 필요한 용어와 규칙은 자료 안에 있다. |
| Q6 | **같은 회차의 실전 과제끼리 난이도가 비슷하다.** 응시자마다 다른 과제를 받아도 공정해야 한다. |

## 4. 직군별 조건

**개발 (DEV)**
- 시작 코드는 컴파일되고 공개 테스트를 통과한다. 숨은 테스트에서만 실패한다.
- 원인이 시작 코드의 한 줄에서 바로 보이지 않는다(예: `return pages + 1;`처럼 눈에 띄는 한 줄은 안 된다).
- 흔한 첫 수정은 NOTES.md의 사례는 통과하지만 숨은 테스트에는 걸린다.
- 숨은 테스트는 NOTES.md 사례 밖에서 같은 원인으로 생기는 경계 사례를 1개 이상 포함한다.
- 동시성 테스트는 결과(재고가 음수인지, 승인 개수 등)만 확인한다. 대기 장치는 시간이 지나면 그냥 진행하고, 맞는 풀이를 시간 초과로 떨어뜨리지 않는다.
- 요구사항과 NOTES.md는 2장 경계의 '줘도 되는 것'만 쓴다.

**비개발 (BIZ)**
- 근거 문서가 2개 이상이고, 모든 계산을 자료의 숫자로 다시 할 수 있다.
- 함정 근거는 사실 진술(측정 범위, 집계 정의, 같은 기간에 있었던 일)로 쓰고, 다른 내용과 같은 문단에 섞는다.
- 용어 정의는 무엇을 뜻하는지만 쓰고, 어떻게 구하는지(계산 절차)는 쓰지 않는다.
- 자료의 '검토 중인 안'은 정답이 아니다. 대안 중 1개 이상은 함정에 빠진 사람이 고를 안이다.

## 5. 시간별 분량 (기본값)

실제 응시 시간으로 검증하기 전의 기본값이다. 파일럿 응시 기록(제한시간 대비 걸린 시간, 점수 분포)이 쌓이면 다시 정한다.

난이도는 생성 AI가 정하지 않고 제한시간으로 정한다: 20분 초급, 40분 중급, 60분 고급. 시간이 곧 깊이(고칠 곳 수, 따라갈 파일 수)를 정하기 때문이다.

| 제한시간 | 개발 | 비개발 |
| --- | --- | --- |
| 20분 | 파일 2~3개, 버그 1개, 숨은 테스트 1~2개 | CSV 1개 + 문서 2개(각 1~2쪽), 문항 3개, 자료 합계 1,500~4,000자 |
| 40분 | 파일 3~5개, 버그 1~2개, 두 곳 이상을 함께 고쳐야 함 | CSV 1~2개 + 문서 2개, 문항 4개 |
| 60분 | 파일 4~6개, 여러 파일을 따라가야 원인이 드러남, 교과서 패턴 하나로는 안 풀림 | CSV 1~2개 + 문서 2~3개, 문항 4~6개 |

## 6. 누가 무엇을 보나

| 단계 | 보는 것 |
| --- | --- |
| 생성 프롬프트 | 1~5장 전체를 생성 규칙으로 넣는다. |
| 자동 검사 | M1~M5와 4장 중 기계로 확인할 수 있는 것. 필수 조건을 어기면 실패(1회 다시 생성), 품질 조건은 경고. |
| 관리자 검수 | 자동으로 확인할 수 없는 M4(다른 말로 쓴 답 노출)와 Q1~Q6. 실전 회차에 과제를 걸 때 Q6. |
| 검증 세션 (생성기를 고칠 때) | 이 문서의 M, Q 번호로 판정하고, 여러 과제에 반복되는 문제를 생성기 개선안으로 정리한다. |

## 7. 아직 정하지 않은 것

- 비개발 M5 자동 검사: 지금 '다른 회사 모델이 풀기'는 풀 수 있는지(M1)를 본다. AI 답을 그대로 내면 함정에 걸리는지를 보는 검사는 아직 없다.
- Q4, Q6 자동 확인: 파일럿 응시 기록으로 과제별 점수 분포와 걸린 시간을 보는 방법을 정한다.
