# 디자인 패턴 검토

> 2026-11-19 초안. [역할_분담.md](../기획/역할_분담.md)의 기능 전체를 놓고, 어디에 어떤 패턴을 쓸지 후보를 비교해 정한다.
> "있음"은 pAIr-back 코드에 이미 있는 것, "할 것"은 구현할 때 적용할 것. 팀 회의에서 확정한다.

## 고르는 기준

1. **바뀔 곳에만 쓴다.** 구현이 2개 이상이거나 곧 늘어날 곳(채점 모델, 저장소, 실행 서버)만 인터페이스로 나눈다. 하나뿐인 곳에 패턴을 넣으면 파일만 늘어난다.
2. **Spring이 이미 주는 것을 먼저 쓴다.** 빈 주입(Strategy 교체), `@ConditionalOnProperty`(설정으로 구현 고르기), `@TransactionalEventListener`(Observer), Security 필터(Chain of Responsibility), AOP(Proxy). 직접 만든 패턴보다 팀원이 읽기 쉽다.
3. **테스트가 쉬워지는지 본다.** 외부 API(LLM, S3, Docker)를 인터페이스 뒤로 숨기면 가짜 구현으로 테스트할 수 있다. 지금 `DualJudgeTest`가 이렇게 돈다.
4. **면접에서 "왜"를 말할 수 있는 것만 남긴다.** 후보와 버린 이유를 이 문서에 적는다.

## 1. 채점 모델 호출: Strategy (있음)

`ai/Judge` 인터페이스에 `ClaudeJudge`, `OpenAiJudge` 두 구현이 있고, `ScoringService`는 `List<Judge>`만 안다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Strategy (인터페이스 + 구현)** | 모델 추가·교체가 설정과 클래스 하나로 끝남. 가짜 Judge로 테스트 가능 | 파일 수가 늘어남 |
| if/else로 회사별 분기 | 처음엔 빠름 | 모델이 늘 때마다 채점 코드를 고침. 테스트에 실제 API가 필요 |
| Spring AI `ChatClient`를 채점 코드에서 바로 사용 | 코드가 짧음 | 프롬프트 캐시, effort 같은 회사별 차이가 채점 코드로 새어 나옴 |

**결정:** 유지. 모델 라우팅(쉬운 체크는 작은 모델로)을 하게 되면 Judge를 고르는 `JudgeRouter`를 하나 더 두면 된다.

## 2. 반복 채점, 비용 기록, 재시도: Decorator (일부 있음)

`ScoringService.Repeated`가 같은 Judge를 감싸 이름만 바꾼다(Decorator). 채점 비용 추적(NFR-CST-01)과 재시도도 같은 방식으로 감싼다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Decorator** (`CostTrackingJudge(RetryingJudge(ClaudeJudge))`) | 무엇이 감싸져 있는지 코드에서 보임. 하나씩 따로 테스트 가능 | 감싸는 순서를 정해 둬야 함(재시도가 안쪽이어야 비용이 한 번만 기록) |
| AOP (`@Around`) | 기존 클래스를 안 건드림 | 동작이 숨겨져 디버깅이 어렵고, 같은 클래스 안에서 부르면 적용 안 됨 |
| Judge 구현마다 직접 코드 | 단순 | Claude, OpenAI에 같은 코드가 두 벌 |

**결정:** Decorator. 감싸는 순서는 `비용 기록 → 재시도 → 실제 호출`.

## 3. 채점 체크 판정: Strategy 목록 (할 것)

지금 `ScoringService.score()` 한 메서드에서 AUTO 체크(U0, D5 등)를 차례로 계산한다. 600줄 클래스의 대부분이 여기다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **AUTO 체크마다 `CheckEvaluator` 구현, Spring이 `List<CheckEvaluator>` 주입** | 체크 하나를 고칠 때 그 클래스만 봄. 체크별 단위 테스트 | 체크가 서로의 결과를 써야 하면(U0이면 다른 항목 0점) 순서 처리가 필요 |
| Chain of Responsibility | 앞 체크 결과로 뒤를 건너뛸 수 있음 | 이 도메인은 "모든 체크를 다 계산"이라 체인의 장점이 없음 |
| 지금처럼 한 메서드 | 흐름이 한눈에 보임 | 체크가 늘수록 메서드가 커지고 테스트가 어려움 |

**결정:** AUTO 체크만 `CheckEvaluator`로 나눈다. JUDGE 체크는 한 번의 LLM 호출로 함께 판정하므로 나누지 않는다. "AI를 안 쓰면 판정 생략" 같은 공통 조건은 평가기를 부르기 전에 처리한다. 체크 구성이 고정(2026-11-12 결정)이라 급하지 않다. DB 전환할 때 같이 한다.

## 4. 채점 흐름 전체: Facade + 단계별 메서드 (정리)

자료 준비 → (비개발) RAG → 두 모델 판정 → 합치기 → 점수 → 리포트 저장.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Facade (`ScoringService.score(attemptId)`) 안에서 private 메서드로 단계 나누기** | 단계 순서가 고정이라 이걸로 충분. 큐 작업자는 메서드 하나만 부름 | 단계를 바꿔 끼울 수 없음(필요 없음) |
| Pipeline / Chain (단계마다 클래스) | 단계 추가·순서 변경이 쉬움 | 단계 사이에 넘길 문맥 객체가 커지고 흐름을 따라가기 어려움 |
| Template Method (개발/비개발 하위 클래스) | 과제 종류별 차이를 하위 클래스로 | 차이는 "자료를 넣느냐" 하나뿐이라 상속은 과함 |

**결정:** Facade 유지. `judgePrefix`, `judgeBody`, `combine`처럼 이미 나뉜 단계를 그대로 두고, 판정 합치기 규칙(`combine`)은 바뀔 일이 적어 패턴을 쓰지 않는다.

## 5. 제출 → 채점: Transactional Outbox + Producer-Consumer (할 것)

시험 종료 순간 100건이 몰려도 하나도 잃지 않아야 한다(팀원 1 "유실 0건").

| 후보 | 장점 | 단점 |
|---|---|---|
| 제출 서비스가 Redis에 바로 넣기 | 가장 단순 | DB 커밋은 됐는데 Redis 넣기 전에 서버가 죽으면 유실. 반대로 Redis엔 넣었는데 DB가 롤백되면 없는 응시를 채점 |
| `@TransactionalEventListener(AFTER_COMMIT)`로 커밋 뒤 Redis에 넣기 | 롤백된 제출은 안 들어감. 초대 메일에서 이미 씀 | 커밋 직후 서버가 죽으면 여전히 유실 |
| **Outbox: 제출 트랜잭션에서 응시를 `attempts.status = 'SCORING'`으로 바꿈 → 커밋 뒤 Redis에 넣고, 주기 작업이 "SCORING인데 DONE 채점이 없는 응시"를 찾아 Redis에 다시 넣음** | 커밋되면 반드시 언젠가 채점됨. Redis가 메시지를 잃어도 DB에서 되살림. "유실 0건"을 설명할 수 있음 | 다시 넣는 주기 작업이 추가됨. 같은 응시가 큐에 두 번 들어갈 수 있음(6번에서 막음) |

**결정:** Outbox. 별도 outbox 테이블이나 새 상태 값 없이, 이미 있는 `attempts.status`의 `SCORING`(제출 후 채점 대기·진행)을 "채점할 것" 표시로 쓴다. ERD 변경 없음. 주기 작업은 제출된 지 몇 분이 지났는데도 RUNNING·DONE 채점이 없는 응시만 다시 넣는다(막 넣은 응시를 또 넣지 않게). Redis 큐는 작업자에게 빨리 나눠 주는 용도이고, 진짜 기록은 DB다. 작업자는 Producer-Consumer(동시 작업 수 설정).

## 6. 같은 채점 두 번 실행 막기: 응시 행 잠금 (할 것)

큐 재시도, 5번의 다시 넣기, 작업자 둘이 같은 메시지를 받는 경우에 같은 채점이 두 번 돌고 비용이 두 번 나갈 수 있다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **응시 행 잠금: `SELECT ... FROM attempts WHERE attempt_id = ? FOR UPDATE` → 그 응시에 RUNNING·DONE 채점이 있으면 건너뜀, 없으면 `scorings`에 RUNNING 행을 만들고 커밋 → 그다음 LLM 호출** | ERD 변경과 추가 인프라 없음. 동시에 와도 하나만 RUNNING을 만듦. 테스트로 증명하기 쉬움 | 작업자가 RUNNING에서 죽으면 오래된 RUNNING을 ERROR로 바꾸는 정리 작업 필요(그래야 5번이 다시 넣음) |
| `scorings (attempt_id, version_id)` 유니크 제약 | DB가 강제 | ERROR 뒤 다시 채점하면 같은 조합의 행이 또 필요해 재채점을 막음 |
| Redis 분산 락 | 빠름 | 락 만료와 실제 작업 시간이 어긋나면 두 번 실행. 진실이 DB와 Redis 두 곳 |
| 결과 저장 때 유니크 키로 막기 | 결과 중복은 막음 | LLM 호출(비용)은 이미 두 번 나감 |

**결정:** 응시 행 잠금. 잠금은 RUNNING 행을 만드는 짧은 트랜잭션에서만 잡고, 50초 걸리는 LLM 호출은 잠금 밖에서 한다. DB에서 한 번 더 막고 싶으면 응시당 RUNNING 하나만 허용하는 부분 유니크 인덱스(`... ON scorings (attempt_id) WHERE status = 'RUNNING'`)를 더할 수 있다. 재채점 기록은 막지 않지만 필수는 아니다.

## 7. 응시·회차·채점 상태: enum 상태 전이 표 (할 것)

응시(진행 → 제출 → 채점 중 → 완료), 회차(예정 → 진행 → 종료, 취소는 시작 전만), 채점(RUNNING → DONE/ERROR).

| 후보 | 장점 | 단점 |
|---|---|---|
| State 패턴 (상태마다 클래스) | 상태별 동작이 많으면 깔끔 | 이 프로젝트의 상태는 "다음에 갈 수 있는 곳"만 다름. 클래스가 과함 |
| **enum + 허용 전이 표 (`status.canMoveTo(next)`), 엔티티 메서드에서만 상태 변경** | 한 파일에 규칙이 다 보임. 잘못된 전이를 한곳에서 막음 | 상태별 동작이 커지면 State로 바꿔야 함 |
| 서비스 곳곳에서 if로 검사 | 처음엔 빠름 | 규칙이 흩어져 "취소는 시작 전만" 같은 규칙이 빠지기 쉬움 |

**결정:** enum 전이 표. `setStatus()`를 열지 않고 `submit()`, `cancel()`처럼 의도가 드러나는 엔티티 메서드로만 바꾼다.

## 8. 파일 저장: Strategy (있음, 넓히기)

`exam/service/SnapshotStorage`에 `LocalSnapshotStorage`, `S3SnapshotStorage`가 있고 `pair.exam.snapshot-storage` 설정으로 고른다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **인터페이스 + `@ConditionalOnProperty`** | 개발은 로컬, 운영은 S3. 테스트에 S3가 필요 없음 | 없음에 가까움 |
| 프로필별 if | 단순 | 저장이 필요한 곳마다 분기 |

**결정:** 감독 스냅샷에만 있는 것을 공통 `FileStorage`(과제 파일, 대상자 CSV, 스냅샷, 제출 파일)로 넓힌다(팀원 1). 기능별 경로 규칙은 호출하는 쪽이 정한다.

## 9. 코드 실행: Strategy + Remote Proxy (할 것)

지금 `run/CodeRunner`는 별도 JVM으로 실행한다. 목표는 Oracle 실행 서버의 Docker 컨테이너(기술검증 7~10번).

| 후보 | 장점 | 단점 |
|---|---|---|
| **`CodeRunner` 인터페이스 → `LocalJvmRunner`(개발·테스트), `RemoteDockerRunner`(운영, 실행 서버 API를 부르는 Proxy)** | 개발 PC에 Docker가 없어도 됨. 응시 서비스는 실행 서버가 어디 있는지 모름 | 두 구현의 결과 형식을 똑같이 맞춰야 함 |
| 백엔드가 Docker를 직접 호출 | 단계가 적음 | 응시자 코드가 DB·API 키와 같은 서버에서 돎(서버 구조 결정과 충돌) |
| 메시지 큐로 실행 요청 | 실행 서버 장애에 강함 | 실행 결과를 몇 초 안에 돌려줘야 해서 동기 호출이 맞음 |

**결정:** Strategy + Remote Proxy. 응시자 배정(가장 한가한 실행 서버)은 Proxy 안에서 응시마다 기록된 서버를 고른다. 실행 서버 장애 처리(일시 중지, 시간 보정)도 Proxy가 맡는다.

## 10. 컨테이너 재사용: Object Pool (확장)

| 후보 | 장점 | 단점 |
|---|---|---|
| **웜 풀: 컨테이너를 미리 띄워 두고 응시 시작 때 하나 꺼내 씀** | 시작 대기 1.6초 → 거의 0 | 쓰고 돌려줄 때 작업 폴더를 확실히 비워야 함(다른 응시자 파일이 남으면 사고). 놀고 있는 메모리 |
| 매번 새로 띄우기 | 깨끗함이 보장됨 | 동시 시작이 몰리면 대기 |

**결정:** 확장 단계. 돌려받은 컨테이너는 재사용하지 않고 버리고, 풀은 "미리 띄워 둔 새 컨테이너"만 채운다. 정리 실수가 생길 수 없다.

## 11. 복기 트리: Memento (할 것)

특정 대화 시점의 파일과 대화를 저장해 두고, 그 시점에서 갈라진 새 응시를 만든다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Memento: 체크포인트 = 그 시점 파일 전체(`checkpoint_files`) + 대화 턴 번호(`checkpoints.turn_no`). 새 응시는 체크포인트에서 복원** | 기술검증 8번 그대로(20KB, 0.8초). 원래 응시를 건드리지 않음 | 체크포인트마다 전체 저장 |
| 바뀐 파일만 저장(차분) | 저장 공간이 작음 | 복원할 때 앞 체크포인트를 다 따라가야 함. 하나가 깨지면 뒤도 다 깨짐 |
| Prototype (응시 전체 복사) | 구현이 쉬움 | 대화·이벤트까지 통째로 복사해 커짐 |

**결정:** Memento, 전체 저장(지금 ERD와 같음). 과제 파일이 작아(20KB) 차분의 이득이 없다. 트리는 `checkpoints.attempt_id`(어느 응시의 시점인가)와 `attempts.forked_from_checkpoint_id`(어느 시점에서 갈라졌나)로 이어진다. (역할 분담의 "바뀐 파일만 저장"은 크기 측정 뒤 다시 정한다.)

## 12. 회사 데이터 분리: Hibernate Filter + AOP (할 것)

"개발자가 조건을 빠뜨려도 새지 않게"(팀원 1 포트폴리오).

| 후보 | 장점 | 단점 |
|---|---|---|
| 쿼리마다 `company_id` 조건 직접 | 명시적 | 하나만 빠뜨려도 다른 회사 데이터가 샘 |
| Repository를 감싸는 Proxy | 한곳에서 처리 | 직접 쓴 JPQL·네이티브 쿼리는 못 막음 |
| **Hibernate `@Filter`(회사 조건) + 요청 시작 때 AOP·인터셉터가 로그인한 회사로 필터를 켬** | 엔티티 조회 전체에 자동 적용. "빠뜨려도 안 샘"을 테스트로 증명 | 네이티브 쿼리와 `findById`(필터 미적용)는 따로 검사해야 함 |
| PostgreSQL 행 수준 보안(RLS) | DB가 강제, 가장 확실 | 커넥션마다 회사 값을 넣는 설정, 팀이 익숙하지 않음 |

**결정:** Hibernate Filter + AOP. `findById`로 꺼낸 엔티티는 공통 검사 메서드로 회사를 확인한다. 다른 회사 접근 403 테스트를 같이 만든다.

## 13. 크레딧 차감: 원장 + 회원 행 잠금 (할 것)

ERD는 잔액 칸 없이 `credit_ledger`에 행을 쌓고, 행마다 차감 뒤 잔액(`balance_after >= 0`)을 적는다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **회원 행 잠금(`SELECT ... FROM users WHERE user_id = ? FOR UPDATE`) → 마지막 `balance_after` 읽기 → 새 원장 행 추가** | 지금 ERD 그대로. 같은 회원의 차감만 줄 서고 다른 회원은 영향 없음. `balance_after >= 0` CHECK가 마지막 방어선 | 잠금을 잡는 동안 같은 회원의 다음 요청이 기다림(채팅 턴은 몇 ms라 문제없음) |
| 낙관적 락(`@Version`) | 락 없음 | 채팅 턴처럼 자주 차감하면 충돌·재시도가 많음 |
| `users`에 잔액 칸을 두고 조건부 UPDATE(`... WHERE credit >= ?`) | 쿼리 하나로 음수 불가, 가장 빠름 | ERD 변경 필요, 잔액과 원장 두 곳이 맞는지 따로 지켜야 함 |

**결정:** 회원 행 잠금(역할 분담과 같음). 원장은 고치지 않고 쌓기만 한다(append-only). ERD의 `UNIQUE (attempt_id, reason)`과 `turn_id UNIQUE`가 같은 차감을 두 번 하는 것을 막는 멱등 키 역할을 하므로, 중복 요청은 유니크 위반을 잡아 "이미 처리됨"으로 돌려준다. 동시 차감 테스트(잔액 음수 0건)를 같이 만든다.

## 14. 메일 발송: Observer + Facade (있음, 넓히기)

`ExamSessionService`가 `InvitesCreated` 이벤트를 내면 `InviteMailer`가 커밋 뒤(`AFTER_COMMIT`) 별도 스레드(`@Async`)에서 보낸다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **도메인 이벤트 + 커밋 뒤 비동기 리스너** | 회차 저장이 메일 서버 장애에 묶이지 않음. 롤백되면 메일도 안 나감 | 서버가 죽으면 보내기 전 메일이 사라짐 |
| 서비스에서 바로 발송 | 단순 | 메일이 느리면 회차 저장도 느림, 메일 실패가 저장을 롤백 |

**결정:** 유지하고 공통 `MailSender` Facade(템플릿 + 발송)를 만들어 가입 인증 메일(팀원 1)도 같이 쓴다. 시작 하루 전 알림처럼 꼭 가야 하는 메일은 5번처럼 발송 기록 테이블을 두고 재시도한다.

## 15. 감독 이벤트 실시간 전달: Pub-Sub (할 것)

응시자 브라우저의 감독 이벤트를 감독관 화면에 실시간으로 보여 준다(감독 API의 WebSocket 릴레이).

| 후보 | 장점 | 단점 |
|---|---|---|
| 서버 메모리의 구독자 목록 | 서버 1대면 충분 | 서버가 2대가 되면 다른 서버에 붙은 감독관은 못 받음 |
| **STOMP + 외부 브로커(Redis Pub/Sub), 채널은 회차 단위** | 서버를 늘려도 동작. Redis는 이미 씀 | 메시지가 저장되지 않음(끊긴 동안 이벤트는 DB에서 다시 조회) |

**결정:** 처음엔 서버 메모리, 서버를 늘릴 때 Redis Pub/Sub. 실시간 전달은 놓쳐도 되고 기록은 DB(`proctor_events`)가 원본이라는 점을 분명히 한다.

## 17. AI 과제 생성: Template Method + 검사 목록 (할 것)

개발 과제(기술검증 16번)와 비개발 과제(18번) 모두 "폼 → 생성 → 자동 확인 → HIDDEN 저장"이다.

| 후보 | 장점 | 단점 |
|---|---|---|
| **Template Method: `TaskGenerator`의 공통 흐름(생성 → 확인 → 저장), 개발·비개발은 프롬프트·스키마·확인 목록만 다름** + **확인은 `TaskCheck` 목록(형식, 검산, 샌드박스 실행, 다른 모델 풀이)** | 공통 흐름이 한곳. 확인 하나를 추가·제거하기 쉬움, 결과표가 곧 관리자 검수 화면 | 상속 구조를 쓰므로 종류가 많아지면 Strategy로 바꿔야 함 |

## 18. 회차 결과 통계: 조회 전용 쿼리 분리 (할 것)

응시자 1,000명 회차의 역량별 분포·순위를 빨리 뽑아야 한다.

| 후보 | 장점 | 단점 |
|---|---|---|
| 엔티티를 다 불러 자바에서 계산 | 코드가 쉬움 | N+1, 메모리. 1,000명이면 느림 |
| **CQRS 일부: 통계는 전용 조회 쿼리(집계 SQL, 인터페이스 프로젝션)로, 쓰기는 엔티티로** | DB가 계산. `ExamParticipantRepository.SessionCounts`처럼 이미 쓰는 방식 | 쿼리가 화면에 묶임 |
| 별도 통계 테이블(미리 계산) | 가장 빠름 | 채점이 끝날 때마다 갱신, 맞지 않을 위험 |

**결정:** 조회 전용 쿼리. 느리다는 측정이 나오면 그때 통계 테이블. CQRS를 프로젝트 전체에 도입하지는 않는다.

## 19. 응답 만들기: DTO + Assembler (전원)

| 후보 | 장점 | 단점 |
|---|---|---|
| 엔티티를 그대로 JSON으로 | 빠름 | 지연 로딩 오류, 숨은 정답·토큰 해시 같은 필드가 샐 위험 |
| **요청·응답 record DTO + 변환은 `from(entity)` 정적 메서드나 작은 Assembler** | 무엇이 나가는지 명확. `exam/web/ExamDtos`가 이미 이렇게 함 | 변환 코드가 늘어남 |
| MapStruct | 변환 코드 자동 생성 | 의존성과 빌드 설정 추가, 팀이 익숙하지 않음 |

**결정:** record DTO + `from()`. 실전 응시 리포트를 응시자에게 숨기는 것처럼 권한에 따라 응답이 다르면 DTO를 나눈다.

## 쓰지 않기로 한 것

| 패턴 | 이유 |
|---|---|
| Singleton (직접 구현) | Spring 빈이 이미 하나만 만든다 |
| Abstract Factory | 함께 바뀌는 제품군이 없다. 모델·저장소·실행기는 각각 따로 바뀐다 |
| Visitor (리포트 만들기) | 리포트 구조가 고정이라 이득이 없다 |
| Event Sourcing (전체) | 크레딧 원장만 쌓기 방식으로 충분하다. 전체 적용은 조회가 복잡해진다 |
| State (클래스로) | 7번. 상태별 동작이 거의 없다 |
