# 박성진 - 담당역할 기술명세 &설명

# **플랫폼 흐름 — 인증·회사 분리·크레딧·채점 큐·운영**

> **핵심 원칙:** 로그인한 사용자와 소속 회사를 기준으로 권한을 확인하고, 자가진단과 기업 시험 데이터를 분리한다. 크레딧 사용과 채점 요청은 기록을 남기며, 채점 실패와 재시도 상황을 추적할 수 있게 한다.
> 

## **1. 전체 흐름**

```
[회원]
  ├─ 가입·이메일 인증·로그인
  ├─ 자가진단 응시 ── 응시 시작·AI 채팅·롤백 시 크레딧 사용
  └─ 리포트·크레딧 내역 조회

[기업 도입 문의]
      ↓ 관리자 승인·담당자 초대
[기업 담당자 로그인] ── 회사·역할 확인 ── 회차·대상자·결과 접근
                                            │
[응시자] 과제 선택 → 코드 편집·실행 → AI 채팅 → 제출
                                            │
                               제출 정보를 채점 큐에 등록
                                            ↓
                                    [채점 작업자]
                                            ↓
                                 [팀원 2 채점 엔진]
                                            ↓
                                  리포트·채점 결과
                                    ↙           ↘
                          사용자 리포트       팀원 4 회차 분석

[운영] 큐 대기·처리·실패와 AI 비용을 확인
[배포] 테스트 → 빌드 → AWS 백엔드 / Oracle 코드 실행 서버
```

인증·회사 권한·크레딧·채점 큐와 같은 **공통 기반**을 맡습니다. 다만 응시 화면에서 크레딧을 사용하는 동작은 팀원 3, 채점 결과를 만드는 기능은 팀원 2, 실전 시험과 회차 분석은 팀원 4의 기능이므로 각 담당자와 연결 규격을 소통하여 방향을 정합니다

## **2. 기술 스택**

| **기술** | **역할** | **문서 기준** |
| --- | --- | --- |
| Spring Security + JWT | 사용자 인증과 API 권한 확인 | JWT 액세스·리프레시 토큰 사용을 역할 분담 문서에서 정의 |
| BCrypt | 비밀번호 저장 | 비밀번호를 해시해 저장 |
| PostgreSQL + JPA | 사용자·회사·크레딧 원장 등 관계형 데이터 관리 | 팀 공통 백엔드 스택과 DB 변경 이력 관리 |
| Redis | AI 호출 제한, 채점 큐 | 역할 분담에서 Redis 사용을 정의. 로그아웃 토큰 차단은 DB 세션 방식으로 대체했다 |
| Redis stream | 큐 작업을 가져와 팀원 2의 채점 로직 호출 | 재시도·실패 보관·동시 처리 설정이 요구사항 |
| Docker Compose | 로컬 개발 환경 | 지금은 메일 서버(Mailpit)와, 선택 실행(`--profile redis`) Redis만 있다. 백엔드·프런트·PostgreSQL 구성은 계획 |
| GitHub Actions | 테스트·빌드·배포 자동화 | 역할 분담의 인프라 항목 |
| AWS S3 | 과제 관련 파일, 대상자 CSV, 감독 자료 등 파일 저장 | 역할 분담과 기획 문서의 파일 저장 계획 |
| AWS EC2 | 백엔드와 코드 실행 환경 분리 | 기술검증 보고서의 서버 구조 |
| Prometheus + Grafana | 서비스·큐·AI 비용 지표 확인 | 역할 분담에서 확장 항목으로 정의 |

## **3. 기능별 담당**

### **3-1. 회원 인증·계정**

- **무엇:** 이메일 인증, 가입, 로그인·로그아웃, 토큰 재발급, 내 정보 조회·수정·탈퇴를 제공한다.
- **어떻게:** Spring Security와 JWT 액세스·리프레시 토큰을 사용하고, 비밀번호는 BCrypt로 저장한다. 로그아웃은 DB의 로그인 세션을 폐기하는 방식이라, 그 세션의 액세스 토큰도 바로 쓸 수 없다(별도의 Redis 차단 목록은 쓰지 않는다). `member_status`가 `ACTIVE`인 계정만 로그인할 수 있도록 한다.
- **왜:** 프런트의 로그인 화면만으로는 API 권한이 보호되지 않는다. 백엔드가 요청마다 사용자와 권한을 검증해야 한다.

탈퇴 시에는 개인정보를 익명화하고 응시·채점 기록과 크레딧 원장은 정책에 따라 보존한다

### **3-2. 회사별 접근 제어와 기업 계정**

- **무엇:** 기업 담당자가 자기 회사의 회차·대상자·결과만 조회하고 관리하도록 한다.
- **어떻게:** 기업은 도입 문의 후 관리자 승인과 초대로 가입한다. 사용자 계정에 회사와 역할을 연결하고, 인증된 사용자 정보의 `companyId`와 조회 대상 데이터의 회사를 비교해 접근을 제한한다.
- **역할:** `USER`, `MANAGER`, `PROCTOR`, `ADMIN`. `MANAGER`는 회차 관리와 감독 권한을 가지며, `PROCTOR`는 감독 업무만 수행한다. 문서에는 `MANAGER > PROCTOR` 권한 계층이 정의되어 있다.
- **왜:** 사용자 요청에서 전달한 회사 ID를 그대로 신뢰하면 다른 회사 데이터에 접근할 수 있다. 권한과 회사 소속을 서버에서 확인하고 회사 간 접근 차단 테스트를 해야 한다.

**기업 도입 문의, 관리자 승인, 담당자 초대, 감독관 초대**가 포함되어 있다. 기업 담당자는 자체 가입하는 방식이 아니라 초대 링크로 가입한다.

### **3-3. 크레딧과 구매**

- **무엇:** 자가진단에 필요한 크레딧을 지급·차감하고, 구매 내역과 사용 내역을 관리한다.
- **어떻게:**
    - 가입 시 무료 크레딧을 지급하고, 크레딧 단품 구매를 지원한다.
    - 응시 시작, AI 채팅 1회, 롤백 1회에 설정된 양을 차감한다. 응시 시작 크레딧에는 채점 1회 비용이 포함된다.
    - 적립·차감은 `credit_ledger` 원장에 사유·응시 ID·크레딧 양·잔액·시각과 함께 기록한다.
    - 동시 차감으로 잔액이 음수가 되지 않도록 회원 행 잠금 등 동시성 제어를 적용한다.
    - 구매는 결제 대행사의 테스트 모드로 구현한다.
- **잔액 부족 시:** 응시 도중 크레딧이 바닥나면 AI 채팅만 제한한다. 코드 편집과 제출은 가능하고, 응시 시작 시 채점 비용을 이미 냈으므로 채점은 진행한다.
- **롤백 정책:** 횟수 제한 없이 사용할 수 있지만, 롤백마다 크레딧을 차감한다.
- **기업 과금:** 기획만 하고 이번 구현 범위에는 포함하지 않는다. 승인된 기업은 무료로 사용한다.

크레딧 잔액은 원장 합계를 기준으로 산출하는 것이 문서의 기준이다. 동시 차감 시 잔액이 음수가 되지 않는지 테스트한다

### **3-4. AI 요청 제한**

- **무엇:** 응시자의 AI 채팅 호출을 사용자별·전체 기준으로 제한한다.
- **어떻게:** Redis로 사용자별 및 전체 호출 수를 관리한다. 한도를 넘은 요청은 프런트와 합의한 응답으로 거절한다.
- **왜:** 동시 응시 중 AI 호출이 몰리는 상황에서 API 한도 초과와 비용 급증을 완화한다.

### **3-5. 제출·채점 큐**

- **무엇:** 제출 요청을 채점 대기 작업으로 전달하고, 작업자가 팀원 2의 채점 엔진을 실행한다.
- **흐름:**
    1. 팀원 3의 자가진단 제출 또는 팀원 4의 실전 시험 제출이 들어온다.
    2. 팀원 1의 공통 흐름에서 채점 요청을 큐에 등록한다.
    3. 작업자가 큐에서 요청을 가져와 팀원 2의 이중 판정·RAG 채점 로직을 호출한다.
    4. 성공·실패 상태를 기록하고, 실패는 정해진 횟수만큼 재시도한다.
    5. 재시도 후에도 실패하면 실패 보관함에 남겨 확인할 수 있도록 한다.
- **요청에 필요한 정보:** 역할 분담 문서에서는 응시 ID와 버전을 미리 합의하도록 되어 있다. 실제 필드명과 채점 상태값은 팀원 2·3·4와 함께 확정해야 한다.
- **왜:** 실전 시험 종료 시 제출이 한꺼번에 몰려도 제출 API가 채점 완료를 기다리지 않게 하고, 대기 작업이 서버 재시작으로 사라지지 않도록 하기 위해서다.

### **3-6. 팀 간 연결 지점**

| **연결 지점** | **담당** | **미리 합의할 내용** |
| --- | --- | --- |
| 로그인 사용자 정보 | 팀원 1 → 전원 | 현재 사용자·회사·역할을 백엔드에서 얻는 공통 방식 |
| 크레딧 차감 | 팀원 1 ↔ 팀원 3 | 응시 시작·AI 채팅·롤백 차감 API, 잔액 부족 응답 |
| 제출 → 채점 큐 | 팀원 3·4 → 팀원 1 → 팀원 2 | 채점 요청 형식, 응시 ID·버전, 상태값 |
| 채점 결과 → 회차 분석 | 팀원 2 → 팀원 4 | 점수·리포트 조회 방식 |
| AI 요청 제한 | 팀원 1 → 팀원 3 | 제한 기준과 프런트가 표시할 응답 형식 |
| 초대·인증 메일 | 팀원 4 → 팀원 1 | 공통 메일 발송 모듈과 메일 종류 |
| S3 파일 저장 | 팀원 1 → 팀원 3·4 | 파일 저장·조회 인터페이스와 권한 |

## **5. 보안·운영 원칙**

- 회사별 접근은 요청에 포함된 회사 ID가 아니라 인증된 사용자 소속을 기준으로 판단한다.
- `MANAGER`, `PROCTOR`, `ADMIN`, `USER` 권한별 API 접근을 테스트한다.
- 비밀번호는 BCrypt로 저장하고, JWT 서명 키와 DB·클라우드 자격 증명은 코드나 저장소에 넣지 않는다.
- 크레딧 차감은 동시 요청에서도 잔액이 음수가 되지 않도록 처리한다.
- 크레딧 적립·차감 사유를 원장에 남긴다.
- 큐 메시지는 채점에 필요한 최소한의 식별 정보만 포함하고, 중복 전달 상황을 고려한다.
- 재시도 횟수는 제한하고, 최종 실패 작업을 추적할 수 있도록 한다.
- Redis 재시작 이후 대기 작업을 복구하려면 실제 운영 환경의 영속성 설정을 검증한다.
- Docker Compose, GitHub Actions, AWS·Oracle 배포와 S3 저장은 역할 분담의 인프라 목표로 관리한다.
- Prometheus·Grafana는 응답 시간, 큐 길이, 회차별 AI 비용과 알림을 확인하는 확장 항목이다.

## **6. 테스트와 측정 지표**

| **테스트 대상** | **확인 내용** |
| --- | --- |
| 인증·권한 | 비로그인 사용자와 권한이 부족한 사용자의 접근 거부 |
| 회사 분리 | 한 회사 담당자가 다른 회사 회차·대상자·결과를 조회할 수 없음 |
| 기업 초대 | 승인된 초대만 가입 가능하고, 회사와 역할이 올바르게 연결됨 |
| 크레딧 지급·차감 | 가입 지급과 응시·채팅·롤백 차감이 원장에 기록됨 |
| 크레딧 동시성 | 동시에 차감해도 잔액이 음수가 되지 않음 |
| 크레딧 부족 | 채팅은 제한되지만 편집·제출·채점은 가능한 정책 확인 |
| 요청 제한 | 사용자별·전체 분당 한도 초과 동작과 프런트 응답 확인 |
| 큐 재시도·실패 | 일시 실패 재시도, 최대 횟수 초과 후 실패 보관 |
| 큐 복구·중복 | 작업자 재시작 후 미완료 작업 처리, 재전달 시 중복 결과 방지 |
| 배포 자동화 | 테스트 실패 시 배포가 진행되지 않음 |
