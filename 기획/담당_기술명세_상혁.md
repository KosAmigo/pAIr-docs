## 1. 개요

pAIr에서 **기업이 실전 시험을 열고 결과를 받아 보기까지의 흐름**을 담당합니다.

기업 담당자가 회차를 열고 지원자를 초대합니다. 지원자는 감독을 받으며 같은 시각에 시험을 보고, 담당자는 결과와 부정행위 의심 구간을 한눈에 봅니다. 감독은 영상을 서버로 보내지 않고 응시자 브라우저 안에서 분석합니다. 관리자 과제 콘솔과 초기화면도 맡습니다.

| 구분 | 내용 |
| --- | --- |
| 담당 흐름 | 회차 생성 → 초대 메일 → 입장·환경 점검 → 감독 → 자동 제출 → 회차 결과 분석 |
| 대표 기능 | 시험 진행 + 감독(브라우저 안 분석), 회차 결과 분석 |
| 맡는 테이블 | `exam_sessions`, `exam_session_tasks`, `exam_participants`, `proctor_consents`, `proctor_events`, `env_scan_photos`, `env_check_progress`, `proctor_notices` (+ 코드표 `proctor_event_types`) |
| 핵심 목표 | 영상 전송 대비 데이터 99% 이상 절감, 종료 시각 뒤 자동 제출 5초 이내, 조건별 감독 오탐률 측정·기준값 조정 |

## 4. 구조 설계

### 실전 시험 흐름

```
기업 담당자 (콘솔)
  → 회차 생성 (과제 여러 개, 시작·종료 시각)
  → 대상자 CSV 업로드 → 초대 메일 (커밋 뒤 비동기)
응시자 (메일 링크)
  → 입장 정보 → 동의 + 환경 점검 (PC 웹캠, 실패해도 저장하고 입장)
  → 대기실: 서버 시각 기준 카운트다운
  → 시작 시각: 서버가 허락할 때만 시작, 과제마다 응시 생성 (행 잠금으로 한 번만)
  → 응시 + 감독 (브라우저 이벤트, PC 웹캠, 연결 신호)
  → 과제별 제출 / 종료 시각에 스케줄러가 남은 과제 자동 제출
  → 채점 큐 (팀원 1) → 채점 (팀원 2)
기업 담당자
  → 회차 결과 분석 (점수는 팀원 2 결과를 읽기만)
```

### 감독 구조

```
[응시자 PC 브라우저]  ← 모든 분석은 여기서
  브라우저 이벤트 감지 ───────────────────────── HTTP ──▶ 백엔드 (콘솔에는 이력으로만)
  PC 웹캠 (MediaPipe, 분석 Worker*) ── 이벤트 + 앞 8초·뒤 4초 사진 ── HTTP ──▶ 백엔드 ──▶ S3
     (* Worker 분리는 프론트 main 에 있음. 실패 시 메인 폴백)
  시험 화면 ──── 10초마다 heartbeat ──── HTTP ──▶ 백엔드 (연결 유예 5분)
[감독관 콘솔] 이벤트 이력과 웹캠 사진 구간을 본다. 실시간 영상은 없다
```

- 영상은 서버로 보내지 않고 저장하지 않습니다. 실시간 영상(웹캠·화면·휴대폰 3채널), 휴대폰 보조 캠, PC 화면 공유는 **사용 안 함**입니다(코드만 남김).
- 이벤트가 나면 PC 가 로컬에 둔 앞 8초·뒤 4초 웹캠 사진(최대 12장)을 약 5초 뒤 올려 파일 저장소에 두고, 감독관·매니저가 완료된 회차에서도 확정/기각합니다. 연속 녹화·서버 추론은 하지 않습니다.
- PC 이벤트는 브라우저 아웃박스에 쌓았다가 보냅니다. 네트워크 오류·5xx 만 다시 보내고 4xx 는 버립니다.

## 5. 주요 기능 명세

### 5.1 회차와 대상자

- 회차 하나에 과제 여러 개(`exam_session_tasks`), 시간은 회차 전체로 봅니다.
- 수정·취소는 시작 전만 됩니다. 취소는 지우지 않고 `canceled_at` 을 남깁니다.
- 대상자는 사이트 양식 CSV(이름, 이메일)로 올립니다. 업로드 전에 형식·중복을 보여 주고, **틀린 행 하나 때문에 전체를 거절하지 않습니다.** 원본은 S3 에 보관합니다.

### 5.2 입장 링크와 메일

- 토큰은 `SecureRandom` 32바이트(Base64URL 43자)이고, **DB 에는 SHA-256 해시만** 저장합니다. 메일을 다시 보내면 토큰을 새로 만듭니다.
- 메일: 등록 즉시, 시작 하루 전 알림, 변경·취소 안내. 회차 저장이 끝난 뒤(커밋 뒤) 별도 스레드에서 보내고, 결과(PENDING/SENT/FAILED)를 남깁니다.

### 5.3 동시 시작과 자동 제출

- 대기실은 `서버 시각 - 내 시각`(왕복 시간의 가운데 기준)으로 카운트다운을 그립니다.
- 시작 API 는 **서버 시각 ≥ 시작 시각**일 때만 허락합니다. 이르면 거절하고 프론트가 1초 뒤 다시 부릅니다.
- 시작을 두 번 눌러도 대상자 행 잠금(`SELECT … FOR UPDATE`)으로 응시는 한 번만 만듭니다.
- 스케줄러가 2초마다 "끝났는데 닫히지 않은 회차"를 찾아 남은 과제를 자동 제출합니다. 회차마다 트랜잭션을 나누고, 두 번 돌아도 안전합니다.
- 후속 질문 단계에서 시간이 끝난 응시도 **빈 답으로 마무리해 채점으로 넘깁니다**(그렇지 않으면 채점이 시작되지 않습니다).
- 채점으로 넘기지 못한 응시가 있으면 회차를 닫지 않고 간격을 늘려(2~30초) 다시 시도하고, 5번 실패하면 포기하고 닫은 뒤 오류 로그를 남깁니다. 포기한 응시는 콘솔 결과 탭의 "멈춘 응시 다시 넘기기"(`POST /api/console/sessions/{id}/rescue`)로 되살립니다.
- `closed_at - ends_at` 을 **자동 제출 지연** 지표로 남깁니다.

### 5.4 감독: 브라우저 이벤트

- 탭 이탈, 창 포커스 이탈, 마우스 이탈, 전체 화면 해제, **외부 붙여넣기(`PASTE`)** 를 감지해 감독 API(1-7)로 `source=BROWSER`, 사진 없이 보냅니다. 붙여넣기는 시험 화면 안에서 복사한 글이면 세지 않고, 20자 미만은 무시하며, 글 내용 대신 글자 수·줄 수·위치만 보냅니다 (`anti-cheating/core/PasteDetector.ts`).
- 한 번의 이탈에서 신호가 여러 개 나오므로 상태 머신으로 하나로 묶습니다.
- 실전 맥락이 있을 때만 켜집니다. 자가진단에서는 켜지지 않습니다.

### 5.5 감독: 카메라

| 카메라 | 감지 |
| --- | --- |
| PC 정면 | 얼굴 없음, 여러 얼굴, 고개 돌림·들기, 오래 숙임, 시선 이탈, 자리 이동, 몸 돌림 |
| 휴대폰 보조 (**사용 안 함**) | 양손 화면 이탈, 휴대폰, 다른 화면, 책, 연결 끊김 규칙은 코드에 남아 있으나 휴대폰 캠을 쓰지 않아 동작하지 않는다 |
| PC 화면 공유 (**사용 안 함**) | 화면 공유 중단·전체 화면 아님 확인은 코드에 남아 있으나 화면 공유를 쓰지 않는다 |

1. **특징값:** 얼굴 변환 행렬로 고개 각도, 눈 블렌드셰이프로 시선(눈 감은 동안 제외), 어깨 랜드마크로 몸통 위치를 구합니다.
2. **개인별 보정:** 시작 3초 동안의 중앙값을 기준 자세로 잡습니다. 카메라 각도가 사람마다 달라도 기준이 맞습니다.
3. **규칙 엔진:** 이상 상태가 정해진 시간 이어져야 경고합니다(예: 얼굴 없음 2초). 0.4초 안의 끊김은 이어 붙이고, 규칙마다 쿨다운을 둡니다.
4. **전송:** 경고 1건 + 320px JPEG 1장. 얼굴로 사람을 식별하지 않습니다(있는지만 봄).
5. **분석 위치:** 웹캠과 휴대폰 영상 모두 응시자 PC 가 분석합니다. 휴대폰은 모델·추론 없이 영상만 보내 부하를 없앴습니다(아이폰이 분석 도중 메모리 부족·페이지 종료, 상태 신호 지연으로 연결이 끊기던 문제). 웹캠·휴대폰 분석에 프레임 예산을 따로 두고, 휴대폰 영상 분석 간격은 최소 200ms 입니다. 휴대폰 영상은 평소 최대 1.2Mbps·15fps 로 보냅니다. **부하 제한(2026-11-21):** 모델은 브라우저 메인 스레드에서 동기로 돌아(얼굴 약 32ms, 포즈 약 21ms) 시험 화면 입력이 끊기므로, 웹캠 분석 간격을 100ms(초당 최대 10회) 이상으로 두고 느리면 걸린 시간의 두 배를 쉽니다. 한 번에 모델 하나만 돌려(얼굴 3번에 포즈 1번, 안 돌린 쪽은 직전 결과를 사용) 한 작업이 50ms 를 넘지 않게 했습니다. 이 PC(GPU) 측정, 8초 기준: 이전 점유 80%·지연 상위 5% 51ms·50ms 넘는 긴 작업 15건 → 현재 29%·27ms·0건. 측정은 얼굴 사진 한 장을 영상처럼 반복해 넣은 것이라 실제 앱과 다를 수 있습니다.

### 5.6 환경 점검

- **점검에 실패해도 응시를 막지 않습니다**(2026-11-22). 환경이 맞는데도 AI 모델이 실패·경고를 내면 입장할 수 없던 문제가 있어서, 실패여도 "점검 결과 저장" 버튼을 보여 주고(통과면 주 버튼, 실패면 보조 버튼) 저장한 뒤 입장합니다. 실패한 채 입장한 결과는 감독 기록에 남아 감독관이 확인합니다. 모델 기준값을 아무리 조정해도 너무 빡세거나 허술해(11-18, 11-20) 판정 권한을 감독관에게 넘긴 결정입니다.
- **콘솔에서 점검을 봅니다.** 점검 화면이 진행 상태를 3초마다 올리고(`env_check_progress`, 대상자당 최신 1건 덮어쓰기, 최대 20,000자) 콘솔 대상자 상세의 점검 카드가 항목별 상태·사유를 보여 줍니다. 진행 상태와 동의 저장 뒤의 결과(`proctor_consents.env_check`) 중 더 최근 것을 보여 주고 실시간인지 저장본인지 표시합니다.
- **감독관이 안내 메시지를 보냅니다.** 자유 입력(최대 500자), 일방향입니다(`proctor_notices`). 응시자 화면에 시험을 막지 않는 배너가 뜨고 "확인"을 누르면 읽음 시각이 남아 콘솔에 읽음이 표시됩니다. 취소·종료된 회차에는 보낼 수 없고, 응시자는 끝난 뒤에도 받은 안내를 읽을 수 있습니다. 답장·정해진 문구 목록·점검 기준을 콘솔에서 바꾸는 기능은 없습니다.
- PC: 자동화 브라우저, 원격·가상 머신(약한 신호), 모니터 수, 가상 카메라, 이어폰·소음, 조명, 얼굴 위치·혼자 있는지, 귀·손목 촬영.
- 휴대폰 점검(조명·책상 위): **사용 안 함.** 휴대폰 보조 캠을 쓰지 않으므로 점검에 나오지 않는다. 구현은 `PHONE_CAM_ENABLED` 뒤에 남아 있다.
- **다시 점검하면 통과하지 못한 항목만 다시 합니다.** 통과(`pass`)한 항목은 결과와 사진을 그대로 두고, 실패·주의·미완료 항목만 해당 단계를 다시 실행합니다(조명·자세는 둘 중 통과하지 못한 쪽만 판정에 반영). "처음부터 다시" 버튼으로 전체를 다시 할 수 있습니다. 책상 스캔용 물체 감지 모델은 처음 한 번만 불러와 재사용합니다(다시 점검할 때마다 새로 받지 않음).
- [사용 안 함: 휴대폰 보조 캠 없이는 동작하지 않음] **책상 위**는 책상 전체가 한 화면에 보이는 곳에 휴대폰을 세워 고정하면(기준 프레임과 1.5초 동안 거의 같으면 고정, 15초 안에 고정되지 않으면 그대로 시작) 6초 동안 1.5초 간격으로 고해상도 사진을 찍어 PC 가 감지합니다(전체 프레임 + 겹치는 2x2 타일).
- [사용 안 함: 휴대폰 보조 캠 없이는 동작하지 않음] **책상 위**는 다른 사람을 보지 않습니다(응시자 본인의 손·팔이 사람으로 잡혀 오탐이 납니다).
- **대기실 입장 마감은 없습니다.** 한때 감독 회차에 "시작 10분 전까지 환경 점검을 마치고 입장"이라는 마감을 뒀으나(감독관이 책상 사진을 확인할 시간 확보) 2026-11-21 에 없앴습니다. 시작 전이면 언제든 입장해 점검하고 대기할 수 있고, 초대 메일은 "시작 전에 미리 입장해 점검을 마쳐 주세요"라고 안내만 합니다.
- [사용 안 함: 휴대폰 보조 캠 없이는 동작하지 않음] **책상 위 스캔은 응시를 막지 않고 경고만 합니다.** 휴대폰·책·화면이 잡히면 응시자 화면에 "책상 위에서 휴대폰 N회, 책 N회가 감지되었습니다. 시험에 필요 없는 물건은 치워 주세요"라는 **경고(`warn`)** 를 보여 주지만, 확인을 묻지 않고 점검은 통과로 넘어갑니다(불통과 `fail` 로 만들지 않습니다). 무엇이 몇 번 잡혔는지와 사진은 감독관에게 전달하고(`env-scan` 사진의 물체 목록), 판단은 감독관이 합니다. 아무것도 잡히지 않으면 "감지된 물체 없음"으로 통과합니다.
- 귀·손목은 사진만 찍어 감독 기록에 남기고, 사진 속 물체를 자동으로 분석하지 않습니다(이어폰·스마트워치 등은 감독관이 사진으로 확인). 점검 결과는 동의와 함께 저장합니다. 책상 위 사진은 감독관이 확인할 수 있게 **응시자 PC 가** 파일 서버에 올립니다(`POST /api/entry/{invite}/env-scan`, 감독 이벤트와 따로 `env_scan_photos` 에 저장, 회차 종료 7일 뒤 파일 삭제). 귀·손목 사진은 올리지 않습니다.
- 테스트용 "점검 건너뛰기"가 개발 서버(또는 `VITE_ALLOW_CHECK_SKIP=true` 빌드)에서만 보이며, 건너뛰면 감독 기록에 건너뜀으로 남고 감독 패널은 뜨지 않습니다.
- 귀 확인은 고개를 **35도 이상** 한쪽으로 돌려 0.3초 유지하면 통과합니다. 옆모습에 가깝게 돌려 얼굴 모델이 얼굴을 놓쳐도, 방금까지 돌리고 있었다면(0.7초 안) 돌린 것으로 인정합니다.
- [사용 안 함: 휴대폰 보조 캠 없이는 동작하지 않음] 휴대폰 보조 캠은 책상 스캔부터 시험 중 감독까지 **후면 카메라를 그대로** 씁니다(카메라를 바꾸지 않습니다). 휴대폰 페이지는 모바일 폭(최소 320px)으로 열립니다.

### 5.7 사진 보관

- JPEG 매직 바이트·200KB 제한을 확인하고 S3 `exam-snapshots/{회차}/{이벤트}.jpg` 에 저장합니다.
- 업로드가 실패하면 이벤트도 롤백되고 아웃박스가 다시 보냅니다(사진 빠진 기록이 생기지 않음).
- **회차 종료 7일 뒤** 파일을 지우고 `snapshot_deleted_at` 만 남깁니다.
- **구현됨(2026-11-23):** 삭제 2일 전부터 감독관·매니저가 회차 단위로 **7일씩 최대 2번** 연장할 수 있고(총 21일), 누가 언제 연장했는지 이력을 남깁니다. 이벤트 앞뒤 증거 구간 사진도 같은 규칙으로 보관합니다. 동의 문구도 v2 로 바꿨습니다 ([API §7](../API/실전시험_감독_API.md)).
- 담당자는 사진을 보고 OK/SUSPECT 로 판정합니다. 자동 탈락은 없습니다.

### 5.8 회차 결과 분석

- 순위(동점은 같은 순위), 만점 대비 10점 구간 분포, 역량별 평균, 상위·하위 25% 비교, 감독 이벤트 유형별 합계.
- 지표: 자동 제출 지연, **데이터 절감률**(실제 사진 용량 ÷ 영상 1.5Mbps 로 감독했다면 보냈을 양).
- CSV 는 UTF-8 BOM, `= + - @` 로 시작하는 값은 `'` 를 붙여 수식 주입을 막습니다. 엑셀(`results.xlsx`)은 요약(지표·점수 분포 차트·항목 평균)과 응시자별 결과표로 내려받습니다.
- 통계는 엔티티를 다 불러 계산하지 않고 집계 쿼리로 뽑습니다(대상자 1번 + 이벤트 집계 1번).

### 5.9 관리자 과제 콘솔

- 팀원 2 의 AI 과제 생성이 `HIDDEN` 으로 저장한 과제를 목록으로 보고, 자동 확인 결과와 함께 검수·편집합니다.
- "응시자로 보기"로 실제 응시 화면에서 미리 풀어 본 뒤 `OPEN` 으로 공개합니다. 회차에는 `usage = 'LIVE' AND status = 'OPEN'` 과제만 걸 수 있습니다.

### 5.10 연결 필수와 연결 유예

> **현재 적용 상태(2026-11-24): 웹캠만 필수.** 휴대폰 보조 캠(`PHONE_CAM_ENABLED`)과 PC 화면 공유(`SCREEN_SHARE_ENABLED`)는 사용하지 않는다(스위치로 끈 상태가 정책, 코드는 유지). 세 채널·두 채널 규칙은 코드로 구현돼 있어 스위치를 켜면 다시 동작한다(휴대폰 영상은 LTE 등에서 TURN 서버가 필요한 한계가 있었다).

두 층으로 나뉩니다. 서로 독립이고 값도 다릅니다.

| | 응시자 화면(프론트) | 서버(백엔드) |
| --- | --- | --- |
| 대상 | **웹캠 한 채널** (휴대폰·화면 공유를 켜면 세 채널) | 시험 화면의 연결 신호 (`heartbeat`, 10초마다) |
| 시작 조건 | 채널이 모두 연결돼야 "응시 시작" 가능 | 시작한 응시자에게만 적용 |
| 유예 | **15초** 안에 복구되면 끊김으로 치지 않음 | **5분** 안에 돌아오면 이어서 응시 |
| 초과하면 | 응시 화면을 막고 끊긴 채널 안내. 모두 돌아와야 풀림 | 링크 만료(`link_expired_at`) + `LINK_EXPIRED` 이벤트 |
| 기록 | 웹캠 끊김. (휴대폰 끊김 `PHONE_DISCONNECTED`·화면 공유 끊김 `SCREEN_STOPPED` 는 사용 안 함) | 90초 넘게 끊겼다 돌아오면 `CONNECTION_LOST` |

- 프론트 판정은 `proctor/core/connectionPolicy.ts` 의 순수 함수(`stepGate`)이고, 차단 창은 `ConnectionGate.tsx` 입니다. 웹캠을 뽑았다 꽂으면 차단 창의 "웹캠 다시 연결", (화면 공유 "다시 시작" 복구는 사용 안 함)
- [사용 안 함] 휴대폰 무응답(stale) 판정은 서버 기준 **15초**(영상을 보내는 중에만)입니다. 처음 6초였으나 아이폰 추론이 메인 스레드를 오래 잡아 오탐이 반복돼 늘렸습니다.
- `CONNECTION_LOST`·`LINK_EXPIRED` 는 자동 탈락이 아니라 담당자가 보는 기록입니다.
- 끊긴 시간은 보전하지 않습니다(종료 시각은 서버 기준 그대로). 차단 중 응시 화면의 타이머 표시 동작은 코드에서 확인하지 못했습니다 (실기기 체크리스트 D6).

### 5.11 PC 화면 공유 (사용 안 함)

> 2026-11-24: 사용하지 않는다. 아래는 구현돼 있는(스위치로 꺼 둔) 동작의 기록이다.

- 동의 문구 4줄(녹화·저장·내용 분석 안 함 / 감독관이 열 때만 실시간 전달 / 이벤트 순간 흐린 한 장만 저장 / "전체 화면"을 고를 것)을 보여 주고 `getDisplayMedia` 로 공유를 받습니다.
- 공유가 살아 있는지와 전체 화면(`displaySurface=monitor`)인지만 봅니다. 창·탭만 공유하면 연결로 치지 않아 시험을 시작할 수 없고, 브라우저가 알려 주지 않으면 막지 않고 기록만 합니다.
- 이벤트 순간의 사진은 **보내기 전에** 가로 96px 로 줄여 글자를 읽을 수 없게 만듭니다(클라이언트 흐림, 원본이 네트워크에 나가지 않음).
- **서버가 아직 `source=SCREEN`·`SCREEN_STOPPED`·`SCREEN_PARTIAL` 을 받지 않아** 프론트는 `SCREEN_EVENTS_ACCEPTED=false` 로 전송을 막아 두었습니다 (PC 화면 로그에만 남음). 백엔드가 받게 되면 이 값을 `true` 로 바꿉니다 ([API §6-6](../API/실전시험_감독_API.md)).

### 5.12 사전 테스트

- `/practice` (로그인 없음)에서 실제와 같은 환경 점검과 연결 상태(웹캠)를 연습합니다. 채널이 연결되고 점검을 통과하면 통과 문구를 보여 줍니다.
- 서버에 이벤트·사진·점검 결과를 **하나도 남기지 않습니다**(`camHub.connectPractice`, 릴레이는 `practice-` 키로 짝만 맺고 저장 안 함).
- "시험 7일 전부터 연다"는 계획 가정이었고 지금은 공개 페이지라 언제든 열립니다.

### 5.13 감독관 영상 보기 (사용 안 함)

> 2026-11-24: 핫스팟 응시자에서 영상 연결(ICE)이 실패해(STUN만 사용) **웹캠·화면·휴대폰 3채널 모두 쓰지 않는다.** 응시자 화면의 동의 문구도 "영상은 서버로 보내지 않는다"로 바뀐다. 아래는 구현돼 있는(스위치로 꺼 둔) 동작의 기록이다.

- 감독관이 콘솔 감독 패널에서 응시자를 **열었을 때만** 응시자 PC 가 웹캠·화면 공유 영상(휴대폰 캠을 켜면 휴대폰 영상까지 3채널)을 감독관에게 WebRTC P2P 로 보냅니다. 휴대폰 영상은 PC 가 이미 받은 스트림을 그대로 다시 보냅니다(휴대폰 부하 없음). 채널당 최대 500kbps(화면 400kbps, 4fps). 영상 칸의 확대 버튼으로 전체 화면 팝업으로 키워 볼 수 있고(같은 스트림을 한 번 더 붙일 뿐), 휴대폰이 꺼져 있으면 휴대폰 칸을 숨기고 2칸으로 배치합니다.
- 영상은 서버를 지나지 않고 저장하지 않습니다. 서버(개발 릴레이)는 `watch`·`unwatch`·`view-rtc` 시그널링만 넘기고, 응시자 1명당 감독관 최대 2명(`MAX_VIEWERS_PER_PARTICIPANT`)입니다. 응시자 PC 가 끊기면 감독관 화면에 "연결되지 않음", 다시 붙으면 자동으로 이어집니다.
- **개발 릴레이로만 동작합니다.** 권한 확인(자기 회사 응시자만)은 개발 릴레이가 로그인 헤더로 임시 확인하며, 운영 백엔드의 Spring WebSocket 구현과 열람 기록은 아직 없습니다 ([API §6-11](../API/실전시험_감독_API.md)).
- 응시자 화면에는 감독관이 볼 수 있다는 동의 문구가 있습니다.

### 5.14 입장·시작 흐름 (늦은 입장, 새로고침)

- **입장 마감은 없습니다.** 시작 시각이 지나도 종료 전이면 처음 입장해 환경 점검·동의 뒤 시작할 수 있습니다(통합 테스트 `lateEntryAfterStartIsAllowed`). 늦게 들어와도 종료 시각은 그대로입니다. 한때 감독 회차에 "시작 10분 전 마감"을 뒀으나 2026-11-21 에 없앴습니다.
- **새로고침 복구:** 이미 시작한 응시자가 링크로 다시 들어오면 곧바로 대기실로 갑니다. 웹캠 연결은 새로고침하면 사라지므로 대기실에서 웹캠을 다시 열고, 열지 못하면 "웹캠 다시 연결" 버튼을 보여 줍니다. 예전에는 대기실에 웹캠을 여는 코드가 없어 "웹캠이 연결되면 시작합니다"에서 멈췄습니다.
- **시작 호출 중복 방지:** 개발 모드(StrictMode)에서 대기실 효과가 두 번 돌면 첫 시작 요청의 결과가 버려져 "시험을 시작하는 중입니다"에서 멈추던 문제를 고쳤습니다. 효과가 정리될 때 시작 표시를 풀어 다시 시도하며, 서버는 두 번 불러도 응시를 한 번만 만듭니다(대상자 행 잠금).
- **알려진 한계:** 연결 신호(`heartbeat`)는 시험 화면에서만 보냅니다. 새로고침 뒤 대기실에서 멈춰 있으면 신호가 없어 90초 뒤 `CONNECTION_LOST`, 5분 뒤 링크 만료가 남을 수 있습니다(대기실에서도 신호를 보내는 개선은 제안 단계). 시작 전에 대기실에서 새로고침하면 단계가 처음(시험 정보)부터 다시 시작합니다(동의는 서버에 저장돼 있음).
- **콘솔 회차 목록:** 진행 중 회차 수가 늘면 "진행 중" 탭으로 자동 이동합니다(예정·종료 탭을 눌러 둔 채 카드 숫자만 오르던 문제). 목록은 30초마다 갱신합니다.

### 5.15 감독 이벤트 알림 (콘솔)

- 새 감독 이벤트가 들어오면 알림음을 냅니다. 처음 불러온 목록은 **기준선**으로만 쓰고 알리지 않으며, 그 뒤 새로 생긴 이벤트만 감독관이 확인(dismiss)할 때까지 모아 보여 줍니다. 응시자(회차·대상자)가 바뀌면 기준선을 새로 잡습니다.
- 음원 파일 없이 Web Audio 로 짧은 두 음(880Hz, 660Hz, 음량 0.12)을 냅니다. 소리 켜기·끄기는 브라우저에 저장하고(기본 켜짐), 브라우저가 소리를 막고 있으면 조용히 건너뜁니다.

### 5.16 인증 메일 서식

- 회원가입 인증 코드 메일을 시험 초대 메일과 같은 서식(`MailLayout` 로고·표)으로 맞췄습니다. HTML + 글자 본문을 함께 담은 `MimeMessage` 로 보내고, 맨 아래 문구(footer)는 인자로 바꿀 수 있습니다.

## 7. 기술 선택 근거

| 결정 | 선택 | 근거 |
| --- | --- | --- |
| 감독 분석 위치 | 응시자 PC 브라우저 안 (MediaPipe) | 영상 전송이 없어 트래픽·저장·개인정보 부담이 사라짐. 서버 GPU 불필요 |
| 경고 판정 | 개인별 보정 + 지속 시간 + 쿨다운 | 고정 기준값은 카메라 각도 차이로 오탐. 한 프레임 튀는 값 무시 |
| 보낼 데이터 | 이벤트 + 사진 1장 | 감독관이 확인할 근거는 남기면서 영상 대비 데이터를 크게 줄임 |
| 시각 기준 | 서버 시각 | 응시자 시계가 틀려도 공정. 판단은 서버 한 곳 |
| 중복 시작 방지 | 대상자 행 잠금 | 두 번 눌러도 응시 하나. 별도 분산 잠금 불필요 |
| 메일 | 커밋 뒤 비동기 | 메일 서버가 느리거나 죽어도 회차 저장은 성공, 롤백되면 메일도 안 나감 |
| 이벤트 전송 | 아웃박스 + 4xx 버림 | 네트워크가 끊겨도 이벤트를 잃지 않고, 다시 보내도 같은 결과인 요청은 반복하지 않음 |
| 사진 저장 | S3 + 실패 시 롤백 | 사진이 빠진 기록보다 주인 없는 파일이 낫다 |
| (사용 안 함) 휴대폰 연결 | 초대 토큰과 다른 짝 코드 | QR 이 찍혀도 입장 링크가 드러나지 않음 |
| 환경 점검 실패 | 저장하고 입장 허용, 감독관이 확인 | AI 모델 판단은 틀릴 수 있는데 통과를 필수로 걸면 환경이 맞는 응시자가 막힘. 입장은 열어 두고 콘솔 점검 카드·안내 메시지로 사후·실시간 대응 |
| 책상 위 감지 | 경고만 하고 통과 | 응시자 본인의 손·팔이 사람으로 잡히는 등 오탐이 있어 모델이 응시를 막으면 부당함. 사진과 물체 목록을 남겨 감독관이 판단 |
| 환경 점검 재시도 | 통과하지 못한 항목만 다시 | 이미 통과한 항목·사진을 다시 하게 하면 응시자 부담과 시간이 늘고, 책상 스캔 모델도 다시 받게 됨 |
| 연결 끊김 | 프론트 15초 + 서버 5분 유예의 두 층 | 15초는 순간 끊김을 넘기고 화면을 바로 막는 용도, 5분은 브라우저를 닫았다 다시 여는 경우까지 이어 푸는 서버 기준 |
| 감독관 영상 | **쓰지 않음** (2026-11-24). 이벤트 기록과 앞뒤 웹캠 사진으로 감독 | 핫스팟 응시자에서 영상 연결이 실패했고 TURN 없이는 쓸 수 없다. 상시 300명 × 영상 전송·저장도 피한다 |

### 개인정보를 지키는 감독 설계
- **문제:** 영상을 서버로 보내면 트래픽, 저장 공간, 개인정보 부담이 큽니다.
- **해결:** 브라우저 안에서 분석하고 이상 순간의 사진 1장만 보냅니다. 얼굴로 사람을 식별하지 않으므로 생체정보를 다루지 않고, 보관 기간이 지나면 삭제합니다.
- **보여 줄 숫자:** 회차 결과의 데이터 절감률 (실제 전송량 ÷ 영상 1.5Mbps 환산량).

### 오탐률을 숫자로 관리
- 조명(밝음·어두움·역광), 각도, 안경 조건마다 정상 응시를 녹화 없이 반복해 경고 수를 셉니다.
- 기준값(`PC_THRESHOLDS`)은 한 파일에 모여 있어 조정 전후를 같은 조건으로 비교합니다.

### 동시 시작·종료
- 시작은 서버만 판단하므로 시계가 틀린 기기도 같은 순간에 시작합니다.
- 종료는 스케줄러가 서버 시각으로 처리하고, 지연(`closed_at - ends_at`)을 숫자로 남깁니다.

### 면접 예상 질문
| 질문 | 답 |
| --- | --- |
| 브라우저 감지는 응시자가 끌 수 있지 않나? | 맞습니다. 그래서 단독 판정이 아니라 신호를 겹칩니다. 웹캠이 연결돼야 응시하고(휴대폰 보조 캠·화면 공유는 사용 안 함), 연결이 15초 넘게 끊기면 응시 화면이 막히고, 시험 화면 연결 신호가 끊기면 서버가 기록·만료시킵니다. 환경 점검에서 자동화 브라우저·가상 카메라를 거르고, 이벤트 앞뒤 웹캠 사진을 감독관이 사후에 확인합니다. 완전히 막으려면 잠금 브라우저가 필요하다는 한계도 문서로 밝혀 둡니다. |
| 오탐이 나면 어떻게 하나? | 자동 탈락이 없습니다. 이벤트는 사진과 함께 담당자가 OK/SUSPECT 로 판정하는 기록입니다. 오탐 자체는 개인별 보정·지속 시간·쿨다운으로 줄이고, 조건별 오탐률로 기준값을 조정합니다. |
| 응시자 1,000명 회차 통계는 어떻게 빠르게 뽑나? | 엔티티를 다 불러 계산하지 않고 집계 쿼리(인터페이스 프로젝션)로 DB 가 계산합니다. 지금 대상자 조회 1번 + 이벤트 집계 1번으로 끝납니다. 측정해서 느리면 그때 통계 테이블을 둡니다. |

## 부록 A. 감독에 쓰는 AI 모델 (모두 응시자 브라우저 안에서 실행)

| 모델 | 무엇을 보는가 | 어디에 쓰나 |
|---|---|---|
| **MediaPipe Face Landmarker** | 얼굴 점 478개, 얼굴 기울기, 눈 깜빡임·시선 | 얼굴 없음, 여러 얼굴, 고개 돌림, 시선 이탈 |
| **MediaPipe Pose Landmarker** | 어깨·몸통 위치 | 자리 이동, 몸 돌림 |
| **MediaPipe Hand Landmarker** | 손 위치 | 환경 점검: 손목 확인 |
| **MediaPipe Object Detector (EfficientDet-Lite0)** | 물체 찾기 (휴대폰, 노트북, 책 등) | **사용 안 함** (휴대폰 보조 캠 전용) |

- **MediaPipe**: 구글이 만든 브라우저용 영상 분석 도구. 컴퓨터 GPU 로 빠르게 돈다 (`@mediapipe/tasks-vision`).
- 얼굴로 **누구인지 알아보지 않는다.** 얼굴이 있는지, 어디를 보는지만 본다 → 생체정보를 다루지 않음.

## 부록 B. 자주 나오는 용어

| 용어 | 뜻 |
|---|---|
| **회차** | 시험 한 번. 시작·종료 시각과 과제 여러 개를 가진다 |
| **대상자** | 회차에 초대된 응시자 |
| **응시(attempt)** | 대상자가 과제 하나를 푸는 기록. 과제마다 1개 |
| **초대 토큰** | 메일 링크에 들어 있는 43자 비밀값. 로그인 대신 본인 확인 |
| **해시(SHA-256)** | 값을 되돌릴 수 없게 바꾼 지문. DB 에는 토큰 대신 이 지문만 저장 → DB 가 새도 링크를 못 만듦 |
| **서버 시각** | 응시자 PC 시계가 틀려도 모두 서버 시계로 판단 → 공정 |
| **행 잠금** | 같은 대상자 요청이 동시에 오면 줄 세우기. 시작 버튼을 두 번 눌러도 응시는 하나 |
| **아웃박스** | 브라우저가 감독 이벤트를 잠깐 쌓아 두는 곳. 인터넷이 끊겨도 나중에 다시 보냄 |
| **개인별 보정** | 시작 3초 자세를 "기준"으로 잡음. 카메라 각도가 달라도 오탐이 줄어듦 |
| **오탐** | 부정행위가 아닌데 경고가 뜬 것 |
| **분석 Worker** | 브라우저가 화면과 별도로 돌리는 작업 공간. 카메라 분석을 여기서 하면 응시 화면(타이핑)이 안 끊김. 안 되면 원래 방식(메인)으로 폴백 |
| **증거 구간** | 경고(이벤트) 앞 8초·뒤 4초의 사진 묶음. 사진 1장보다 맥락이 있고 연속 녹화보다 개인정보 부담이 작다 |
| **마이그레이션** | DB 표 구조를 바꾸는 SQL 파일 (`V2__erd_changes.sql`, `V11__connection_grace.sql`, `V14__env_scan_photos.sql`, `V19__env_check_notices.sql`) |
| **연결 유예** | 시험 중 연결이 끊겨도 기다려 주는 시간. 응시자 화면은 15초(웹캠), 서버는 5분(시험 화면 연결 신호). 넘으면 응시 화면 차단 / 링크 만료 |
| **하트비트** | 시험 화면이 10초마다 "살아 있음"을 서버에 알리는 신호 |
| **연결 채널** | 웹캠 하나. 연결돼야 응시할 수 있다 (휴대폰 보조 캠·PC 화면 공유는 사용 안 함) |
| **CSV 주입 방지** | `=` `+` `-` `@` 로 시작하는 칸 앞에 `'` 를 붙여 엑셀이 수식으로 실행하지 않게 함 |
| **데이터 절감률** | 실제 보낸 사진 용량 ÷ 영상으로 감독했다면 보냈을 양. 목표 99% 이상 절감 |
| **자동 제출 지연** | 종료 시각과 서버가 실제로 제출 처리한 시각의 차이. 목표 5초 이내 (테스트 0.8초) |
