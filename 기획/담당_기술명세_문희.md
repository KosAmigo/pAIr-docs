## 1. 개요

pAIr에서 **응시자가 과제를 고르고, 코드를 고치고 실행하고, AI에게 물어보며 풀고, 제출한 뒤 원하는 시점으로 돌아가 다르게 풀어 보기까지의 흐름**을 담당합니다.

응시자는 브라우저 편집기에서 코드를 고치고, [빌드]·[실행]은 한 번마다 새로 만드는 격리 컨테이너에서 합니다. AI에게 질문을 보낼 때마다 그 시점이 체크포인트로 자동 저장되어, 끝난 뒤 어느 질문 시점으로든 돌아갈 수 있습니다. 돌아가면 기존 응시는 그대로 두고 새 응시가 생겨서 두 풀이를 나란히 비교합니다. 채점, 리포트, 실전 시험 모두 응시(`attempts`)를 기준으로 붙기 때문에 응시 DB 전환을 가장 먼저 했습니다.

| 구분 | 내용 |
| --- | --- |
| 담당 흐름 | 과제 선택 → 코드 편집 → Docker 실행 → AI 채팅 → 제출 → 복기 트리 |
| 대표 기능 | Docker 샌드박스, 복기 트리 |
| 맡는 테이블 | `tasks`, `task_files`, `attempts`, `attempt_files`, `attempt_events`, `chat_turns`, `chat_attachments`, `checkpoints`, `checkpoint_files` (9개) |
| 핵심 목표 | 악성 코드 시나리오를 컨테이너에서 모두 차단, 체크포인트 복원 1초 이내, 편집기 진단 0.3초 이내, 동시에 채팅해도 크레딧 잔액이 음수가 되지 않음 |

## 4. 구조 설계

### 응시 흐름 (자가진단)

```
응시자 (과제 목록)
  → 과제 선택 → [응시 시작]
       응시 생성 + 공개 파일 복사 + 크레딧 차감
  → 풀이
       편집 (2초 자동 저장) · 편집기 진단 · [빌드] [실행]
       AI 질문 (보낼 때마다 체크포인트 자동 생성)
  → [제출]  SOLVING → FOLLOWUP, 파일·대화 잠금
  → 후속 질문 답변  FOLLOWUP → SCORING → 채점 요청(서버 스레드 풀 또는 Redis 큐, 팀원 1) → 채점 (팀원 2)
  → 끝난 뒤: 복기 트리에서 질문 시점 선택 → 새 응시 생성 (롤백)
```

### 실전 시험에서 달라지는 점 

| 항목 | 자가진단 | 실전 |
| --- | --- | --- |
| 응시자 | 로그인한 회원 (`attempts.user_id`) | 로그인 없음, 초대 토큰으로 본인 확인 (`attempts.participant_id`) |
| 응시 생성 | [응시 시작] 버튼 | 과제를 **처음 열 때** (과제마다 응시 1건) |
| 크레딧 | 응시 시작·롤백·채팅 턴마다 차감 | 없음 (기업 무료) |
| 종료 | 직접 제출 | 직접 제출 또는 종료 시각에 **자동 제출** (후속 질문 없이 바로 `SCORING`) |
| 롤백·복기 | 가능 | 불가 (DB가 막음) |

### 코드 실행 구조

```
[응시 서버 (백엔드)]   CodeRunner (인터페이스)
   ├─ LocalJvmRunner     개발·테스트용. 별도 JVM 실행
   └─ RemoteDockerRunner ── 내부 API (토큰) ──▶ [샌드박스 서버 (EC2)]  SandboxRunner
                                                  [빌드]·[실행]마다 일회용 컨테이너 1개 (docker run --rm, 끝나면 삭제)
                                                  소스 = 임시 폴더에 쓴 뒤 읽기 전용 마운트, /tmp 만 tmpfs 64MB
                                                  javac + JUnit, 30초 안에 끝나지 않으면 컨테이너 강제 종료
```

- 응시자 코드는 DB·API 키가 없는 실행 서버에서만 돕니다.
- 이 문서와 코드의 "샌드박스"는 격리 실행 환경을 뜻하는 일반 용어이고, 구현은 **일반 Docker 컨테이너**(실행마다 만들고 지움)입니다. AI 에이전트용 MicroVM 제품인 Docker Sandboxes(sbx)가 아닙니다.
- 컨테이너는 **풀이 중에 빌드·실행하는 도구**이고 풀이의 원본은 DB(`attempt_files`)입니다. 실행마다 DB의 파일을 새 컨테이너에 넣어 돌리므로, 컨테이너가 죽어도 잃는 것이 없고 이전 실행의 흔적도 다음 실행에 남지 않습니다.

### 컨테이너 수명

컨테이너는 실행 한 번에만 존재한다. 응시 시작이나 제출 때 컨테이너를 만들거나 지우는 일은 없다.

| 시점 | 동작 |
| --- | --- |
| 응시 시작 | 컨테이너를 만들지 않음 (파일은 DB에 저장) |
| [빌드]·[실행]·채점의 숨은 테스트 | 자리가 나면(동시 4개, 최대 60초 대기, 넘으면 503) 일회용 컨테이너를 `docker run --rm` 으로 만들고, 소스를 읽기 전용으로 마운트해 javac(+JUnit) 실행. 끝나면 컨테이너 삭제 |
| 30초 안에 끝나지 않음 | 컨테이너를 강제 삭제(`docker rm -f`)하고 `[TIMEOUT]` 안내 |
| 체크포인트·롤백 | 롤백은 새 응시이므로 복원할 컨테이너가 없음. 실행할 때 DB 의 복원된 파일을 새 컨테이너에 넣음 |
| 제출 (실전은 종료 자동 제출 포함) | 정리할 컨테이너가 없음. 후속 질문·채점은 DB의 파일을 씀 |
| 샌드박스 서버가 실행 도중 죽음 | 컨테이너 안의 `timeout`(서버 제한 + 시작 여유 15초 + 5초)이 스스로 종료시킨다(`--rm` 이라 삭제까지). 서버가 다시 켜질 때 남은 `pair-run-*` 컨테이너를 모두 지운다 |

## 5. 주요 기능 명세

### 5.1 응시 상태와 시작

- 상태는 `SOLVING → FOLLOWUP → SCORING → DONE`, 채점이 실패하면 `ERROR`(다시 채점하면 `SCORING`)입니다. 서비스가 현재 상태를 검사하고, 상태와 제출 시각의 짝은 DB CHECK 가 막습니다. 허용 전이 표는 아직 없습니다.
- 모드는 `SELF`(회원, 자가진단용 과제)와 `LIVE`(대상자, 기업용 과제)입니다. DB가 `(task_id, mode)` 복합 FK와 CHECK로 둘이 섞이지 않게 막습니다. 기업용 과제는 자가진단 목록에 나오지 않습니다.
- 자가진단은 시작할 때 크레딧을 차감합니다(채점 1회 비용 포함). 잔액이 부족하면 시작할 수 없고, 같은 과제를 다시 풀면 새 응시로 같은 크레딧입니다.

### 5.2 작업 파일과 자동 저장

- 시작할 때 과제의 공개(`VISIBLE`) 파일만 `attempt_files`로 복사합니다. 숨은 테스트와 정답(`HIDDEN`)은 응시자에게 보내지 않고 채점할 때만 읽습니다.
- 수정 가능한 파일은 과제마다 지정하고 나머지는 읽기 전용입니다. 서버가 저장과 수정 제안 적용 때 경로 규칙(`logs/`·`자료/`)과 `task_files.read_only` 를 검사합니다. 컨테이너에는 소스 전체가 읽기 전용으로 들어갑니다.
- 입력이 멈추고 2초 뒤 자동 저장하고 `SAVE` 기록을 남깁니다. `SOLVING`일 때만 저장되고 제출하면 잠깁니다.
- `attempt_files`는 최종본만 가집니다. 이전 상태는 체크포인트가 가집니다.

### 5.3 빌드·실행 (Docker 샌드박스)

- **[빌드]**는 컴파일만, **[실행]**은 컴파일 + JUnit입니다. 과제 `test/` 폴더의 보이는 테스트와 응시자가 추가한 테스트가 돌고, 숨은 테스트는 화면 [실행]에 포함하지 않고 채점 때 서버가 따로 돌립니다.
- 컨테이너 설정 :

| 설정 | 막는 것 |
| --- | --- |
| `--network none` | 외부 접속, 데이터 유출 |
| `--memory 512m --memory-swap 512m` | 메모리 폭탄 |
| `--cpus 1` | CPU 독점 |
| `--pids-limit 128` | 프로세스·스레드 폭탄 |
| `--read-only` + `/tmp` tmpfs 64MB (소스는 읽기 전용 마운트) | 시스템 파일 쓰기, 디스크 채우기 |
| `--cap-drop ALL`, `no-new-privileges`, 일반 사용자 | 권한 상승, 컨테이너 탈출 시도 |
| `--init` + 30초 강제 종료 + 남은 프로세스 정리 | 무한 루프, 교착, 좀비 프로세스 |

- 컨테이너에는 실행할 소스를 임시 폴더에 쓴 뒤 **통째로 읽기 전용 마운트**합니다. 응시자 코드는 소스를 바꿀 수 없고, 쓸 수 있는 곳은 `/tmp`(64MB)뿐입니다.
- 결과: 컴파일 오류 위치(줄·열), 통과·실패 수, 출력 줄. 요약은 `BUILD`·`RUN` 이벤트로 남아 "테스트를 실행해 확인했는지" 채점 근거가 되고, 원래 코드를 고친 뒤 모든 테스트가 통과한 첫 실행은 `FIRST_VALID`로 기록합니다.
- 30초를 넘으면 중단하고 "교착 상태일 수 있습니다"를 안내합니다. 서버가 바빠서 느려진 것을 응시자 책임으로 보지 않도록, 제한 시간은 실행이 시작된 순간부터 잽니다.

### 5.4 편집기 진단 (JDK Compiler API)

- 입력이 멈출 때마다 서버가 코드를 분석해 오류 밑줄, 타입을 아는 자동 완성, 정의로 이동을 돌려줍니다.
- 입력 중인 코드는 대부분 문법이 깨져 있어서, 문법 오류가 있어도 타입 분석까지 진행하는 옵션(`-XDshould-stop.ifError=FLOW`)을 씁니다. 파일 관리자는 풀에 모아 재사용하고, 동시 분석은 4개까지입니다.
- 코드를 실행하지 않고 분석만 하므로 컨테이너가 필요 없습니다. 

### 5.5 AI 채팅

- 답변은 SSE로 글자가 오는 대로 보냅니다(가상 스레드). 한도: 질문 1,000자, 응시당 질문 40회, 출력 8,000토큰, 추론 강도 low (설정 파일로 교체).
- 한 질문의 처리를 세 단계로 나눠 **AI 호출을 트랜잭션 밖**에 둡니다.
  1. 상태·크레딧 확인 (짧은 읽기)
  2. AI 호출 (평균 7.6초, 트랜잭션 없음)
  3. 질문·답 두 턴 저장 + 체크포인트 생성 + 크레딧 차감 (짧은 트랜잭션)
- AI가 빈 답을 주면(추론 모델이 한도 안에서 답을 못 끝낸 경우) 3단계를 하지 않고 `CHAT_EMPTY`만 기록합니다. 턴도 크레딧도 남지 않고, 그 질문은 채점에서 제외합니다.
- 크레딧이 바닥나면 **채팅만 막고** 편집·저장·제출은 됩니다. 차감은 저장된 턴 ID를 가리키므로(`credit_ledger.turn_id`) 턴 저장과 한 트랜잭션입니다. 차감 전에 회원 행을 `FOR UPDATE`로 잠가 동시 요청에도 잔액이 음수가 되지 않게 합니다(팀원 1의 크레딧 API 호출).
- 첨부는 과제 자료(PDF 페이지)와 내 작업 파일만 됩니다. 질문당 5개·합계 3만 자까지이고, 새로 붙인 파일마다 크레딧 5가 더 듭니다. 서버가 파일을 직접 읽어 실제로 AI에게 보낸 글자를 `chat_attachments.sent_text`에 복사해 둡니다(작업 파일은 계속 바뀌므로).
- AI는 응시자가 대화에 붙여 넣거나 첨부한 내용만 봅니다.
- 스트리밍 중 응시자가 화면을 닫으면 보내기가 실패하고, AI 호출을 멈추고 턴을 저장하지 않습니다. 크레딧도 차감되지 않습니다.
- AI 호출 수 제한(팀원 1)은 **아직 없습니다**. 생기면 약속한 응답 형식으로 안내합니다.

### 5.6 AI 수정 제안 (SEARCH/REPLACE)

- AI가 답 끝에 "바꿀 원래 내용 / 새 내용" 블록을 붙이고, 응시자가 [적용]하면 서버가 파일에 반영해 편집기가 바로 바뀝니다. [거절]하면 파일은 그대로입니다.
- 원래 내용이 파일에서 **한 글자도 틀리지 않고 그대로 있을 때만** 바꿉니다. 응시자가 그 사이 고쳐서 못 찾으면 적용을 막고 "코드 보기로 확인하고 직접 고쳐 주세요"를 안내합니다. 이미 적용한 제안은 다시 적용할 수 없습니다.
- 적용·거절은 `AI_EDIT` 이벤트로 남습니다. 채점이 "적용한 뒤 테스트 없이 제출"(C1)과 "제안을 걸러냄"을 판단하는 근거입니다.
- 새 파일 만들기: 지금은 AI 수정 제안으로 **만들 수 있습니다**(허용 경로만, `AttemptStateRepository.creatable`). "지정한 파일만 수정" 규칙에 맞춰 막을지는 팀 확정이 필요합니다.

### 5.7 제출·후속 질문·채점 연결

- 제출하면 파일과 대화가 잠기고 `SOLVING → FOLLOWUP`, `SUBMIT` 기록을 남깁니다. 컨테이너는 실행마다 지우므로 따로 정리하지 않습니다.
- 후속 질문은 과제마다 3개입니다. 답할 때 보인 질문 문구와 답을 응시 행(`attempts.followup_questions`·`followup_answers`)에 저장해, 과제를 나중에 바꿔도 채점이 응시자가 본 문구를 씁니다.
- 답변까지 끝나면 `SCORING`으로 바꾸고 채점을 맡깁니다. Redis 채점 큐(팀원 1)는 설정(`PAIR_SCORING_QUEUE_ENABLED`, 기본 꺼짐)이고, 꺼져 있으면 서버 안 스레드 풀이 채점합니다. 서버 시작 때 `SCORING`에 남은 응시는 다시 맡깁니다.
- 실전의 자동 제출은 후속 질문 없이 바로 `SCORING`이 되고 `auto_submitted`가 켜집니다.

### 5.8 체크포인트·롤백·복기 트리

**체크포인트**
- 응시자가 **질문을 보낼 때마다 자동으로** 만듭니다(질문 턴 1개당 1개, 질문 저장과 같은 트랜잭션). 그래서 어느 질문 시점으로든 돌아갈 수 있고, "그 질문을 다르게 해 보기"가 롤백의 목적과 맞습니다.
- 파일은 **바로 앞 체크포인트(첫 번째는 과제 원본)에서 바뀐 것만** `checkpoint_files`에 저장합니다.
- 질문 k 시점 복원은 `turn_no <= k`인 체크포인트 파일을 쿼리 한 번으로 읽어, 과제 원본 위에 오래된 순서로 덮어씁니다(Java). H2 테스트에서 `DISTINCT ON`을 쓸 수 없어 이 방식을 택했습니다.
- DB 규칙: 체크포인트는 같은 응시의 **질문(USER) 턴만** 가리키고(`(attempt_id, turn_no, turn_role)` → `chat_turns` 복합 FK), 질문 하나에 하나만 만들 수 있습니다.

**롤백 = 새 응시 생성**
- 원래 응시는 그대로 두고, `forked_from_checkpoint_id`가 그 체크포인트를 가리키는 새 응시를 만듭니다. 원래 대화·파일·채점 근거가 보존되고, 복기 트리에서 두 갈래를 나란히 비교합니다.
- 질문 k에서 갈라지면 원래 응시의 **1 ~ k-1 턴을 새 응시의 `chat_turns`로 같은 턴 번호로 복사**합니다. 복사한 턴은 크레딧을 다시 차감하지 않고, 이후 새로 보낸 질문만 차감합니다. 채점·리포트는 응시 하나의 대화만 읽으면 됩니다.
- 파일은 복원값으로 새 응시의 `attempt_files`를 채웁니다. 다음 실행 때 이 파일이 새 컨테이너에 들어갑니다. 롤백에는 `ROLLBACK` 크레딧만 차감합니다(새 응시에 `ATTEMPT_START`는 붙이지 않음, 원장 `UNIQUE (attempt_id, reason)`).
- **자가진단만** 롤백할 수 있습니다. 실전 응시는 DB CHECK(`forked_from_checkpoint_id IS NULL OR mode = 'SELF'`)가 막습니다. 롤백 횟수 제한은 없고 크레딧으로만 제한합니다.
- 원래 응시와 같은 회원·같은 과제인지는 서비스 코드가 검사합니다(DB로는 표현이 어려움).

**복기 트리**
- 노드는 응시, 간선은 `attempts.forked_from_checkpoint_id → checkpoints.attempt_id`입니다. 어느 질문 시점에서 갈라졌는지(`checkpoints.turn_no`)를 간선에 표시하고, 두 갈래 점수는 팀원 2의 리포트 조회를 읽습니다.

## 7. 기술 선택 근거

| 결정 | 선택 | 근거 |
| --- | --- | --- |
| 응시 기록 저장 | JSON 파일 → DB | 채팅·작업 기록·실행·제출·채점·복기가 같은 데이터를 쓰고, 동시 응시·관계 조회·상태 변경·백업이 필요함 |
| DB 관리 | Flyway + `ddl-auto: validate` | 제약(CHECK, 복합 FK, 부분 인덱스)을 JPA가 만들 수 없음. 팀원 모두 같은 순서로 적용하고 엔티티와 DB가 어긋나면 서버가 안 켜짐 |
| 연관관계 조회 | 연관관계 매핑 없이 ID 컬럼 + 화면별 일괄 조회 | 필요한 행만 읽습니다. 목록에서 응시마다 다시 조회하면 N+1이 생겨, 11-25에 일괄 조회로 고쳤습니다 ([기록](../기술검증%20및%20개선/문희/2026-11-25.md)) |
| 테스트 DB | H2 + 조건부 실제 PostgreSQL | 평소 테스트는 빠른 H2. 복합 FK·CHECK·엔티티와 스키마 일치처럼 H2가 못 보는 것은 `PAIR_PG_TEST_URL`이 있을 때 빈 로컬 PostgreSQL에서 확인 |
| 대화·작업 기록 | 추가 전용 | 감점 근거가 "#T03 대화", "테스트 실행 안 함"처럼 이 기록을 가리킴. 바뀌면 점수의 근거가 무너짐 |
| 코드 실행 | Docker 샌드박스 | 서버에서 직접 실행하면 무한 루프·파일 삭제·외부 접속으로 서버와 키가 위험. 외부 실행 API는 파일 여러 개·JUnit·작업 폴더 유지가 어렵고 코드가 밖으로 나감 |
| 실행 서버 | DB·API 키가 없는 별도 서버 | 컨테이너를 만들 권한은 서버 권한이므로 응시자 코드와 비밀 정보를 같은 서버에 두지 않음 |
| 컨테이너 단위 | 실행마다 일회용 1개 (2026-11-21 결정) | 시작 시간(약 1.6초)이 매번 들지만, 응시 중 놀고 있는 컨테이너가 없어 서버 자원을 실행하는 동안만 쓰고, 이전 실행의 흔적이 남지 않으며, 정리할 컨테이너가 없어 정리 실수가 없음. 파일은 DB에서 매번 넣음 |
| 작업 폴더 | 소스는 읽기 전용 마운트, 쓰기는 크기 제한 `/tmp`(tmpfs 64MB)만 | 과제 자료·숨은 테스트 보호, 디스크 채우기 방지. 제한은 응시자 코드가 바꿀 수 없는 곳(컨테이너 설정)에 둠 |
| 편집기 진단 | CodeMirror + JDK Compiler API | 언어 서버는 응시자당 약 250MB, Compiler API는 약 28MB·평균 0.1초. 코드를 실행하지 않아 격리가 필요 없음 |
| 채팅 전송 | SSE | 질문 1번 → 답 스트림이라 한 방향이면 충분. 일반 HTTP라 인증·프록시를 그대로 씀 (WebSocket은 양방향이 필요할 때) |
| 동시 스트림 | 가상 스레드 (Java 21) | 스트림은 AI 답을 기다리며 대부분 놀고 있음. 일반 스레드 풀은 동시 채팅이 몰릴 때 바닥남 |
| AI 호출과 트랜잭션 | AI 호출은 트랜잭션 밖 | 7.6초 걸리는 호출 동안 DB 연결과 회원 행 잠금을 붙잡지 않음 |
| 크레딧 차감 | 원장 + 회원 행 비관적 잠금 (팀원 1 API) | 잔액 컬럼만 쓰면 이력이 없고, 잠금이 없으면 동시 요청이 같은 잔액을 봄. 차감은 짧고 한 회원 안에서만 충돌해 잠금이 재시도보다 단순 |
| 수정 제안 | SEARCH/REPLACE + 응시자 승인 | 파일을 직접 고치면 검토 불가·AI가 못 본 내용을 덮어씀, 전체 재작성은 토큰 낭비, 줄 번호는 파일이 바뀌면 틀어짐. 못 찾으면 적용을 막음 |
| 체크포인트 시점 | 질문마다 자동 | `attempt_files`는 최종본만 가져서 수동 저장이면 저장 안 한 시점으로 못 돌아감. 롤백의 목적이 "그 질문을 다르게" |
| 체크포인트 저장 | 바뀐 파일만 | 질문이 자동으로 늘어난 만큼(최대 40개) 매번 전체를 복사하면 같은 파일이 쌓임. 복원은 쿼리 한 번으로 읽어 덮어씀 |
| 롤백 | 새 응시 생성 | 기존 응시를 되돌리면 이미 받은 채점 근거(대화·파일)가 사라짐. 두 갈래를 나란히 비교할 수 있고 테이블이 더 필요 없음 |
| 롤백 대화 | 이전 턴을 새 응시로 복사 | 대화는 글자라 중복 부담이 작고, 채점·리포트가 응시 하나만 읽으면 됨. 참조 방식은 롤백이 여러 번이면 거슬러 올라가야 함 |

**제품 코드로 잰 값 (2026-11-21)**

실제 PostgreSQL(pgvector/pg16, 같은 PC의 Docker)에서 제품 코드(`CheckpointService`, `RollbackService`, `SandboxRunner`)를 직접 호출해 쟀습니다.

측정에 쓴 `*BenchTest` 3개는 평소 빌드에서 쓰이지 않아 2026-11-24 에 삭제했다(커밋 `9a2f4ff`). 다시 잴 때는 `9a2f4ff^` 에서 되살려 `PAIR_BENCH=1` 로 돌린다.

체크포인트 복원·롤백 (`CheckpointRestoreBenchTest`). 과제 order-deadlock(파일 11개, 6KB), 질문 N개 응시의 질문 N 시점(변경분을 가장 많이 덮는 지점)을 30번 복원. 목표는 1초 이내.

| 질문 수 | 복원 중앙값 (보통 / 최악) | 복원 최대 (보통 / 최악) | 롤백 (보통 / 최악) |
| --- | --- | --- | --- |
| 1 | 5.4 / 2.3ms | 6.9 / 3.0ms | 41 / 16ms |
| 10 | 2.9 / 2.6ms | 9.3 / 5.9ms | 36 / 27ms |
| 20 | 2.6 / 3.5ms | 3.1 / 8.1ms | 44 / 42ms |
| 40 | 2.5 / 5.3ms | 6.3 / 9.7ms | 99 / 151ms |

보통 = 질문마다 파일 1개가 바뀜, 최악 = 질문마다 파일 11개가 모두 바뀜(40개일 때 저장 행 440개). 롤백은 새 응시를 만들고 파일과 앞 대화를 복사하는 시간이다. 한계: 작은 파일, 같은 PC의 DB, 예열 후 값이라 원격 DB에서는 네트워크 시간이 더해진다. 재현: `PAIR_BENCH=1 PAIR_PG_TEST_URL=... sh gradlew test --tests '*CheckpointRestoreBenchTest'`.

샌드박스 동시 실행 (`SandboxConcurrencyBenchTest`, 호스트 8코어, 실행당 CPU 1·메모리 512MB·제한 30초, 상한 해제):

| 동시 실행 | 전체 | 평균 | 최대 | 성공 |
| --- | --- | --- | --- | --- |
| 1 | 5.5초 | 5.5초 | 5.5초 | 1/1 |
| 4 | 7.2초 | 7.1초 | 7.2초 | 4/4 |
| 8 | 8.8초 | 8.4초 | 8.8초 | 8/8 |
| 16 | 28.2초 | 26.0초 | 28.2초 | 16/16 |

16개는 모두 성공했지만 최대 28초로 제한 30초에 가깝다. 그래서 동시 실행 상한을 코어 수 이하(기본 4)로 두고 나머지는 대기열에 세운다.

## 9. 향후 과제

2026-11-26 기준 남은 것입니다. 응시 DB 전환, 샌드박스 연결·동시 실행 상한·컨테이너 정리, 크레딧 연동, 체크포인트·롤백·복기 화면, 실전 응시의 초대 토큰 확인은 구현돼 있습니다.

| 과제 | 내용 |
| --- | --- |
| 샌드박스 용량 | 목표 인원 결정 → 1건의 단계별 시간 측정, Java 시작 옵션, 상한 2 측정, [빌드] 분리 검토 → 사양 확정 뒤 재측정 |
| 보안 그룹 점검 | 8282 는 앱 서버만, 8181 은 인터넷 차단 |
| 컨테이너 풀 (확장) | 미리 띄워 둔 일회용 컨테이너. 쓴 컨테이너는 버림 |
| AI 호출 수 제한 응답 | 팀원 1의 제한이 생기면 채팅의 안내 처리 |
| 응시 상태 전이 표 | enum 허용 전이, 팀원 2·4와 |
| 제출 → 채점 재발행 | 서버 시작 때 복구는 있음. 주기 재발행이 필요한지 팀원 1·2와 확인 |
| 수정 제안의 새 파일 만들기 | 지금은 만들 수 있음. 막을지 확정 |
| 숨은 테스트 분리 | 응시자 코드와 다른 컨테이너에서 실행할지, 위협 범위를 정한 뒤 판단 |
| 편집기 도우미 부하 | 지금은 앱 서버에서 돎. 서버 사양에 맞춰 재측정 |
| 체크포인트 저장 범위 문서 | 구현은 바뀐 파일만. [디자인_패턴.md](../설계/디자인_패턴.md) 11번의 전체 저장 서술과 맞추기 |
| 실전 응시의 체크포인트 | 지금은 만들어짐(롤백은 불가). 만들지 않을지 확정 |
| 제출 뒤 재진입 | 지금은 제출하면 잠금 |

**예상 질문**

| 질문 | 답 |
| --- | --- |
| 응시자 500명이 동시에 풀면? | 컨테이너는 응시 수가 아니라 **그 순간 실행 중인 수**만큼 생깁니다. 동시 실행 상한과 대기열이 있고, 대기 한도를 넘으면 503입니다. 지금 사양(vCPU 2, 상한 1)에서 측정한 것은 동시 요청 약 10건까지라서 500명을 감당한다고 말할 수 없고, 사양이나 서버 수를 늘려 다시 측정해야 합니다. |
| AI가 파일을 바로 고치게 하지 않은 이유는? | 응시자가 변경을 검토하지 못하고, AI가 못 본 내용을 덮어쓸 수 있습니다. SEARCH/REPLACE는 원래 내용이 정확히 일치할 때만 바꾸고, 적용·거절이 기록으로 남아 "AI 결과를 검증했는가"를 채점할 수 있습니다. |
| 크레딧이 동시에 두 번 차감되면? | 차감 전에 회원 행을 `FOR UPDATE`로 잠가 순서대로 처리합니다. 원장의 `balance_after >= 0` CHECK가 마지막 방어선이고, 같은 질문을 두 번 차감하는 것은 `UNIQUE (turn_id)`가 막습니다. |
