## 2. 기술 선택

근거 수준: **측정** = 후보를 직접 돌려 비교 / **일부** = 고른 것만 재서 기준 통과 확인 / **논리** = 장단점으로 판단(4장)

| 결정 | 선택 (다른 후보) | 근거 | 수준 |
|---|---|---|---|
| 점수 산출 | 체크 판정 + 코드 감점 (LLM이 점수 직접) | 덜 흔들리고 더 정확함, 근거 없는 감점은 무효 처리 (19) | 측정 |
| 채점 모델 | Haiku 5.5 + gpt-6.1-terra (Sonnet 5.5, gpt-6.1-sol) | 정확도는 같은 수준, 비용 1/4 (17) | 측정 |
| 채점 방식 | 두 회사 모델 이중 판정 (한 모델) | v6에서 두 모델이 함께 틀린 칸 0개, 한쪽만 틀리면 절반 감점이라 오차가 반으로 줄어듦. 한쪽 장애 때 대체 가능 | 측정 (terra 단독 재검토 필요) |

## 3. 항목별 메모

### 채점 (1\~6, 17, 19)

- **3 채점 일관성 (⚠️)**
  - 판정 기준 문장을 계속 구체화함: v2 → v3 → v4 → v5(U2, K2) → v6(U1, C3, D1, D4, 이유와 판정 값 일치 규칙).
  - 기준을 고치면 정확도는 올랐지만(아래 17번) 흔들림은 줄지 않았음. 같은 조건으로 여러 번 돌리면 회차마다 평균 1.4\~3.1점(v4 1.4·3.1, v5 3.0·2.6, v6 2.6·2.9)으로, 처음 잰 v4의 1.4점은 운이 좋았던 값임.
  - 남은 흔들림의 원인: 한 모델만 "걸림"이라고 하면 절반 감점이 되어 회차마다 2\~3점씩 오르내림. 기준 문장보다는 모델이 매번 조금씩 다르게 답하는 탓이라 문장으로는 더 줄이기 어려움.
  - 다음에 볼 것: terra 단독 채점(아래 이중 판정 참고), 한 체크를 여러 번 물어 다수결로 정하기.
- **4 두 모델 차이**: v6에서 정답표 690칸 중 12\~16칸(1.7\~2.3%)에서 엇갈렸고, 그때는 늘 한쪽이 맞았음.
- **17 채점 모델 정확도**: v6 두 회차 기준 Haiku 98.1\~98.8%, terra 99.4\~99.6%. 상위 모델(Sonnet 96.4%, sol 97.1%)은 v4 기준으로 같은 v4의 Haiku·terra(96.8\~97.7%)와 같은 수준인데 비용은 약 4배($0.075). 138칸에서 1칸이 0.7%p라 1\~2%p 차이는 우열로 보지 않음.
  - 정답표를 고친 칸 4개(이유는 정답표 파일의 note에 적음): l5r P2(걸림), gmp C1(안 걸림, AI 수정을 적용하지 않음), al0 P4(걸림, 한계 언급 없음), anp D3(안 걸림, 출처를 따질 수치가 없음).
- **19 점수 산출 방식**: 같은 정보와 같은 기준 문장(v4)을 주고 항목 점수만 직접 매기게 함(`grader/direct_compare.py`, $0.27). 비교 대상은 같은 v4로 돌린 체크 판정 2회.
  - 총점 차이 평균: 점수 직접 5.3점(최대 16점) vs 체크 판정 1.4\~3.1점(최대 4\~8점).
  - 정답표 기준 기대 총점과의 오차: 점수 직접 4.6점 vs 체크 판정 1.8\~2.3점.
  - 점수 직접 방식은 이유 문장이 전부 칭찬인데도 "다만 \~가 부족했다"처럼 막연한 말로 항목마다 2\~6점을 깎았음. 체크 판정은 근거 턴이 없는 감점을 코드가 무효로 처리함.
- **이중 판정**: v6에서 두 모델이 함께 틀린 칸은 0개였고, 틀린 칸은 모두 한쪽만 틀려 절반 감점으로 끝났음. 다만 terra 혼자 정확도(99.4\~99.6%)가 Haiku보다 높아서, terra 단독이 더 정확하고 덜 흔들릴 가능성이 있음. 비용과 장애 대비까지 같이 따져 다시 볼 것.

### 실행 환경 (7\~10)

- **7**: `--network none --memory 512m --cpus 1 --pids-limit 128 --read-only --cap-drop ALL --init`. 작업 폴더는 크기 제한 tmpfs 볼륨(64MB, 파일 2만 개). Docker Desktop은 `--storage-opt size`를 지원하지 않아 tmpfs를 씀. 응시 중에는 컨테이너를 띄워 두고 보관은 체크포인트 tar로 함.
- **8**: 작업 폴더를 tar로 저장·복원. 체크포인트 1개에 20KB.
- **9**: 폴더는 읽기 전용, 지정 파일만 쓰기 허용. 롤백은 root 컨테이너로 복원.
- **10**: CodeMirror + JDK 컴파일러 API. 30명 동시 입력 시 CPU 1개 1.4초, 2개 0.7초. 언어 서버는 1명당 250MB라 제외.

### RAG (11\~15)

- **11**: PDFBox의 위치 정렬을 켜면 2단 편집에서 좌우 줄이 섞여서 끔. Tika도 20/20이지만 내부에서 PDFBox를 씀.
- **12**: 3-large는 1위 적중만 좋고(14 vs 10) 비용은 약 6.5배. 질문 20개라 1개 차이가 5%p여서 19 vs 17은 확실한 차이로 보지 않음.
- **13**: 고정 800자 19/20, 400자 19/20, 200자 13/20. 쪽이 짧은 문서라 쪽 단위가 가장 단순함.
- **14**: 과제 1,000개 × 조각 50개. HNSW는 가까운 40개를 먼저 고른 뒤 과제로 걸러서 결과가 0개였음(반복 스캔을 켜도 재현율 40%). 인덱스는 391MB.
- **15**: 자료 12개(39,410자)로 통째로/RAG 각 3회 비교. 입력 토큰 60\~76% 절감, 비용 −47%. 총점 차이 4.7점 중 자료를 보는 체크(C2, C3)는 2점이고 나머지는 자료와 무관한 체크의 흔들림. 문서가 늘수록 절감이 커짐.

### 과제 생성 (16, 18)

- **16**: 관리자 폼 → gpt-6.1-terra 구조화 출력 → 샌드박스 자동 확인(시작 코드 컴파일, 숨은 테스트가 시작 코드에서 실패하고 정답에서 통과). 평균 38초.
- **18**: 자료 CSV·문서, 숨은 체크리스트, 함정, 객관식·단답형 문항을 생성하고 자동 확인함(단답형 24개 검산 일치, Claude Sonnet이 44문항 모두 정답). 평균 66초.
- 공통: 난이도와 함정이 실제 응시자를 걸러 내는지는 자동 확인으로 알 수 없어 관리자 검수(HIDDEN → OPEN)와 파일럿에서 봄.

## 4. 측정하지 않은 선택의 근거

### 벡터 DB: pgvector

우리 조건: 검색은 항상 과제 하나 안(수십 조각)에서만 하고, 자료는 과제와 같이 생기고 같이 지워지고, 시험 자료라 밖으로 보내지 않는 게 좋고, 운영할 서버는 적을수록 좋음.

| | 장점 | 우리 조건에서 걸리는 점 |
|---|---|---|
| pgvector | 과제 표와 같은 DB, 한 트랜잭션으로 저장·삭제, 서버 추가 없음 | HNSW에 필터를 걸면 결과가 빔 → 정확 검색으로 해결 (14) |
| Pinecone | 운영할 게 없음, 큰 규모에 강함 | 자료가 외부로 나감, 비용, 규모 이점이 필요 없음 |
| Qdrant | 필터와 근사 검색을 같이 잘함 | 서버 하나 더 운영, PostgreSQL과 데이터를 따로 맞춰야 함 |
| Chroma | 설치가 가장 쉬움 | Java 지원이 약하고 운영 경험이 적음 |

전용 DB의 강점은 아주 많은 조각에서 찾을 때 나오는데, 우리는 과제로 먼저 걸러 수십 개만 남김. 전체 자료를 한꺼번에 검색해야 하는 날이 오면 Qdrant를 먼저 검토함. Spring AI `VectorStore`가 네 가지를 모두 지원해서 바꾸기도 어렵지 않음.

### LLM 연동: Spring AI

- 우리는 호출, 구조화 출력, 임베딩, 캐시만 씀. Spring AI는 두 회사를 같은 `ChatModel`로 다루고, `BeanOutputConverter`로 JSON Schema 출력을 지원함.
- LangChain4j는 에이전트와 RAG 도구가 강점인데 우리는 쓰지 않음. 회사별 SDK는 새 기능이 가장 빠르지만 두 회사 코드를 따로 짜야 함.
- 막힌 곳은 Batch API 하나뿐이었고, `BatchClient`에서 REST로 직접 호출해 해결함.

### 그 밖

- **출력 형식**: 함수 호출은 도구를 부르는 형태라 응답에서 꺼내는 단계가 하나 더 있음. 판정 결과만 받으면 되므로 JSON Schema가 더 단순함.
- **임베딩 후보**: OpenAI 모델만 비교함(키를 늘리지 않으려고). 실제 자료로 적중률이 90% 밑이면 bge-m3(직접 설치, 자료가 밖으로 안 나감)를 먼저 비교함.
- **캐시**: 실험에서 Claude는 입력의 49%, OpenAI는 88%가 캐시에서 읽힘. 같은 샘플을 연달아 채점한 조건이라 높게 나왔을 수 있음. 실제 적중률은 파일럿에서 확인함.

## 5. 서버 구조

```
브라우저 → AWS EC2 (무료): Spring Boot + PostgreSQL (회원, 응시 기록, AI, 채점)
                │ 내부 API (토큰, AWS IP만 허용)
                ▼
           Oracle Cloud (무료 ARM): 실행 서버 (컨테이너, 테스트 실행, 롤백, javac 분석)
```

- 응시자 코드는 DB, API 키와 다른 서버에서 실행함.
- 응시 시작 때 가장 한가한 실행 서버를 DB에 기록하고 끝까지 그 서버만 씀. 1대로 시작해 늘면 추가함.
- 실행 서버 장애 시 실행을 멈추고 시간을 보정함. 제출 파일은 AWS에 보관함.
