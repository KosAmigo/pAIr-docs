- 판정 호출이 두 번이라 한 모델만 쓸 때보다 비용이 늘지만, 그래도 건당 $0.018로 목표 $0.05 안입니다.

### LLM 연동: Spring AI vs LangChain4j vs 회사별 SDK

직접 비교해 재지는 않았습니다. 우리가 쓰는 기능 기준으로 장단점을 정리했습니다.

| | Spring AI | LangChain4j | 회사별 SDK |
|---|---|---|---|
| 장점 | Spring 공식 프로젝트, Boot 자동 설정. 두 회사 채팅·임베딩을 같은 `ChatModel` 방식으로 쓰고, `BeanOutputConverter`로 JSON Schema 출력, Anthropic 캐시 옵션, pgvector `VectorStore` 지원 | 인터페이스만 선언하면 되는 AI Services, 에이전트·RAG 도구가 많음, Spring Boot starter 있음 | 새 기능(Batch, 캐시 세부 옵션)을 가장 먼저 씀 |
| 단점 | Batch API 없음, 새 기능 반영이 SDK보다 늦음, 1.x 버전 사이 API 변경 | Spring 공식이 아님. 우리가 쓰는 기능(호출, 구조화 출력, 임베딩)에서는 더 얻는 게 적음 | 두 회사 코드를 따로 짜고 응답 형식을 맞추는 코드를 직접 작성 |

**결론**: 우리는 에이전트나 복잡한 체인 없이 "호출 + 구조화 출력 + 임베딩"만 쓰므로 Spring AI로 충분합니다. 실제로 막힌 곳은 Batch 하나뿐이었고, `BatchClient`에서 REST로 직접 호출해 보완했습니다.

### 점수 산출: 체크 판정 + 코드 감점 vs LLM이 점수 직접 (19번)

같은 샘플 7개 × 5회, 같은 두 모델(Haiku + terra), 같은 정보와 같은 기준 문장(v4)을 주고 **항목별 점수만 직접** 매기게 했습니다. 자동 체크(숨은 테스트 등)는 v4 결과를 그대로 써서 판정 부분만 비교했습니다. 스크립트: pAIr-back `grader/direct_compare.py`, 결과: `grader/runs/direct-20261119-134718`, 비용 약 $0.27.

| 샘플 | 점수 직접 5회 | 차이 | 지금 방식(v4) 5회 | 차이 | 기대 총점 |
|---|---|---|---|---|---|
| 개발 · 모범 | 91 94 94 96 92 | 5 | 100 ×5 | 0 | 100 |
| 개발 · 모범을 반말로 | 98 94 95 100 100 | 6 | 100 ×5 | 0 | 100 |
| 개발 · 후속 답변이 실제와 다름 | 93 ×5 | 0 | 93 ×5 | 0 | 96 |
| 개발 · 증상만 가림 | 59 75 60 69 61 | **16** | 73 73 73 75 73 | 2 | 73 |
| 개발 · 통째로 맡김 | 47 50 50 48 47 | 3 | 50 50 49 48 48 | 2 | 35 |
| 비개발 · 모범 | 97 98 98 97 96 | 2 | 96 98 98 98 98 | 2 | 96 |
| 비개발 · AI 답 그대로 | 58 63 61 61 59 | 5 | 65 63 61 63 65 | 4 | 62 |
| **합계** | 차이 평균 **5.3**, 최대 16 | | 차이 평균 **1.4**, 최대 4 | | |

기대 총점(정답표대로 감점했을 때의 총점)과의 평균 오차는 점수 직접 5.4점, 지금 방식 3.0점입니다.

- **흔들림이 4배 가까이 큼**: "증상만 가림" 샘플은 같은 응시인데 59점에서 75점까지 나왔습니다. Claude가 한 번은 활용력 6점, 다음에는 15점을 줬습니다. 체크 판정은 "걸렸나/안 걸렸나"만 정하고 감점 크기는 코드가 정하므로 이런 폭이 생기지 않습니다.
- **근거 없이 깎음**: 모범 응시에서 Claude는 이유 문장이 전부 칭찬인데도 "다만 중간 확인이 부족했다"처럼 막연한 말로 항목마다 2~6점씩 깎았습니다. 지금 방식은 근거 턴이 없는 감점을 코드가 무효로 처리해서 이런 감점이 남지 않습니다.
- **두 방식 다 못 잡는 것**: "통째로 맡김" 샘플은 두 방식 모두 기대 총점(35)보다 13~15점 높게 줍니다. 두 모델이 같이 놓치는 체크(U2, C1, K2)가 원인이라 점수 방식이 아니라 판정 기준 문장을 고쳐야 줄어듭니다.
- 그 밖의 장점: 응시자와 기업에게 감점 이유를 체크 항목과 근거 턴으로 보여 줄 수 있고, 배점을 바꿔도 프롬프트는 그대로입니다.
- 단점: 체크 항목에 없는 문제는 잡지 못하고, 체크 목록을 만드는 데 손이 많이 듭니다.

### 출력 형식: JSON Schema vs 함수 호출

- JSON Schema와 함수 호출은 둘 다 정해진 구조로 답하게 하는 방식입니다. 함수 호출은 "도구를 부르는" 형태라 응답에서 도구 호출을 꺼내는 단계가 하나 더 있습니다.
- 우리는 도구를 실행하지 않고 판정 결과만 받으므로 JSON Schema가 더 단순하고, Spring AI `BeanOutputConverter`로 두 회사에 같은 클래스를 씁니다.
- 함수 호출 방식으로는 재지 않았습니다. JSON Schema가 0/35로 기준을 넘어서 비교할 이유가 적었습니다.

### 임베딩 모델: 후보가 좁았던 점

- OpenAI 두 모델만 비교했습니다. 이미 OpenAI 키를 쓰고 있어 회사를 늘리지 않으려는 이유였습니다.
- 비교하지 않은 후보: Voyage, Cohere(다국어 모델), bge-m3(공개 모델, 직접 설치하면 자료가 밖으로 안 나감).
- 질문 20개로는 1개 차이가 5%p라서 3-small과 3-large의 차이(19 vs 17)도 확실한 차이라고 보긴 어렵습니다. 3-small이 기준(90%)을 넘고 더 싸다는 것까지가 근거입니다.
- 다시 볼 때: 실제 과제 자료로 질문을 늘렸는데 적중률이 90% 밑으로 떨어지면 bge-m3를 먼저 비교합니다.

### 비용 절감: Batch와 캐시

- **Batch**: 50% 할인이지만 결과가 몇 분~최대 24시간 뒤에 옵니다. 응시 직후 채점(2분 이내)에는 못 쓰고, 지금은 채점 실험 툴(`GraderService`)의 반복 실험에서만 씁니다. 실제 응시 채점(`ScoringService`)은 바로 호출합니다.
- **캐시**: 과제·정답·체크 항목을 앞부분에 고정해 캐시합니다. v4 실험에서 Claude는 입력의 49%, OpenAI는 88%가 캐시에서 읽혔습니다. 다만 같은 샘플을 연달아 채점한 조건이라 높게 나왔을 수 있습니다. 캐시는 몇 분만 유지되므로 실제로는 같은 과제의 응시가 몰려 있을 때만 적중합니다. 실제 적중률은 파일럿에서 확인합니다.

### 벡터 DB: pgvector vs Pinecone vs Qdrant vs Chroma

직접 띄워 비교하지는 않았고, 각 제품 문서와 우리 조건으로 판단했습니다. 14번은 "pgvector로 충분한가"만 쟀습니다.

우리 조건부터 정리하면:

- 검색은 항상 **과제 하나 안**에서만 합니다. 과제 하나의 조각은 수십 개라서, 수백만 개 사이를 빠르게 찾는 능력은 필요 없습니다.
- 과제를 만들거나 지우면 자료 조각도 **같이 생기고 같이 지워져야** 합니다.
- 과제 자료는 회사 시험 문제라서 **밖으로 보내지 않는 쪽**이 좋습니다.
- 인원이 적어서 운영할 서버는 **적을수록** 좋습니다.

| | pgvector | Pinecone | Qdrant | Chroma |
|---|---|---|---|---|
| 형태 | PostgreSQL 확장 | 클라우드 서비스만 있음 | 별도 서버 (직접 설치 또는 클라우드) | 내장형 또는 별도 서버 |
| 장점 | 과제 표와 같은 DB라 SQL 한 번에 거르고, 한 트랜잭션으로 같이 저장·삭제. 백업·모니터링 기존 그대로 | 운영할 게 없음, 큰 규모로 늘리기 쉬움 | 거르기(필터)와 근사 검색을 같이 하도록 만들어짐, 양자화로 메모리 절약 | 설치가 가장 쉬움, 시제품 만들기 좋음 |
| 단점 | 규모가 아주 커지면 전용 DB보다 조정할 수 있는 게 적음, DB와 자원을 나눠 씀, HNSW에 필터를 걸면 결과가 비는 문제 (14번에서 직접 확인) | 과제 자료가 외부로 나감, 쓴 만큼 비용, 회사에 묶임, PostgreSQL과 따로 맞춰야 함 | 서버 하나 더 운영·백업, PostgreSQL과 따로 맞춰야 함 | 공식 클라이언트가 Python·JS 중심, 운영 경험이 덜 쌓임, PostgreSQL과 따로 맞춰야 함 |
| 우리 조건에서 | 과제로 거르면 수십 개라 정확 검색으로 충분 (B-tree로 거른 뒤 전부 비교) | 규모 이점이 쓸모없고 외부 전송이 걸림 | 필터 강점이 있지만 수십 개면 차이 없음 | 시제품 이후에는 이점이 적음 |

**pgvector를 고른 이유**: 전용 벡터 DB들의 강점(큰 규모, 빠른 근사 검색, 필터 결합)은 대부분 "많은 조각 중에서 찾기"에서 나옵니다. 우리는 과제로 먼저 걸러 수십 개만 남기므로 그 강점을 쓸 일이 없습니다. 대신 서버 추가, 두 저장소 맞추기, 외부 전송 같은 비용만 생깁니다.

**바꿔야 할 때**: 과제를 넘어 전체 자료를 한꺼번에 검색하게 되어 근사 검색이 필요해지면 Qdrant를 먼저 검토합니다(필터와 근사 검색을 같이 하는 점이 14번에서 본 HNSW 문제를 직접 해결). Spring AI의 `VectorStore`가 네 가지를 모두 지원해서 바꾸는 비용은 크지 않습니다.

## 서버 구조

```
브라우저 → AWS EC2 (무료): Spring Boot + PostgreSQL (회원, 응시 기록, AI, 채점)
                │ 내부 API (토큰, AWS IP만 허용)
                ▼
           Oracle Cloud (무료 ARM): 실행 서버 (컨테이너, 테스트 실행, 롤백, javac 분석)
```

- 무거운 실행은 Oracle, 응시자 코드는 DB/API 키와 다른 서버에서 실행
- 응시자 배정: 응시 시작 때 가장 한가한 실행 서버를 DB에 기록하고 끝까지 그 서버만 씀. 1대로 시작해 늘면 추가
- 대비: 실행 서버 장애 시 실행 일시 중지와 시간 보정. 제출 파일은 AWS에 보관
