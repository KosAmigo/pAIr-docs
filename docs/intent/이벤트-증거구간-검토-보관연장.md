# 의도: 이벤트 앞뒤 증거 구간 + 감독관 검토 + 보관 연장 (휴대폰 캠 재개)

> 상태: 사용자가 2026-11-23 확정 (interview-me). 구현은 새 세션에서 이 문서를 읽고 시작한다.
> 관련 문서: `기술검증 및 개선/상혁/Worker_분리_설계.md` (특히 10~13장 실측: 분석 Worker 분리, 저사양 측정, 휴대폰 JPEG 크기)

## 목표 (Why)

- 경고(이벤트)가 나면 **그 앞뒤 시간 구간의 이미지**(PC 웹캠 + 휴대폰 뒷캠)를 증거로 저장하고, **감독관·매니저가 완료된 회차에서도** 장면을 훑어보며 확정/기각을 판단하게 한다. 휴대폰 보조 캠을 다시 켠다.
- 이유: 사진 1장은 맥락이 부족하다. 상용 서비스처럼 연속 녹화를 하면 개인정보·저장 부담이 크다. 휴대폰은 영상(WebRTC/TURN) 대신 **JPEG 프레임**으로 보내 연결을 단순하게 한다. 모델은 선별만 하고 판단은 사람이 한다.
- 대상: 응시자(PC + 휴대폰), 감독관, 매니저.

## 하지 않을 것 (Out of scope)

- 연속 영상 녹화, 영상 스트리밍(WebRTC)
- 서버 추론(RunPod 등). 분석은 **응시자 PC 브라우저**에서 한다 (감독관 PC에서 분석하지 않는다)
- 휴대폰에서 직접 분석
- 메일·푸시 등 새 알림 시스템 (알림은 콘솔 표시로 한다)
- 무제한 연장
- 보급형 휴대폰 실측, 아이폰·갤럭시 외 기종 최적화

## 확정된 내용

### 흐름

```
응시자 휴대폰 ─(JPEG 프레임)→ 서버(중계) ─→ 응시자 PC(브라우저, 분석 Worker)
                                             └─(이벤트 + 앞뒤 구간 사진)→ 서버/파일 저장소 ─→ 감독관·매니저 콘솔(보기·판단)
```

- 서버는 분석하지 않는다. 휴대폰 프레임 중계, 사진 저장, 연장·삭제 관리만 한다.
- 응시자 PC에서 **웹캠 분석 Worker**와 **휴대폰 프레임 분석 Worker를 둘로 나눈다** (한쪽 지연·실패가 다른 쪽에 번지지 않게). 휴대폰 분석(손·물체·밝기)은 지금 메인 스레드에서 도는 `phoneAnalysis.ts`를 Worker로 옮기는 것이다. 기존 `VisionBackend` 구조와 폴백(Worker 실패 시 메인)을 재사용한다.
- 느린 PC 대응: 환경 점검의 "이 PC의 분석 속도" 자가 측정에 휴대폰 분석 비용을 포함하고, 느리면 웹캠·휴대폰 분석 간격을 함께 늘린다. 구현 후 코어 제한 측정(`tools/lowspec-bench`)으로 Worker 둘이 동시에 돌 때의 화면 끊김과 분석 속도를 다시 잰다.

### 성공 기준

1. 휴대폰이 **해상도를 고정한 JPEG 프레임**을 보낸다. 기종별로 **장당 약 13~15KB**에 맞춰 화질을 자동 조절한다(아이폰이 같은 설정에서 1.6~1.8배 커서). 변화가 없으면 건너뛰고(평균 변화량 임계값 약 0.04 근처, 작은 물체를 놓치지 않도록 영역별 변화량 검토), **5초마다 생존 신호**를 보낸다. 서버는 오래된 프레임을 버리고 최신만 전달한다.
2. 이벤트가 나면 **앞 8초 / 뒤 4초(시간 기준, 최대 24장)** 를 응시자 PC가 보관했다가 올려 **파일 저장소**에 저장한다. PC 웹캠 프레임도 같은 방식으로 로컬 링 버퍼에 두었다가 이벤트 때만 올린다(연속 업로드 없음).
3. 감독관·매니저가 **완료된 회차**에서 이벤트별 구간을 타임라인으로 보고 **확정/기각**한다.
4. 저장된 사진은 **회차 종료 7일 뒤 자동 삭제**한다. **삭제 예정 2일 이내**면 감독관·매니저가 **연장 버튼**으로 **7일씩, 최대 2번**(총 21일) 연장하고, 누가 언제 연장했는지 **이력**을 남긴다. 콘솔에 "삭제 예정" 표시를 한다.

### 제약

- 연속 녹화·영상 스트리밍 없음. 분석은 응시자 PC 브라우저에서 유지. 전송량과 비용을 낮게 유지(무료 한도 안에서 운영 가능한 수준을 목표).
- 이미지는 DB가 아니라 **파일 저장소**에 두고 DB에는 키와 이벤트 정보만 둔다(기존 감독 사진 보관·`snapshot_deleted_at` 방식 재사용).
- 브랜치 전략: 백엔드는 develop으로 PR, 프론트는 개인 브랜치에서 테스트 후 main merge, 문서는 main에 바로.

### 같이 할 일

- 설계 문서 정리 (위 내용 반영).
- **구현 전 확인**: 완료된 회차에서 감독관·매니저가 스냅샷을 이미 볼 수 있는지(권한, API, 콘솔 화면, 삭제 규칙)를 코드로 확인하고 결과를 보고한다.

### 백엔드(pAIr-back) 범위 (확정 전 추측이었으나 사용자가 확정)

- 휴대폰↔응시자 PC **프레임 중계**(운영용. 지금은 프론트 개발 서버의 `proctorRelay` 플러그인뿐이고 운영 중계는 없다)
- 이벤트 증거 구간 업로드·조회 API
- 보관 연장 API와 이력, 삭제 배치 수정(연장 반영)
- 사진 보관 기간 설정값 정리(코드 기본값 7일과 `application.yml` 30일 불일치 확인)

## 알려진 위험 (구현 때 확인)

- 휴대폰 분석(손·물체)의 PC 비용은 측정하지 않았다. 코어가 적은 PC에서 Worker 둘이 코어를 나눠 쓰면 분석 속도가 더 떨어질 수 있다.
- 변화 감지는 평균 변화량만으로는 작은 물체(이어폰, 메모지) 변화를 놓칠 수 있다.
- 서버 중계는 모든 프레임이 서버를 지나가므로 대역폭·무료 한도·대기열(오래된 프레임 버리기) 설계가 필요하다.
- 휴대폰 보조 캠은 TURN·운영 릴레이 미비로 중단했던 이력이 있다(프레임 방식은 TURN이 필요 없다).
- 아이폰은 인코더가 달라 크기가 다르고, 갤럭시는 손전등이 가능하다. 두 기종 모두 지원한다.
